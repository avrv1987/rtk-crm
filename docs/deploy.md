# Установка и публикация

Документ описывает запуск CRM на Linux-сервере через Docker Compose: демо-стенд по HTTP и публикационный вариант с TLS. Требования ТЗ: §6.4 (Docker), §6.9 (Linux), воспроизводимость развёртывания (NFR-08, [соответствие ТЗ](delivery/Соответствие_ТЗ.md)).

## Состав контура

| Сервис | Образ | Роль | Порт наружу |
|---|---|---|---|
| `web` | `frontend/Dockerfile` (nginx 1.29.2) | единый origin: SPA, прокси `/api/`, Swagger UI и OpenAPI в backend, `/idp/` в Keycloak | 8081 (демо) или 80/443 (публикация) |
| `backend` | `backend/Dockerfile` (Temurin 21 JRE) | Spring Boot API и BFF-вход через OIDC | нет |
| `backend-bootstrap` | тот же образ, профиль Compose `demo` | одноразовое заполнение демо-данных или создание первого администратора без демо-данных; сброс демо-данных к эталону | нет |
| `postgres` | `postgres:16.11-bookworm` | БД CRM и отдельная БД Keycloak | нет |
| `keycloak` | `quay.io/keycloak/keycloak:26.7.4` | realm `rtk-crm`, вход пользователей | нет |
| `clamav` | `clamav/clamav:1.4.6-debian13-slim`, профиль Compose `security` | проверка вложений | нет |
| `site-fixture` | `nginx:1.29.2-alpine`, профиль Compose `demo` | демонстрационный стенд предложенного API сайта (`docs/integrations.md`); поднимается bootstrap-скриптом, только если `SITE_BASE_URL=http://site-fixture:8080` | нет |
| `moodle`, `moodle-db` | `bitnamilegacy/moodle:4.5.4-debian-12-r0`, `mariadb:11.4.5`; отдельный проект `rtk-crm-moodle` (`infra/moodle/compose.yaml`) | настоящий демо-Moodle, постоянная часть демо-стенда; поднимается и настраивается bootstrap-скриптом, пока `DEMO_LMS=true` | `127.0.0.1:8082` (только локально); в публикационном варианте — имя `MOODLE_PUBLIC_HOST` через `web` |

Порядок старта задаётся healthcheck-ами: `web` ждёт healthy `backend` и `keycloak`; `backend` ждёт healthy `postgres`, `keycloak` и, если включён профиль `security`, `clamav`. Healthcheck `backend` — `curl` на `/actuator/health` внутри контейнера; этот путь наружу не проксируется. При первом запуске ClamAV скачивает сигнатуры несколько минут, и `backend` стартует только после этого. У healthcheck ClamAV задан `start_period: 15m`: неудачные проверки во время первой загрузки не считаются, поэтому медленный канал не переводит сервис в `unhealthy`. Если сигнатуры не скачались за 15 минут и следующие три проверки по 30 секунд, `bootstrap-demo.sh` завершается ошибкой; повторный запуск безопасен.

### Профили Compose

| Профиль | Сервисы | Назначение |
|---|---|---|
| `core` — без профиля, поднимается всегда | `web`, `backend`, `postgres`, `keycloak` | обязательный состав системы: интерфейс и API, база данных, вход |
| `security` | `clamav` | антивирусная проверка вложений и загружаемых файлов |
| `demo` | `site-fixture`, `backend-bootstrap`; демо-Moodle — отдельный проект (раздел «Демо-Moodle») | демонстрационные источники и заполнение демо-данных |

Профиль `core` не имеет метки: сервисы без `profiles` в `compose.yaml` запускаются любой командой `docker compose up`. Без профилей запуск такой:

```bash
docker compose --env-file .env.local up -d --wait                         # core
docker compose --env-file .env.local --profile security up -d --wait      # core и ClamAV
docker compose --env-file .env.local --profile security --profile demo up -d --wait
```

Профили можно задать и переменной `COMPOSE_PROFILES` в `.env.local` (через запятую). `bootstrap-demo.sh` и `bootstrap-demo.ps1` записывают туда `security,demo` для демо-стенда и `security` для установки без демо-данных, если значение пустое; флаг `--profile` в командной строке заменяет `COMPOSE_PROFILES`, а не дополняет её. Серверу, который был развёрнут до появления профилей, достаточно один раз запустить bootstrap повторно или дописать `COMPOSE_PROFILES=security` в `.env.local`: без этого ClamAV при следующем `up` не будет создан заново, а `down` его не остановит (команды остановки ниже используют `--profile '*'`).

Без `demo` система пустая: ни вузов, ни пользователей, ни источников. Первого администратора и демо-данные создаёт `backend-bootstrap`; установка без демо-данных запускает его с `DEMO_DATA=false` и создаёт одного администратора. Источники заявок и LMS в этом случае настраиваются на реальные системы (README, раздел «Интеграции»).

Без `security` ClamAV не запущен, а `backend` стартует, не дожидаясь его. Проверка файлов не пропускается, а закрывается отказом:

- вложение к карточке принимается, но получает статус «не удалось проверить», остаётся в карантине и не отдаётся на скачивание;
- импорт каталогов и анкет слушателей из XLSX отклоняется с сообщением «Антивирусная проверка недоступна; повторите позже»;
- остальные функции работают.

Поэтому `security` входит в обе команды bootstrap и в публикационный вариант; отключать его можно только для разработки без работы с файлами.

### ClamAV: проверка готовности и перезапуск

Healthcheck ClamAV — `clamdcheck.sh` из образа: он отправляет `PING` в clamd по TCP 3310, тем же путём, что backend при проверке вложений, и ждёт `PONG`. Живая оболочка контейнера без clamd проверку не проходит; три неудачи подряд (около 1,5 минуты) переводят сервис в `unhealthy`.

Сам по себе `unhealthy` контейнер не перезапускает: Docker без Swarm перезапускает только завершившийся контейнер. В образе ClamAV процесс PID 1 после запуска clamd — `tail -f /dev/null`, поэтому смерть clamd (например, OOM-kill ядром) контейнер не завершала: он оставался `running`, `RestartCount=0`, а вложения не проверялись. Поэтому в `compose.yaml` у `clamav` задан свой entrypoint `infra/clamav/supervise.sh` и `init: true`:

- `supervise.sh` удаляет устаревший сокет, запускает штатный `/init` образа (freshclam и clamd), ждёт появления сокета clamd и дальше раз в 10 секунд проверяет, что процесс `clamd` жив;
- если clamd исчез, скрипт завершается с кодом 1, `docker-init` (PID 1 при `init: true`) завершает контейнер, и `restart: unless-stopped` поднимает его заново; clamd перечитывает сигнатуры из тома `clamav-data` без повторной загрузки;
- если `/init` завершился до запуска clamd (например, не скачались сигнатуры), контейнер тоже завершается и перезапускается, как и раньше.

Перезапуск запускается по исчезновению процесса clamd, а не по неудачному `PING`: под нагрузкой и во время перечитывания сигнатур (`ConcurrentDatabaseReload no` на это время блокирует проверки) `PING` может не пройти у живого clamd, что прервало бы проверки и заново загрузило бы базу примерно на минуту. Зависший, но живой clamd контейнер не перезапускается — его показывает `unhealthy`, перезапуск вручную: `docker compose ... restart clamav`. Пока clamd недоступен, вложения остаются в карантине и не получают статус «Проверен» (fail-closed).

Бюджет памяти: clamd держит в памяти одну копию сигнатур, около 1 ГБ (`ConcurrentDatabaseReload no` не даёт второй копии при обновлении), проверка одного файла ограничена 25 МБ (`StreamMaxLength`, `MaxScanSize`, `MaxFileSize` в `infra/clamav/clamd.conf`). `mem_limit: 2g` оставляет запас на проверки и freshclam. Если памяти не хватает всему серверу (сумма лимитов контейнеров больше RAM), ядро убивает самый крупный процесс — обычно clamd, даже если его собственное потребление ниже лимита 2 ГБ. Контейнер перезапустится сам, но при нехватке памяти clamd может упасть снова: `docker inspect <контейнер clamav> --format '{{.RestartCount}} {{.State.OOMKilled}}'` показывает такие перезапуски, и серверу нужна память (раздел «Требования к серверу»).

### Перезагрузка сервера

Долгоживущие сервисы обоих проектов — `web`, `backend`, `postgres`, `keycloak`, `clamav`, `site-fixture` в `compose.yaml` и `moodle`, `moodle-db` в `infra/moodle/compose.yaml` — объявлены с `restart: unless-stopped`. После перезагрузки сервера или перезапуска Docker они поднимаются сами, повторный bootstrap не нужен; нужно только, чтобы служба Docker стартовала вместе с системой (`systemctl enable docker`). Порядок `depends_on` при таком запуске не соблюдается: `backend` или `web`, поднявшиеся раньше `postgres` и `keycloak`, завершаются с ошибкой и перезапускаются Docker, пока зависимости не станут доступны. Одноразовый `backend-bootstrap` политики перезапуска не имеет. Сервис, остановленный командой `docker compose ... stop`, после перезагрузки остаётся остановленным.

Политика применяется при следующем `bootstrap-demo.sh` (или `docker compose ... up -d`): контейнеры пересоздаются с сохранением томов. После bootstrap `docker inspect` показывает `RestartPolicy=unless-stopped` у всех контейнеров; контейнер, чей процесс завершён изнутри (например, `site-fixture`), Docker поднимает снова тем же способом.

## Демо-Moodle

Демо-стенд по умолчанию включает настоящий Moodle и полностью настроенную интеграцию. Он живёт в отдельном Compose-проекте `rtk-crm-moodle` со своими томами и сетью, поэтому `docker compose ... down` основного стенда его не трогает, а сам Moodle переживает пересоздание CRM.

Пока `DEMO_LMS=true` (значение по умолчанию, записывается в `.env.local`) и `MOODLE_BASE_URL` пуст или равен `http://moodle:8080`, `bootstrap-demo.sh` и `bootstrap-demo.ps1` перед запуском CRM:

1. Генерируют пароли MariaDB, администратора Moodle и учётной записи жюри `crm-jury` в `infra/moodle/.env.local` (права 600) и поднимают `moodle` и `moodle-db` с ожиданием healthy. Первая установка Moodle занимает несколько минут, healthcheck ждёт до 20 минут.
2. Внутри контейнера от пользователя `daemon` выполняют `infra/moodle/demo-setup.php`: включают веб-сервисы и REST, создают пользователя `crm-ws` с системной ролью `crmwsreader` (7 прав на чтение, в том числе `moodle/user:viewdetails`), внешний сервис `crm_readonly` с четырьмя функциями только на чтение и постоянный токен; курсы «Демо: Java-разработчик» (completion включён, группы «Поток А1» и «Поток А2»), «Демо: анализ данных» (completion выключен, группа «Поток Б1») и «Демо: обучение преподавателей» (completion включён, без групп), преподавателя, 10 синтетических учащихся и 4 синтетических слушателей повышения квалификации: 6 активных в курсе Java и один с приостановленным зачислением, 3 завершения, 4 учащихся в курсе анализа данных, 4 слушателя в курсе обучения преподавателей и 3 завершения; для сигналов LMS — курсы «Демо: веб-разработка» (completion включён, 3 учащихся, 1 завершение) и «Демо: информационная безопасность» (только преподаватель). Пользователь `crm-jury` получает роль `crmjuryviewer` на категории демо-курсов — только просмотр курсов, участников, групп и отчёта о завершении (`moodle/course:view`, `moodle/course:viewparticipants`, `moodle/course:enrolreview`, `moodle/site:accessallgroups`, `moodle/user:viewdetails`, `report/completion:view`). Он не зачислен на курсы, поэтому в числа CRM не попадает; пароль передаётся скрипту через переменную окружения `docker compose exec -e`, а не аргументом.
3. Дописывают в `.env.local` `MOODLE_BASE_URL=http://moodle:8080`, `MOODLE_TOKEN`, `MOODLE_COURSE_IDS` и ключи сопоставления `MOODLE_DEMO_JAVA_COURSE`, `MOODLE_DEMO_DATA_GROUP`, `MOODLE_DEMO_TEACH_COURSE`, `MOODLE_DEMO_WEB_COURSE`, `MOODLE_DEMO_EMPTY_COURSE`. Токен на экран не выводится.
4. Запускают `backend` и `backend-bootstrap` с `infra/moodle/compose.crm.yaml`, который подключает их к сети `rtk-crm-moodle`.
5. `backend-bootstrap` создаёт программу «Демо-программа: анализ данных», сопоставляет курс Java целиком с «Университетом А» и программой «Демо-программа: цифровой университет» (поток занятий студентов), курс обучения преподавателей — с той же парой вуз-программа как поток вида «Обучение преподавателей», группу «Поток Б1» — с «Университетом Б» и программой «Демо-программа: анализ данных», все три — с датами: с первого числа текущего месяца (по Москве) на год; курсы веб-разработки и информационной безопасности — со «Школой № 1 (демо)» и программой «Демо-программа: цифровой университет» с потоками «началось 60 дней назад, кончается через 4 дня» и «началось 30 дней назад, кончается через 90 дней» (сигналы LMS, `docs/integrations.md`), и выполняет первую синхронизацию сайта и Moodle от имени `admin`. Сопоставление, которое администратор уже изменил, и источник, у которого уже есть успешный запуск, повтор не трогает; демо-сопоставлению без дат (стенд, поднятый до V15) повтор добавляет эти даты. Неуспешная первая синхронизация завершает bootstrap ошибкой.

Итог на свежем стенде: у `kam-a` в карточке «Демо: внедрение цифрового университета» блок «Обучение (LMS)» (обучающихся 6, завершили 3, не завершили 3, статус неизвестен 0, поток обучения с первого числа месяца запуска на год, групп с обучающимися 2, преподавателей 1) и список «Обучение преподавателей (LMS)» (записано 4, завершили 3) и событие «Данные LMS» в истории; поскольку у этой же работы этап «Обучение преподавателей» ещё не пройден (карточка на первом этапе маршрута), в разделе «Обучение» появляется предложение «Отметить этап выполненным по данным LMS»; у `kam-b` — взаимодействие «Обучение в LMS: Демо: анализ данных» (группа «Поток Б1»: 4 обучающихся, завершение не отслеживается); отчёт «Востребованность программ» показывает заявки сайта, обучающихся и по одному параллельному потоку у каждой из двух программ. Администратор видит в «Источниках данных» оба источника с успешным запуском и записи сайта для разбора, в том числе `pr-demo-006` «Университет Е (нет в CRM)».

Повторный bootstrap ничего не дублирует: Moodle-скрипт находит существующих пользователей, курсы, группы, роль, сервис и токен, CRM не добавляет сопоставлений, а первая синхронизация не повторяется.

Отключение: `DEMO_LMS=false ./scripts/bootstrap-demo.sh` (или строка `DEMO_LMS=false` в `.env.local`). Скрипт очищает демо-значения `MOODLE_*` в `.env.local` и пересоздаёт `backend` без сети Moodle; источник MOODLE в CRM становится ненастроенным, ранее полученные снимки остаются. Сами контейнеры Moodle при этом не останавливаются: `docker compose -p rtk-crm-moodle -f infra/moodle/compose.yaml stop`. Обратное включение — `DEMO_LMS=true ./scripts/bootstrap-demo.sh`: токен и курсы берутся из того же Moodle. Если в `MOODLE_BASE_URL` задан другой Moodle, демо-Moodle не поднимается при любом `DEMO_LMS`.

`scripts/moodle-demo.sh` можно запускать и отдельно: `MOODLE_COMPOSE_PROJECT=...` меняет имя проекта, `MOODLE_CRM_URL` — адрес, который запишется в `MOODLE_BASE_URL`. Ручной эквивалент подключения backend к Moodle — `docker compose --env-file .env.local -f compose.yaml -f infra/moodle/compose.crm.yaml up -d backend`; явные `-f` отменяют `COMPOSE_FILE`, поэтому для публикационного варианта `-f compose.prod.yaml` указывается между ними. Любая последующая команда `up` без `infra/moodle/compose.crm.yaml` пересоздаёт backend без сети Moodle.

Backend видит Moodle через внешнюю сеть `rtk-crm-moodle`; основной `compose.yaml` от неё не зависит. `host.docker.internal` не используется: на Linux он требует `host-gateway` и публикации порта Moodle на внешнем интерфейсе. Порт `8082` опубликован только на `127.0.0.1` — для входа администратора Moodle или `crm-jury` с этой же машины (`http://localhost:8082`, логины и пароли — в `infra/moodle/.env.local`). Moodle образа Bitnami формирует `wwwroot` из заголовка `Host` каждого запроса, поэтому один экземпляр отвечает и на `http://moodle:8080` из сети CRM, и на `http://localhost:8082` с хоста. Схему `https` он берёт из переменной `HTTPS`: `infra/moodle/apache-forwarded-proto.conf` ставит её, когда запрос пришёл с `X-Forwarded-Proto: https` (так запросы приходят от `web` публикационного варианта): запрос с заголовком `X-Forwarded-Proto: https` получает в ответе ссылки `https://<Host>/...`, без заголовка — `http://<Host>/...`.

Плановая синхронизация: `SOURCES_SYNC_CRON` (формат cron Spring из шести полей, часовой пояс Москвы; демо — `0 0 * * * *`, каждый час; `-` отключает). Запуск идёт от имени активного администратора, который последним запускал синхронизацию этого источника; источник, который никто не запускал, по расписанию не синхронизируется. КАМ и руководитель обновляют данные LMS и сайта своей карточки кнопкой «Обновить данные источников» (`docs/integrations.md`).

Полное удаление Moodle вместе с томами — `docker compose -p rtk-crm-moodle -f infra/moodle/compose.yaml down -v` (удаляет только проект Moodle; после него следующий bootstrap установит Moodle заново и выдаст новый токен). Образ `bitnami/moodle` с прежним тегом `4.5.7-debian-12-r2` в Docker Hub отсутствует: Bitnami перенёс образы в `bitnamilegacy`, последний опубликованный там Moodle 4.5 — `4.5.4-debian-12-r0`; этот тег закреплён и обновлений безопасности больше не получает, для демонстрации это приемлемо, для Moodle заказчика неприменимо.

## Требования к серверу

- Linux x86_64 (Ubuntu 22.04+, CentOS Stream 9 или аналог), 4 ГБ RAM и больше: ClamAV ограничен 2 ГБ. Этого хватает для демонстрации; под нагрузкой 50 пользователей и 10 отчётов контейнеры стенда занимали до 3,5 ГБ, поэтому для НФТ6/НФТ7 нужно от 6 ГБ только под стенд ([docs/load-testing.md](load-testing.md)). Демо-Moodle сверх этого; при нехватке памяти ядро убивает clamd, и проверка вложений прерывается до перезапуска контейнера (раздел «ClamAV: проверка готовности и перезапуск»).
- Docker Engine и Docker Compose v2 не ниже 2.24 (нужен тег `!override` в `compose.prod.yaml`).
- `bash` 4+, `openssl` (без него секреты берутся из `/dev/urandom` через `base64`), `sed`, `tr`.
- Доступ в интернет при первой сборке: образы, Maven Central, npm registry, сигнатуры ClamAV.

## Демо-стенд

```bash
git clone <репозиторий> rtk-crm && cd rtk-crm
./scripts/bootstrap-demo.sh
```

Скрипт повторяет `scripts/bootstrap-demo.ps1` без PowerShell:

1. Создаёт или дополняет `.env.local` (права 600): недостающие имена БД и пользователей получают значения по умолчанию, недостающие секреты — случайные 256-битные значения. Уже заданные значения и посторонние ключи сохраняются, порядок строк не меняется. Секреты в вывод не попадают.
2. Поднимает `postgres` и `keycloak` и ждёт healthy.
3. Входит в `kcadm.sh` внутри контейнера Keycloak под bootstrap-администратором; пароль берётся из окружения контейнера, в аргументы команд на хосте не попадает.
4. Повторно применяет `infra/keycloak/rtk-crm-realm.json` к существующему realm. Импорт realm при старте Keycloak выполняется только один раз, поэтому без этого шага изменения политики паролей, журналов событий и языка не дошли бы до уже созданного стенда. В realm включена локализация с единственным языком `ru` (`internationalizationEnabled`, `supportedLocales`, `defaultLocale`): форма входа, её подсказки и ошибки (в том числе о неверном имени пользователя или пароле), смена временного пароля и личный кабинет `/idp/realms/rtk-crm/account` показываются встроенным русским переводом Keycloak, переключателя языка нет. Затем настраивает второй фактор входа (раздел «Второй фактор входа») и роли CRM (раздел «Роли CRM в Keycloak»).
5. Создаёт или обновляет конфиденциальный клиент `crm-bff`: redirect URI `PUBLIC_ORIGIN/api/auth/callback/keycloak`, web origin `PUBLIC_ORIGIN`, атрибут `post.logout.redirect.uris` = `PUBLIC_ORIGIN` и `PUBLIC_ORIGIN/*` (разделитель Keycloak `##`), маппер ролей «crm realm roles». Для `PUBLIC_ORIGIN=http://rtk.localhost:8081` те же значения добавляются для `http://localhost:8081`.
6. Создаёт или обновляет пользователей `kam-a`, `kam-b`, `kam-c`, `kam-d`, `kam-e`, `kam-f`, `kam-g`, `kam-h`, `leader`, `leader-b`, `leader-c`, `admin`, `management`, `enrol`, `partner`, `unprofiled`, `unprofiled-2` и задаёт им пароль `DEMO_USER_PASSWORD`. Каждому демо-пользователю с профилем назначает роль realm по его роли из «Состава демо-данных» (`kam-*` и `enrol` — `crm-user`, `leader*` — `crm-leader`, `admin` — `crm-admin`, `management` — `crm-management`, `partner` — `crm-partner`); `unprofiled*` ролей не получают. После `scripts/secure-demo-accounts.sh` (`DEMO_ACCOUNTS_SECURED=true`) существующих пользователей не трогает, а недостающих создаёт отключёнными (раздел «Демо-пользователи на публикуемом стенде»).
7. Если `DEMO_LMS=true`, поднимает и настраивает демо-Moodle (раздел «Демо-Moodle»); если `SITE_BASE_URL=http://site-fixture:8080`, поднимает стенд API сайта.
8. Записывает `.demo-identities.yml` с реальными `sub` пользователей и, для демо-Moodle, сопоставлениями курса и группы, собирает и поднимает `backend`, `clamav`, `web` с ожиданием healthy и запускает `backend-bootstrap`: профили, команды, вузы, справочники, демо-карточка, сопоставления и первая синхронизация источников.

Повторный запуск безопасен: секреты и данные сохраняются, клиент и пользователи обновляются, CRM-профили и назначения не перезаписываются. Роли, команды и переносы вузов, сделанные администратором в интерфейсе, повтор сохраняет и не считает ошибкой; недостающие демо-профили и организации (например, `kam-d`, `leader-b`, школу и колледж на стенде, поднятом раньше) он добавляет. Команда, которая ещё называется своим ключом (`team-a`, `team-b` на старом стенде), получает имя из конфигурации демо; команду, переименованную администратором, повтор не трогает. Если демо-пользователь успел войти до bootstrap, его профиль создан первым входом и ждёт активации; bootstrap активирует такой профиль с ролью и командой из конфигурации демо, поэтому ранний вход `admin` не оставляет систему без администратора. Профиль, уже активированный или заблокированный администратором, bootstrap не трогает (`docs/roles.md`).

Необязательный аргумент — путь к другому env-файлу: `./scripts/bootstrap-demo.sh /srv/rtk-crm/env`.

В Git Bash на Windows скрипт запускается так же. Он сам задаёт `MSYS2_ARG_CONV_EXCL=/opt/`, если переменная не задана, иначе MSYS превратил бы пути `/opt/keycloak/...` в аргументах `docker compose exec` в пути Windows; на Linux переменная ни на что не влияет. macOS со штатным bash 3.2 не подходит: нужны ассоциативные массивы bash 4+.

Несколько стендов на одной машине разделяются именем проекта Compose: `COMPOSE_PROJECT_NAME=crm2 ./scripts/bootstrap-demo.sh`. Переменная имеет приоритет над `name: rtk-crm` в `compose.yaml`; у второго стенда будут свои контейнеры, сеть и тома, но порт 8081 общий, поэтому одновременно работает только один демо-стенд.

### Установка без демо-данных

Боевая установка создаёт одного администратора CRM и больше ничего:

```bash
cat >> .env.local <<'EOF'
DEMO_DATA=false
CRM_ADMIN_USERNAME=ivanov-admin
EOF
./scripts/bootstrap-demo.sh
```

`DEMO_DATA=false` можно передать и переменной окружения при запуске, она запишется в `.env.local`. В этом режиме скрипт:

- не генерирует `DEMO_USER_PASSWORD` и `SITE_TOKEN`, не поднимает демо-Moodle и стенд сайта (`DEMO_LMS=true` вместе с `DEMO_DATA=false` — ошибка, адрес стенда сайта в `SITE_BASE_URL` очищается); настоящие источники задаются переменными из раздела «Переменные окружения»;
- создаёт в Keycloak одного пользователя `CRM_ADMIN_USERNAME` (по умолчанию `admin`) с именем `CRM_ADMIN_DISPLAY_NAME` (по умолчанию «Администратор») и временным паролем `CRM_ADMIN_PASSWORD`: если пароль не задан, генерируется случайный и записывается только в `.env.local`, в вывод не попадает. Почта администратора — `CRM_ADMIN_EMAIL` (по умолчанию `admin@rtk-crm.local`, помечена подтверждённой): профиль пользователя Keycloak требует почту, и без неё после смены пароля появляется форма «Обновление информации учетной записи». При первом входе Keycloak требует сменить пароль, а при `MFA_REQUIRED_FOR_PRIVILEGED=true` — и подключить приложение-аутентификатор (раздел «Второй фактор входа»);
- передаёт `backend-bootstrap` только этого администратора (`demo-data: false`): создаётся активный профиль CRM с ролью `ADMIN` без команды. Команд, вузов, справочников, карточек, сопоставлений и первой синхронизации нет; базовый шаблон этапов «Базовый процесс ИТ Школы РТК» создаёт миграция V8, он есть в любой установке. Конфигурация с другими пользователями или организациями в этом режиме отклоняется, ничего не записав.

Повторный запуск пароль и учётную запись администратора не меняет: пользователь создаётся только один раз; почта `CRM_ADMIN_EMAIL` дописывается, только если у администратора её нет. Дальше администратор создаёт команды, профили и вузы в интерфейсе или импортом (`docs/import.md`), новые сотрудники входят через Keycloak и ждут активации (`docs/roles.md`). `scripts/reset-demo-data.sh` и `scripts/secure-demo-accounts.sh` в этом режиме отказываются работать.

### Сброс демо-данных

```bash
./scripts/reset-demo-data.sh
```

Скрипт возвращает данные CRM демо-стенда к состоянию сразу после bootstrap, не пересобирая образы и не перезапуская сервисы:

1. Запускает `backend-bootstrap` из уже собранного образа с `APP_DEMOBOOTSTRAP_RESET=true`: Flyway удаляет все объекты схемы CRM и заново применяет миграции, после чего выполняется обычное заполнение демо-данных из `.demo-identities.yml` и первая синхронизация сайта и демо-Moodle. Очистка разрешена только в этом запуске: у работающего `backend` она по-прежнему запрещена (`spring.flyway.clean-disabled` по умолчанию).
2. Очищает внутри работающего `backend` том вложений и каталог готовых файлов отчётов (`APP_REPORTS_STORAGE_ROOT`, по умолчанию `/var/lib/rtk-crm/reports`): после очистки схемы на эти файлы не ссылается ни одна строка `report_jobs`.

Что меняется: исчезают карточки, комментарии, файлы, шаблоны, импорты, отчёты и записи автоматических проверок; профили, роли, команды, вузы и назначения возвращаются к таблице «Состав демо-данных»; профиль `unprofiled`, активированный в ходе проверок, снова отсутствует. Все сеансы CRM завершаются (таблица сеансов тоже пересоздаётся), пользователи входят заново. Keycloak не меняется: пользователи, их пароли и отключения, в том числе после `scripts/secure-demo-accounts.sh`, сохраняются; Moodle не меняется. Запросы пользователей во время сброса получают ошибку. Скрипт отказывается работать без `.demo-identities.yml` и при `DEMO_DATA=false`. Необязательный аргумент — путь к env-файлу. Вариант для PowerShell — `scripts/reset-demo-data.ps1`.

### Роли CRM в Keycloak

Роль сотрудника CRM берёт из ролей realm в ID-токене (`docs/roles.md`, раздел «Роль из Keycloak»). Bootstrap при каждом запуске идемпотентно:

- создаёт роли realm `crm-user`, `crm-leader`, `crm-admin`, `crm-management`, `crm-partner`, если их нет, и делает `crm-admin` составной ролью с `crm-privileged`;
- создаёт или обновляет у клиента `crm-bff` маппер «crm realm roles»: тип `oidc-usermodel-realm-role-mapper` («User Realm Role»), claim `realm_access.roles`, multivalued, добавлять в ID-токен — да, в access-токен, userinfo и introspection — нет (access-токен уже получает `realm_access.roles` из стандартной области `roles`, CRM его не читает). У клиента должен оставаться «Full scope allowed» (по умолчанию), иначе роли realm в токен не попадут;
- назначает роли демо-учёткам или `CRM_ADMIN_USERNAME` (`crm-admin`). Повтор заново назначает демо-учёткам их роль из конфигурации, другие роли, назначенные администратором, не снимает.

Служебному клиенту `crm-account-sync` для назначения и снятия ролей realm достаточно уже выданной роли `realm-management/manage-users`: Admin API `…/users/{id}/role-mappings/realm` и `…/role-mappings/realm/available` требует права управлять пользователем, а назначать роли realm, не являющиеся административными ролями `realm-management`, Keycloak разрешает с `manage-users`. Это минимально необходимый набор; `manage-realm`, `view-realm` и `manage-clients` не нужны. Выдать себе или другим административные роли `realm-management` клиент не может: Keycloak проверяет, что у назначающего они есть.

Установка, где роли до этого лежали только в CRM: после обновления и bootstrap администратор CRM один раз нажимает «Перенести роли в Keycloak» в «Профилях CRM» (`POST /api/admin/crm-profiles/keycloak-roles`). До переноса сотрудники работают по роли из CRM; повторное нажатие безопасно.

Роль в консоли Keycloak (master realm, bootstrap-администратор, или администратор realm `rtk-crm`): Users → пользователь → Role mapping → Assign role → фильтр «Filter by realm roles» → `crm-…` → Assign; снять — Unassign. У сотрудника должна быть ровно одна роль `crm-*` (при нескольких действует старшая: ADMIN → MANAGEMENT → LEADER → USER). Изменение действует со следующего входа; сразу — «Завершить сеансы» в CRM или Users → пользователь → Sessions → Sign out в консоли. Новая роль realm (Realm roles → Create role) сама по себе прав в CRM не даёт: набор ролей CRM задан кодом, новая роль может быть только составной поверх `crm-*` (например, отдел, в который входит `crm-user`). Представителю вуза роль `crm-partner` вручную назначать бессмысленно: без доступа, открытого в карточке вуза, она ничего не открывает.

### Второй фактор входа

При `MFA_REQUIRED_FOR_PRIVILEGED=true` администратор и оператор зачисления входят с одноразовым кодом из приложения-аутентификатора (TOTP: Яндекс Ключ, Google Authenticator, FreeOTP и другие; 6 цифр, 30 секунд, HmacSHA1 — политика OTP в `infra/keycloak/rtk-crm-realm.json`). По умолчанию, при `false` или без переменной, второй фактор выключен: демо-стенд и публикуемый демонстрационный сервер работают без него, жюри входит демо-учётками `admin` и `enrol` без телефона. Используются штатные средства Keycloak 26, без расширений:

- роль realm `crm-privileged` отмечает учётные записи, которым нужен второй фактор;
- поток входа `crm-browser`: cookie сеанса или форма «логин и пароль», за ней условный подпоток «Condition - user role = `crm-privileged`» → «OTP Form». Пользователь с ролью, у которого приложение ещё не подключено, при входе получает от Keycloak шаг подключения (QR-код), остальные входят только по паролю;
- при `true` bootstrap создаёт поток `crm-browser` заново и назначает его потоком входа realm; при `false` возвращает встроенный поток `browser`, удаляет `crm-browser` и снимает с пользователей роли `crm-privileged` незавершённое обязательное действие «Настроить OTP» (`CONFIGURE_TOTP`), если его успел поставить Keycloak. Сотрудник, который уже подключил приложение, во встроенном потоке по-прежнему вводит код (так Keycloak поступает с любым подключённым приложением); отвязать приложение — «Сбросить второй фактор» в CRM.

Bootstrap при каждом запуске создаёт роль, если её нет, и назначает роль администратору `CRM_ADMIN_USERNAME` (без демо-данных) или демо-учёткам `admin` и `enrol`. Кроме того, `crm-admin` включает `crm-privileged`, поэтому администратор, назначенный в консоли Keycloak, проходит второй фактор с первого входа. Дальше роль ведёт CRM: при заведении администратора, смене роли на «Администратор» или с неё и при установке и снятии флага «Оператор зачисления» CRM сразу меняет роль через сервисный клиент `crm-account-sync`; если Keycloak недоступен, изменение профиля не сохраняется. В «Профили CRM» → «⋯» есть «Сбросить второй фактор»: CRM отвязывает приложение сотрудника (потерян телефон), и при следующем входе Keycloak попросит подключить новое (`docs/roles.md`).

Включение — шаг перехода из демонстрационного режима в эксплуатацию, вместе с установкой без демо-данных (`DEMO_DATA=false`). Bootstrap записывает в `.env.local` `MFA_REQUIRED_FOR_PRIVILEGED=false`, если переменной нет; включить:

```bash
sed -i 's/^MFA_REQUIRED_FOR_PRIVILEGED=.*/MFA_REQUIRED_FOR_PRIVILEGED=true/' .env.local
./scripts/bootstrap-demo.sh
```

Перед включением у каждого администратора и оператора зачисления должен быть под рукой телефон с приложением: при следующем входе Keycloak попросит его подключить. Выключить — то же со значением `false`. Действующие сеансы при переключении не прерываются: новый порядок применяется к следующему входу. На стенде, поднятом до появления второго фактора, роль получают только учётки из bootstrap; остальным действующим администраторам и операторам зачисления её назначает кнопка «Сбросить второй фактор» (приложений у них ещё нет) или `kcadm.sh add-roles -r rtk-crm --uusername <логин> --rolename crm-privileged`. Если администратор потерял приложение и другого администратора нет, приложение отвязывают в консоли Keycloak (master realm, bootstrap-администратор): realm `rtk-crm` → Users → пользователь → Credentials → удалить OTP.

|---|---|---|
| «Слушатели» | `MODULE_ENROLMENT_ENABLED` | раздел «Зачисление», анкеты слушателей с персональными данными, оплаты в модуле, файл для LMS по потоку, флаг «Оператор зачисления» |
| Кабинет вуза | `MODULE_PARTNER_ENABLED` | роль PARTNER и вход представителя вуза, кнопка «Открыть доступ в кабинет» у контакта, флаги «Показывать вузу» и «Доступен вузу» |

Как включить:

```bash
sed -i 's/^MODULE_ENROLMENT_ENABLED=.*/MODULE_ENROLMENT_ENABLED=true/; s/^MODULE_PARTNER_ENABLED=.*/MODULE_PARTNER_ENABLED=true/' .env.local
./scripts/bootstrap-demo.sh
```

Если строк в `.env.local` ещё нет (стенд развёрнут до появления флагов), `bootstrap-demo.sh` и `.ps1` допишут их сами: `true` при `DEMO_DATA=true`, иначе `false`; значения, уже записанные в файле, не меняются, а прежняя строка `ENROLMENT_ENABLED` переносится в `MODULE_ENROLMENT_ENABLED`. Так демо-сервер при выкладке не теряет функций. Для модуля «Слушатели» нужны ключи шифрования (`ENROLMENT_*`, их создаёт bootstrap). Выключенный модуль отвечает на все свои методы `404`, его экранов, колонок и справки в интерфейсе нет; данные в базе не удаляются, включение возвращает всё как было. Состояние модулей без входа отдаёт `GET /api/config`.

## Права на секреты в Windows

`.env.local`, `.demo-identities.yml` и `infra/moodle/.env.local` содержат пароли, секреты OIDC-клиентов, ключи шифрования анкет слушателей и токены источников. После каждой записи или обновления любого из этих файлов `bootstrap-demo.ps1` вызывает общую функцию `Protect-SecretFile`: снимает наследование прав и штатным `icacls` оставляет доступ только текущему пользователю, `SYSTEM` (SID `S-1-5-18`) и группе `Administrators` (SID `S-1-5-32-544`) — без новых зависимостей. Группы указаны SID, а не именем: имя `Administrators` локализовано на русской Windows, SID — нет. `secure-demo-accounts.ps1` так же защищает файл индивидуальных паролей `.demo-accounts.local` (и его временный черновик) и обновлённый им `.env.local`. На Linux и macOS ту же роль играет `chmod 600` в bash-версиях тех же скриптов.

`scripts/check-secret-acl.ps1 [-EnvFile <файл>]` проверяет права всех трёх файлов, не читая их содержимое: наследование должно быть отключено, а разрешения — только у текущего пользователя, `SYSTEM` и `Administrators`. Отсутствующий файл пропускается без ошибки. Лишнее разрешение или включённое наследование — строка с путём и причиной, код выхода 1; когда все найденные файлы в порядке (или ни один ещё не создан) — код 0.

### Ротация локальных демо-секретов

Секрет, который мог стать известен посторонним на локальном Windows-стенде, ротируется существующим bootstrap без вывода значений в терминал:

1. В ограниченном текстовом редакторе удалить строку нужного секрета (или весь `.env.local` / `infra/moodle/.env.local`, если скомпрометирован весь файл), не печатая прежнее значение никуда, кроме этого редактора.
2. Запустить `./scripts/bootstrap-demo.ps1` (или `.sh` — на Linux) повторно: недостающий секрет генерируется заново тем же генератором, что при первом запуске, а файл перезаписывается с тем же ограниченным доступом.
3. Если секрет — часть клиента или пользователя Keycloak (`CRM_OIDC_CLIENT_SECRET`, `CRM_ACCOUNT_SYNC_CLIENT_SECRET`, `KEYCLOAK_ADMIN_PASSWORD`, `DEMO_USER_PASSWORD` для ещё не защищённых `secure-demo-accounts` учёток), bootstrap обновляет его в realm тем же запуском; уже открытые сессии со старым секретом не завершаются автоматически — после ротации `CRM_OIDC_CLIENT_SECRET` уместен `docker compose --env-file .env.local up -d --force-recreate --no-deps backend`. Пароли учёток, защищённых `secure-demo-accounts.ps1`/`.sh` (`DEMO_ACCOUNTS_SECURED=true`), ротируются тем же скриптом (раздел «Демо-пользователи на публикуемом стенде»), а не bootstrap.
4. `scripts/check-secret-acl.ps1` — контроль, что права после перезаписи не расширились.

Саму ротацию значений и прав на уже развёрнутом стенде выполняет владелец стенда описанными выше шагами 1–4 и проверяет `check-secret-acl.ps1`.

## Публикационный вариант

`compose.prod.yaml` накладывается на `compose.yaml` и меняет:

- `keycloak`: режим `start --import-realm` вместо `start-dev`. Остальные параметры берутся из основного файла: `KC_HOSTNAME=${PUBLIC_ORIGIN}/idp`, `KC_PROXY_HEADERS=xforwarded`, `KC_HTTP_ENABLED=true` (TLS завершается на nginx, Keycloak доступен только во внутренней сети), `KC_HEALTH_ENABLED=true`. При первом старте в режиме `start` Keycloak выполняет сборку конфигурации, поэтому запуск дольше.
- `backend`: `SESSION_COOKIE_SECURE=true`.
- `web`: публикует 80 и 443 вместо 8081, берёт `infra/web/tls.conf` вместо `infra/web/default.conf` и монтирует сертификат и ключ из `TLS_CERTIFICATE_FILE` и `TLS_CERTIFICATE_KEY_FILE`. Порт 80 отвечает редиректом 301 на `https://<host>`. Снаружи закрыты `/idp/admin/` (консоль и Admin REST API) и `/idp/realms/master/` — ответ 404.

Запуск:

```bash
cat >> .env.local <<'EOF'
PUBLIC_ORIGIN=https://crm.example.ru
TLS_CERTIFICATE_FILE=/etc/ssl/rtk-crm/fullchain.pem
TLS_CERTIFICATE_KEY_FILE=/etc/ssl/rtk-crm/privkey.pem
COMPOSE_FILE=compose.yaml:compose.prod.yaml
EOF
./scripts/bootstrap-demo.sh
```

Compose читает `COMPOSE_FILE` из файла, переданного через `--env-file`, поэтому и скрипт, и ручные команды `docker compose --env-file .env.local ...` работают с публикационным вариантом. Проверка файлов без запуска: `docker compose --env-file .env.local config --quiet`.

`PUBLIC_ORIGIN` должен совпадать с адресом, который видит браузер, без порта для 443. После смены `PUBLIC_ORIGIN` скрипт нужно запустить повторно: он обновит redirect URI клиента, а `.demo-identities.yml` получит новый issuer.

### Moodle для жюри

Демо-Moodle публикуется за тем же nginx `web` и тем же сертификатом, но под отдельным именем хоста, а не путём `/lms/`. Путь не подходит: Moodle строит все ссылки из `wwwroot`, а образ Bitnami установлен в корень сайта, поэтому префикс пути пришлось бы переписывать в HTML, JavaScript и переадресациях. Отдельное имя сохраняет корень, `wwwroot` получается из `Host` запроса, а схема — из `X-Forwarded-Proto` (раздел «Демо-Moodle»).

```bash
cat >> .env.local <<'EOF'
MOODLE_PUBLIC_HOST=lms.crm.example.ru
EOF
./scripts/bootstrap-demo.sh
```

- DNS-имя `MOODLE_PUBLIC_HOST` указывает на тот же сервер, сертификат `TLS_CERTIFICATE_FILE` содержит оба имени (SAN) или является wildcard.
- Bootstrap добавляет `infra/moodle/compose.crm.prod.yaml`: `web` подключается к сети `rtk-crm-moodle`, получает шаблон `infra/web/moodle-tls.conf` — сервер 443 с `server_name ${MOODLE_PUBLIC_HOST}`, `proxy_pass http://moodle:8080`, заголовками `Host` и `X-Forwarded-Proto: https`, лимитом тела 100 МБ. Порт 80 отвечает переадресацией на HTTPS для любого имени (`tls.conf`).
- CRM по-прежнему обращается к Moodle по внутреннему адресу `http://moodle:8080`; токен наружу не выходит.
- Жюри входит в Moodle под `crm-jury` (пароль `MOODLE_JURY_PASSWORD` из `infra/moodle/.env.local`): только просмотр демо-курсов, участников, групп и отчёта о завершении, без права что-либо менять. Учётная запись администратора Moodle жюри не передаётся: образ `bitnamilegacy/moodle:4.5.4-debian-12-r0` закреплён и обновлений безопасности не получает. Учётная запись `crm-ws` для входа в интерфейс не предназначена.
- По той же причине Moodle публикуется только на время показа. После показа строка `MOODLE_PUBLIC_HOST` удаляется из `.env.local` и `bootstrap-demo.sh` запускается снова: `web` пересоздаётся без сервера Moodle, а CRM продолжает читать Moodle по внутренней сети. На время показа доступ к имени `MOODLE_PUBLIC_HOST` можно дополнительно ограничить адресами жюри на сетевом экране сервера.

Проверено без запуска: `docker compose -f compose.yaml -f compose.prod.yaml -f infra/moodle/compose.crm.yaml -f infra/moodle/compose.crm.prod.yaml config` с тестовыми значениями — `web` в сетях `rtk-crm` и `rtk-crm-moodle`, шаблон смонтирован; `nginx -t` образа `nginx:1.29.2-alpine` с `tls.conf`, `moodle-tls.conf` и самоподписанным сертификатом — синтаксис верен. Живая публикация с настоящим сертификатом не выполнялась.

Администрирование Keycloak в публикационном варианте выполняется изнутри контейнера: `docker compose --env-file .env.local exec keycloak /opt/keycloak/bin/kcadm.sh ...`.

### Демо-пользователи на публикуемом стенде

При `DEMO_DATA=true` скрипт и в публикационном варианте создаёт демо-пользователей из таблицы «Состав демо-данных» с одним общим паролем `DEMO_USER_PASSWORD`, в том числе `admin` с ролью CRM `ADMIN`. Пока пароль известен кому-то кроме администратора стенда, любой из этих пользователей может войти в CRM с его правами. Боевая установка делается без демо-данных (раздел «Установка без демо-данных»).

Перед открытием стенда посторонним демо-учётки получают индивидуальные пароли, а ненужные отключаются:

```bash
./scripts/secure-demo-accounts.sh kam-a kam-b leader admin
```

Аргументы — учётные записи, которые остаются доступными; остальные демо-учётки (`kam-a`, `kam-b`, `kam-c`, `kam-d`, `kam-e`, `kam-f`, `kam-g`, `kam-h`, `leader`, `leader-b`, `leader-c`, `admin`, `management`, `enrol`, `partner`, `unprofiled`, `unprofiled-2`) отключаются. Скрипт для каждой демо-учётки:

- задаёт новый случайный пароль; пароли оставленных учётных записей записываются в `.demo-accounts.local` в корне проекта (права 600, файл в `.gitignore`, при каждом запуске перезаписывается), на экран не выводятся; пароль отключённой учётки нигде не сохраняется. Пароли пишутся сначала во временный файл `.demo-accounts.<случайный суффикс>` с теми же правами; если скрипт прерывается посреди списка, этот файл с уже выданными паролями остаётся, скрипт называет его путь и просит запустить себя повторно (повтор выдаёт всем учёткам новые пароли и доводит отключение до конца), а прежний `.demo-accounts.local` не меняется;
- включает оставленные и отключает остальные учётные записи Keycloak;
- завершает их сеансы Keycloak и удаляет их сеансы CRM (`spring_session` по имени пользователя), поэтому прежний общий пароль и уже открытые вкладки перестают работать сразу;
- записывает `DEMO_ACCOUNTS_SECURED=true` в `.env.local`.

После показа тот же скрипт без аргументов отключает все демо-учётки: `./scripts/secure-demo-accounts.sh`. Повторный запуск с другим списком выдаёт новые пароли. Пароли передаются жюри по защищённому каналу, файл после передачи удаляется.

Защита не отменяется повторным `bootstrap-demo.sh` (например, при обновлении): пока в `.env.local` стоит `DEMO_ACCOUNTS_SECURED=true`, bootstrap не меняет пароли и признак «включена» существующих демо-пользователей, а недостающих создаёт отключёнными и без пароля. Вернуть общий пароль всем демо-учёткам можно только явно: удалить строку `DEMO_ACCOUNTS_SECURED` из `.env.local` и запустить bootstrap. Необязательный первый аргумент `--env-file <файл>` задаёт другой env-файл; вариант для PowerShell 7 — `scripts/secure-demo-accounts.ps1 [-EnvFile <файл>] kam-a leader`: файл паролей доступен только текущему пользователю, `SYSTEM` и `Administrators` (на Windows `icacls` снимает наследование и оставляет записи для этих трёх SID, на Linux и macOS — `chmod 600`) ещё до записи первого пароля; обновлённый `.env.local` защищается так же (раздел «Права на секреты в Windows»). При `DEMO_DATA=false` скрипт отказывается работать: демо-учёток нет.

Сотрудников заводят, сбрасывают им пароль и завершают сеансы кнопками в «Администрирование → Профили CRM» (`docs/roles.md`). Запасной путь — когда CRM ещё недоступна или нужна первая учётная запись администратора сверх `CRM_ADMIN_USERNAME` — изменить учётную запись вручную изнутри контейнера: `docker compose --env-file .env.local exec keycloak /opt/keycloak/bin/kcadm.sh set-password -r rtk-crm --username <логин>` после входа `kcadm.sh config credentials` под bootstrap-администратором; `set-password` без `--new-password` запрашивает пароль в терминале.

### Внешний TLS-прокси

Если TLS завершает корпоративный прокси, возможны два варианта.

- Прокси обращается к `web` по HTTPS на 443 — используется `compose.prod.yaml` без изменений.
- Прокси обращается к `web` по HTTP на 8081 — используется только `compose.yaml` с `PUBLIC_ORIGIN=https://...`, `SESSION_COOKIE_SECURE=true` и `TRUSTED_PROXY_CIDR` = адрес прокси, каким его видит контейнер `web`. Тогда nginx передаёт в backend и Keycloak полученные от прокси `X-Forwarded-Proto` и `X-Forwarded-For`; от остальных адресов эти заголовки заменяются на `$scheme` и `$remote_addr`. `X-Forwarded-Host` всегда равен `Host` запроса, а `Forwarded`, `X-Forwarded-Port` и `X-Forwarded-Prefix` удаляются для всех адресов: Spring (`server.forward-headers-strategy: framework`) ставит `Forwarded` выше `X-Forwarded-*`, и без этого клиент мог бы подменить схему, порт и префикс адреса. Keycloak в этом варианте остаётся в `start-dev`, а `/idp/admin/` открыт, поэтому для публикации предпочтителен первый вариант.

## Размещение за общим обратным прокси

На сервере, где TLS и маршрутизацию по доменам уже выполняет общий прокси (например отдельный Caddy в сети Docker `edge`, общий для нескольких проектов), `compose.prod.yaml` не подходит: он сам занимает порты 80 и 443. Вместо него накладывается `compose.edge.yaml`:

- `web` не публикует портов и подключается к внешней сети `edge` (имя меняется переменной `EDGE_NETWORK`) и к сети демо-Moodle `rtk-crm-moodle`;
- nginx доверяет заголовкам `X-Forwarded-*` только от подсети общего прокси (`EDGE_PROXY_CIDR`, по умолчанию `172.18.0.0/16`);
- Keycloak работает в режиме `start`, cookie сессии получает флаг `Secure`;
- демо-Moodle публикуется через тот же nginx по имени `MOODLE_EDGE_HOST` (шаблон `infra/web/moodle-edge.conf`), CRM обращается к нему по внутреннему адресу `http://moodle:8080`;
- у контейнеров заданы ограничения памяти, чтобы стенд не вытеснял соседние проекты; у Moodle ограничения заданы в `infra/moodle/compose.yaml`, а ClamAV не держит две копии сигнатур при обновлении (`ConcurrentDatabaseReload no`).

Порядок установки:

```bash
cat >> .env.local <<'ENV'
PUBLIC_ORIGIN=https://crm.example.ru
COMPOSE_FILE=compose.yaml:compose.edge.yaml
MOODLE_EDGE_HOST=lms.example.ru
ENV
nice -n 10 ./scripts/bootstrap-demo.sh
```

В конфигурацию общего прокси добавляется блок проекта, например для Caddy:

```
crm.example.ru {
	@kcadmin path /idp/admin /idp/admin/* /idp/realms/master /idp/realms/master/*
	respond @kcadmin 404
	reverse_proxy rtk-crm-web-1:8080
}

lms.example.ru {
	reverse_proxy rtk-crm-web-1:8080
}
```

Перед правкой общего прокси сохраняется копия его конфигурации и выполняется проверка синтаксиса (`caddy validate`). У каждого имени должна быть A-запись на сервер и не должно быть посторонней AAAA-записи: иначе Let's Encrypt проверяет домен по IPv6 на чужом адресе и не выдаёт сертификат.

## Nginx

Общие правила сервера — `infra/web/crm-site.conf`, подключается из `infra/web/default.conf` (HTTP) и `infra/web/tls.conf` (HTTPS). Оба файла монтируются как шаблон `/etc/nginx/templates/default.conf.template`; штатный entrypoint образа nginx подставляет `TRUSTED_PROXY_CIDR` через `envsubst`.

Файлы смонтированы в контейнер и читаются только при его старте, а `up -d --build` не пересоздаёт контейнер, если образ не изменился. Поэтому `bootstrap-demo.sh` и `bootstrap-demo.ps1` после запуска сервисов пересоздают `web` (`up -d --wait --force-recreate --no-deps web`). После правки `infra/web/*.conf` на работающем стенде без bootstrap: `docker compose --env-file .env.local up -d --force-recreate --no-deps web`.

- В backend проксируются `/api/`, `/swagger-ui`, `/v3/api-docs`, `/openapi.yaml`; в Keycloak — `/idp/` со снятием префикса. `/healthz` отвечает сам nginx статикой `200 ok`, backend и Keycloak не трогает — на него ходит healthcheck `web` в `compose.yaml`.
- `client_max_body_size 21m` совпадает с `spring.servlet.multipart.max-request-size: 21MB`; лимит одного файла — 20 МБ (`app.attachments.max-file-size`). Превышение на nginx возвращает JSON `{"code":"PAYLOAD_TOO_LARGE","message":"Размер запроса превышает допустимый: не более 20 МБ на файл","requestId":...}` с кодом 413 и `Content-Type: application/json; charset=utf-8` в формате `ApiError`. Запрос не дошёл до backend, поэтому `requestId` строится из `$request_id` nginx: 32 шестнадцатеричных символа разбиваются дефисами в вид UUID (`map` в `default.conf` и `tls.conf`), как требует `ApiError.requestId` в `openapi.yaml`.
- gzip для CSS, JavaScript, JSON, YAML (`/openapi.yaml`) и SVG от 1 КБ, в том числе для запросов через прокси (`gzip_proxied any`). Ответ содержит `Vary: Accept-Encoding` (`gzip_vary on`), чтобы общий кеш не отдал сжатую версию клиенту без поддержки gzip.
- Клиентские `Forwarded`, `X-Forwarded-Port` и `X-Forwarded-Prefix` дальше не передаются; `X-Forwarded-For` и `X-Forwarded-Proto` принимаются только от `TRUSTED_PROXY_CIDR`.
- `/assets/` (файлы Vite с хешем в имени) отдаются с `Cache-Control: public, max-age=31536000, immutable`, шрифты `/fonts/` — с `Cache-Control: public, max-age=31536000` (при замене файла шрифта меняется его имя), `index.html` и прочие пути SPA — с `Cache-Control: no-cache`.
- Заголовки безопасности — на каждом ответе SPA и статики (`/`, `/index.html`, `/assets/`, `/fonts/`, ответ 413 из `@payload_too_large`): состав в `infra/web/security-headers.conf`, подключён через `include` в каждый такой `location` отдельно, а не только на уровне `server` — `add_header` не наследуется во вложенный `location`, если в нём уже есть свой `add_header` (здесь это `Cache-Control`). Заголовки: `Content-Security-Policy` (`default-src 'self'`; frontend не использует инлайновые скрипты и стили — проверено по `frontend/dist` после сборки), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, короткая `Permissions-Policy`. `Strict-Transport-Security` — картой `$crm_hsts` в `default.conf` и `tls.conf` от того же `$crm_forwarded_proto`, что и остальные `X-Forwarded-*`: значение только при HTTPS, на локальном HTTP заголовка нет вовсе (пустое значение `add_header` в nginx заголовок не отправляет). `server_tokens off` скрывает версию в `Server`. Не тронуты: `/idp/` (своя CSP Keycloak), `/api/`+`/swagger-ui`+`/v3/api-docs` (заголовки Spring Security по умолчанию — HSTS/nosniff/X-Frame-Options уже приходят, дублировать нечем; своя CSP для Swagger UI не заведена, см. «Ограничения» ниже). Демо-Moodle (`moodle-edge.conf`, `moodle-tls.conf`) получил только `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options: SAMEORIGIN` и `Permissions-Policy` — без CSP и без HSTS: Moodle использует инлайновые скрипты, а `X-Forwarded-Proto` там не проверяется картой доверенных адресов, как для CRM.

## Тесты backend в Docker

Образ собирается быстрым путём без тестов. Тесты запускаются отдельной стадией того же `backend/Dockerfile`, JDK и Maven на хосте не нужны:

```bash
docker build --target test backend
```

Успешная сборка стадии означает, что `mvn -B test` прошёл. BuildKit кеширует успешную стадию; для принудительного повтора — `docker build --no-cache-filter test --target test backend`.

## Резервное копирование и восстановление

```bash
./scripts/backup.sh /srv/backup/rtk-crm/2026-09-24
./scripts/restore.sh /srv/backup/rtk-crm/2026-09-24
```

Второй необязательный аргумент обоих скриптов — env-файл, по умолчанию `.env.local`.

`backup.sh` работает на запущенном стенде и пишет в новый или пустой каталог (umask 077). Каждый файл шифруется на лету, до записи на диск: `openssl enc -aes-256-cbc -pbkdf2 -iter 600000 -md sha256` на хосте (нужен OpenSSL 1.1.1 и новее, есть в Ubuntu, Debian и Git Bash):

- `crm.dump.enc` и `keycloak.dump.enc` — `pg_dump --format=custom` БД CRM и Keycloak, выполняется в контейнере `postgres`;
- `attachments.tar.enc` — содержимое тома `attachments-data` (вложения, включая карантин); архив создаёт одноразовый контейнер образа `backend`, путь берётся из `APP_ATTACHMENTS_STORAGE_ROOT`;
- `reports.tar.enc` — содержимое тома `reports-data` (готовые файлы заказанных отчётов, `APP_REPORTS_STORAGE_ROOT`, по умолчанию `/var/lib/rtk-crm/reports`), тем же способом;
- `SHA256SUMS` — контрольные суммы четырёх зашифрованных файлов: проверяются без ключа.

Ключ — `BACKUP_ENCRYPTION_KEY` из окружения или env-файла (bootstrap генерирует его в `.env.local`) либо файл `BACKUP_ENCRYPTION_KEY_FILE` с правами 600 или 400 (первая строка; права проверяются через `stat`, поэтому файл с ключом работает на Linux, в Git Bash на Windows — ключ из переменной). Сгенерировать ключ в файл: `(umask 077; openssl rand -base64 48 > /root/rtk-crm-backup.key)`. Если ключ не задан ни в окружении, ни в env-файле (стенд, поднятый до шифрования копий), `backup.sh` генерирует новый, дописывает строку `BACKUP_ENCRYPTION_KEY=` в env-файл, предупреждает об этом в stderr и делает зашифрованную копию; прежние вызовы, в том числе из скриптов выкладки, продолжают работать. После этого копию `.env.local` вне сервера нужно обновить. Если env-файл недоступен для записи, ключ короче 32 символов или файл `BACKUP_ENCRYPTION_KEY_FILE` не читается или доступен другим, скрипт завершается с ошибкой и ничего не пишет: незашифрованной копии он не делает. После записи он расшифровывает начало обоих дампов и проверяет заголовок `PGDMP`. Ключ хранят отдельно от копий, вместе с копией `.env.local`: без него копию не восстановить. Расшифровать файл вручную: `openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -md sha256 -pass env:BACKUP_ENCRYPTION_KEY -in crm.dump.enc -out crm.dump` (или `-pass file:<путь к ключу>`). Шифрование без проверки подлинности: подмену файла выявляет `SHA256SUMS`, только если он хранится отдельно от копии.

Проверка скриптов без Docker: `bash scripts/backup-test.sh` подменяет `docker` заглушкой и проверяет на временном каталоге появление ключа в env-файле, отказ с коротким ключом или недоступным файлом ключа, отсутствие открытых данных в копии, `SHA256SUMS`, восстановление с верным ключом, остановку до изменений стенда при чужом ключе, восстановление старой незашифрованной копии и проверку прав файла ключа.

Сервисы не останавливаются. Файлы отчётов архивируются первыми, затем БД, затем вложения. Загрузка вложения во время копирования может оставить в архиве файл без записи в БД. Отчёт, достроенный во время копирования, наоборот, попадёт в БД без файла и после восстановления ответит `410 REPORT_RESULT_UNAVAILABLE` — его заказывают заново; зато в копии не бывает файлов отчётов без записи в БД, которые не удалил бы срок хранения. Копию лучше делать в период без загрузок и заказов. Том `clamav-data` не копируется: сигнатуры скачиваются заново.

Файлы отчётов лежат в именованном томе `reports-data`, поэтому переживают пересоздание `backend` (`up --force-recreate`, обновление образа, `down` без `-v`); без тома пересоздание удаляло бы файлы вместе с контейнером, задание при этом оставалось бы `SUCCEEDED`, а скачивание возвращало бы `410`. Том создаётся из образа с владельцем `crm`, поэтому обновлять нужно с пересборкой: `bootstrap-demo.sh` или `docker compose ... up -d --build backend`.

Копия содержит персональные данные CRM и БД Keycloak с хешами паролей и секретом клиента `crm-bff`. Её хранят вне сервера с ограниченным доступом и не включают в публикуемый комплект. `.env.local` в копию не входит и хранится отдельно: для восстановления нужен тот же файл, потому что секрет клиента `crm-bff` записан и в нём, и в БД Keycloak.

`restore.sh` восстанавливает копию на существующий стенд или в новое место: другой сервер или другое имя проекта Compose. Нужны клон репозитория, `.env.local` исходного стенда и тот же `PUBLIC_ORIGIN`: профили CRM связаны с issuer `PUBLIC_ORIGIN/idp/realms/rtk-crm`. Скрипт:

1. Проверяет `SHA256SUMS` и при расхождении завершается, ничего не меняя. Если в копии зашифрованные файлы, берёт ключ так же, как `backup.sh`, и расшифровывает начало обоих дампов; неверный ключ останавливает восстановление до любых изменений стенда. Дальше файлы расшифровываются потоком, открытые копии на диск не пишутся. Копия, сделанная до шифрования (`crm.dump`, `keycloak.dump`, `attachments.tar`), восстанавливается без ключа. Копия без `reports.tar` восстанавливается с предупреждением в stderr: файлы отчётов не восстанавливаются, готовые отчёты отвечают `410 REPORT_RESULT_UNAVAILABLE` и заказываются заново.
2. Поднимает `postgres`. На пустом томе init-скрипт создаёт роли и пустые БД.
3. Останавливает `web`, `backend`, `keycloak`.
4. Удаляет и заново создаёт обе БД, загружает дампы через `pg_restore --no-owner --no-privileges --role=<роль БД>`, поэтому владельцем объектов становится роль из `.env.local`.
5. Очищает том вложений и распаковывает `attachments.tar`; очищает том отчётов и распаковывает `reports.tar`, если он есть в копии, с владельцем `crm` (так том пригоден для записи и тогда, когда его впервые создал ещё старый образ `backend`).
6. Поднимает `keycloak`, `clamav`, `backend`, `web` с ожиданием healthy.

Текущие данные стенда при восстановлении удаляются. `bootstrap-demo.sh` после восстановления не нужен. Восстановление можно выполнить в другой проект Compose (другое имя проекта или другой сервер) с новыми томами; данные CRM и Keycloak, включая id профилей и вход пользователей, совпадают с исходным стендом. Повторный `restore.sh` на уже заполненном стендом приводит к тому же состоянию; изменённый `attachments.tar` останавливает восстановление на проверке контрольных сумм.

### Копирование по расписанию

`scripts/backup-scheduled.sh <каталог-копий> [число-копий] [env-file]` — обёртка над `backup.sh` для запуска по расписанию. Число хранимых копий по умолчанию 7; срок хранения определяет оператор ПДн (копии содержат ПДн и хеши паролей). За один запуск скрипт:

1. Проверяет, что каталог копий доступен для записи, берёт блокировку `flock` на файл `.lock` в нём и только после этого удаляет оставшиеся от прерванных запусков каталоги `.partial-*`. Если предыдущий запуск ещё идёт, новый завершается сбоем «another backup is already running» и ничего не удаляет; блокировка снимается сама при завершении процесса, в том числе аварийном. Нужна утилита `flock` (пакет `util-linux`).
2. Выполняет `backup.sh` в каталог `.partial-<время UTC>`; вывод `backup.sh` пишется в `backup.log`.
3. Проверяет `SHA256SUMS` (`sha256sum --check`; заголовок `PGDMP` обоих дампов уже проверил `backup.sh`), затем переименовывает каталог в `<время UTC>`, например `2026-09-25T020000Z`. Незавершённая или повреждённая копия под этим именем не появляется.
4. Удаляет самые старые копии сверх заданного числа и записывает время копии в `last-success`.

При любом сбое (каталог недоступен для записи, ошибка `backup.sh`, расхождение контрольных сумм) скрипт удаляет незавершённый каталог, старые копии не трогает, пишет строку `FAILED` в `backup.log`, выводит в stderr причину и время последней успешной копии, отправляет то же сообщение в системный журнал (`logger -t rtk-crm-backup -p user.err`, если `logger` есть) и завершается с кодом 1. Журнал запусков — `backup.log` в каталоге копий (строки `START`, `OK`, `ROTATED`, `FAILED`), время последней успешной копии — файл `last-success`.

Задание запускается от несистемного пользователя из группы `docker`, от имени которого выполнялся bootstrap (ему принадлежат каталог проекта и `.env.local` с правами 600), а не от root: для root проверка «каталог доступен для записи» всегда проходит, потому что root пишет и в каталог с правами 555. Ежедневная копия в 02:00 с хранением трёх копий через cron такого пользователя (`crontab -u deploy -e`, где `deploy` — этот пользователь):

```cron
MAILTO=admin@example.ru
0 2 * * * /srv/rtk-crm/scripts/backup-scheduled.sh /srv/backup/rtk-crm 3 /srv/rtk-crm/.env.local
```

Cron отправляет на `MAILTO` всё, что скрипт вывел, а при успехе скрипт молчит, поэтому письмо приходит только о сбое (нужен настроенный локальный MTA). Без почты сбой виден в системном журнале: `journalctl -t rtk-crm-backup` или `/var/log/syslog`.

Вариант с systemd: служба с `OnFailure=` запускает уведомление при коде выхода, отличном от 0, а `systemctl list-timers` показывает время последнего и следующего запуска.

```ini
# /etc/systemd/system/rtk-crm-backup.service
[Unit]
Description=RTK CRM backup
OnFailure=rtk-crm-backup-failed.service

[Service]
Type=oneshot
User=deploy
ExecStart=/srv/rtk-crm/scripts/backup-scheduled.sh /srv/backup/rtk-crm 3 /srv/rtk-crm/.env.local

# /etc/systemd/system/rtk-crm-backup.timer
[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

`rtk-crm-backup-failed.service` — любая команда уведомления, принятая у оператора (почта, мессенджер, система мониторинга). Включение: `systemctl daemon-reload && systemctl enable --now rtk-crm-backup.timer`. Копия, созданная по расписанию, восстанавливается тем же `restore.sh` с путём к каталогу копии. Каталог копий лучше держать на отдельном диске или регулярно переносить копии вне сервера (раздел выше).

Проверка уведомления о сбое: `chmod 555 /srv/backup/rtk-crm` и запуск задания вручную (`systemctl start rtk-crm-backup.service` или команда из crontab от того же пользователя) дают код 1, сообщение «is not writable» в stderr и системном журнале; `chmod 755` возвращает каталог. Если задание всё же выполняется от root, каталог делают недоступным для записи иначе: `chattr +i /srv/backup/rtk-crm` (снимается `chattr -i`) или монтирование только для чтения (`mount --bind -o ro`).

Хранение сверх заданного числа копий заменяет самые старые новыми, а параллельный запуск во время ещё идущего блокируется `flock` и завершается кодом 1 со строкой `FAILED another backup is already running`, не трогая каталог `.partial-*` первого запуска.

## Остановка и удаление

```bash
docker compose --env-file .env.local --profile '*' stop
docker compose --env-file .env.local --profile '*' down
docker compose --env-file .env.local --profile '*' down -v
```

`down` сохраняет тома с БД, вложениями, файлами отчётов и сигнатурами ClamAV; `down -v` удаляет их вместе с данными.

Демо-Moodle — отдельный проект, эти команды его не касаются: `docker compose -p rtk-crm-moodle -f infra/moodle/compose.yaml stop` останавливает его с сохранением данных, `... down -v` удаляет вместе с томами (раздел «Демо-Moodle»). `scripts/backup.sh` Moodle не копирует: его демо-данные воспроизводит bootstrap.

## Ограничения

- `bootstrap-demo.sh`, `backup.sh`, `restore.sh`, `secure-demo-accounts.sh`, `reset-demo-data.sh` и `release-gate.sh`/`.ps1` разработаны и проверены в Git Bash на Windows и в WSL/bash 4+; отдельной проверки на выделенном Linux-сервере под управлением Docker Engine ещё не было.
- `Content-Security-Policy` и `Strict-Transport-Security` заданы только для SPA и статики (раздел «Nginx»); `/api/`, `/swagger-ui`, `/v3/api-docs` получают заголовки Spring Security по умолчанию без собственной CSP.
- Копирование по расписанию — `backup-scheduled.sh` из cron или таймера systemd (раздел «Копирование по расписанию»); в интерфейсе CRM дата последней копии не показывается, её видно в `last-success`, `backup.log` и системном журнале.
- `secure-demo-accounts.ps1` и другие варианты скриптов для PowerShell совместимы с Windows PowerShell 5.1.
- Перечень сторонних компонентов и лицензий — `docs/licenses.md`.
- `Protect-SecretFile` в `bootstrap-demo.ps1` и `Protect-File` в `secure-demo-accounts.ps1` (раздел «Права на секреты в Windows») ограничивают доступ к секретам текущим пользователем, `SYSTEM` и `Administrators`; `scripts/check-secret-acl.ps1` проверяет права всех трёх файлов, не читая их содержимое.

## Зеркало Maven при сборке образа

Образ backend собирается Maven внутри Docker и скачивает зависимости из центрального репозитория. Если он недоступен с машины сборки (отказ 403 или таймаут), задайте зеркало переменной `MAVEN_MIRROR_URL` в окружении или в `.env.local`, например `MAVEN_MIRROR_URL=https://maven-central.storage-download.googleapis.com/maven2`. Без переменной сборка идёт напрямую в центральный репозиторий.
