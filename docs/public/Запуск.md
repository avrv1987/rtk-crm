# Запуск CRM ИТ Школы РТК

Документ описывает, как поднять систему на своём компьютере или сервере, что при этом запускается, как войти, как подключить настоящие системы вместо демонстрационных, как делать резервные копии и обновлять систему. Устройство системы — в [описании архитектуры](Архитектура.md), работа по ролям — в [инструкциях пользователей](Инструкции_пользователей.md).

## Требования

- Linux x86_64 (например Ubuntu 22.04 или новее) или Windows с Docker Desktop (WSL2).
- Docker Engine и Docker Compose v2 не ниже 2.24.
- `bash` 4 и новее и `openssl` (в Windows без bash — PowerShell 7 и новее). Стандартный bash в macOS слишком старый.
- Память: 4 ГБ для демонстрации, от 6 ГБ при нагрузке с десятками пользователей и одновременными отчётами. Антивирусу нужно около 2 ГБ.
- Доступ в интернет при первой сборке: образы Docker, зависимости Java и JavaScript, сигнатуры антивируса.

## Получение кода

```bash
git clone https://github.com/avrv1987/rtk-crm.git
cd rtk-crm
```

## Запуск демонстрационного стенда

Одна команда:

```bash
./scripts/bootstrap-demo.sh
```

В Windows без bash:

```powershell
pwsh -NoProfile -File ./scripts/bootstrap-demo.ps1
```

Скрипт:

1. создаёт файл `.env.local` со случайными паролями и ключами (он не попадает в git, права доступа ограничены владельцем);
2. поднимает базу данных и Keycloak, создаёт в Keycloak клиента системы, роли и демонстрационных пользователей;
3. поднимает демонстрационные источники (Moodle, заявки и оплаты, рынок труда, CRM заказчика);
4. собирает образы, запускает backend, антивирус и web;
5. заполняет демонстрационные данные: команды, менеджеров, организации, карточки работы, справочники и первую синхронизацию источников.

Первый запуск занимает от 5 до 15 минут: сборка образов, загрузка сигнатур антивируса, установка демонстрационного Moodle. Повторный запуск безопасен: пароли и данные сохраняются.

Варианты запуска:

```bash
DEMO_LMS=false ./scripts/bootstrap-demo.sh    # без демонстрационного Moodle
DEMO_DATA=false ./scripts/bootstrap-demo.sh   # пустая система с одним администратором
./scripts/reset-demo-data.sh                  # вернуть демонстрационные данные к исходным
```

## Что запускается

Сервисы объединены в профили Compose.

| Профиль | Сервисы | Назначение |
|---|---|---|
| `core` (без метки, запускается всегда) | `web`, `backend`, `postgres`, `keycloak` | обязательная часть: интерфейс и API, база данных, вход |
| `security` | `clamav` | антивирусная проверка вложений и загружаемых файлов |
| `demo` | демонстрационные источники заявок, рынка труда и CRM заказчика, заполнение демонстрационных данных; демонстрационный Moodle — отдельным проектом Compose | демонстрация без настоящих систем |

Без профиля `demo` система пустая. Без профиля `security` проверка файлов не пропускается, а закрывается отказом: вложения остаются в карантине, импорт файлов отклоняется с сообщением «Антивирусная проверка недоступна». Поэтому `security` включён в обе команды запуска.

Профили можно задать переменной `COMPOSE_PROFILES` в `.env.local`, скрипт запуска записывает её сам.

## Адрес и вход

После запуска приложение открывается по адресу `http://rtk.localhost:8081` (браузеры сами направляют имена `*.localhost` на локальный компьютер; работает и `http://localhost:8081`).

| Что | Адрес |
|---|---|
| Приложение | `http://rtk.localhost:8081` |
| Swagger UI (описание API) | `http://rtk.localhost:8081/swagger-ui/index.html` |
| Описание API в OpenAPI | `http://rtk.localhost:8081/openapi.yaml` |
| Страница учётной записи Keycloak | `http://rtk.localhost:8081/idp/realms/rtk-crm/account` |

Как войти: откройте приложение, нажмите «Войти» и введите логин и пароль демонстрационного пользователя. Логины по ролям перечислены в разделе «Роли» файла `README.md`. Пароль демонстрационных учётных записей генерируется при первом запуске и записывается в `.env.local`. Его не публикуют и не передают другим.

При установке без демонстрационных данных создаётся один администратор; его начальный пароль также записывается в `.env.local`, при первом входе система просит задать свой.

## Установка без демонстрационных данных

Для рабочей установки создайте одного администратора и подключите настоящие источники:

```bash
cat >> .env.local <<'EOF'
DEMO_DATA=false
CRM_ADMIN_USERNAME=<логин администратора>
EOF
./scripts/bootstrap-demo.sh
```

Скрипт не поднимает демонстрационные источники, создаёт в Keycloak администратора и его профиль в CRM. Команды, сотрудников и организации администратор затем заводит в интерфейсе или импортом таблиц.

## Основные переменные окружения

Все переменные хранятся в `.env.local`. Образец имён без значений — `.env.example`. Значения секретов не публикуются и не добавляются в git.

| Группа | Переменные | Назначение |
|---|---|---|
| Адрес | `PUBLIC_ORIGIN` | внешний адрес системы без завершающей косой черты; от него зависят вход и ссылки |
| Режим | `DEMO_DATA`, `DEMO_LMS` | демонстрационные данные и демонстрационный Moodle: `true` или `false` |
| База данных | `CRM_DB_*`, `KEYCLOAK_DB_*`, `POSTGRES_SUPERUSER*` | имена баз и учётные записи; пароли генерируются автоматически |
| Вход | `CRM_OIDC_CLIENT_SECRET`, `CRM_ACCOUNT_SYNC_CLIENT_SECRET`, `KEYCLOAK_ADMIN_*` | секреты клиентов и администратор Keycloak; генерируются автоматически |
| Второй фактор | `MFA_REQUIRED_FOR_PRIVILEGED` | `true` — администраторы и операторы зачисления входят с одноразовым кодом из приложения-аутентификатора; в демонстрационном режиме выключен |
| Источники | `SITE_*`, `MOODLE_*`, `LABOR_MARKET_*`, `CRM_BASE_URL`, `CRM_TOKEN` | адреса и токены внешних систем, см. ниже |
| Расписание | `SOURCES_SYNC_CRON` | расписание плановой синхронизации источников (часовой пояс Москвы), `-` отключает |
| Модули | `MODULE_ENROLMENT_ENABLED`, `MODULE_PARTNER_ENABLED` | включение модулей, см. ниже |
| Сроки хранения | `RETENTION_*` | как долго хранятся файлы отчётов, неактивные контакты, журнал и анкеты слушателей |
| Публикация | `SESSION_COOKIE_SECURE`, `TRUSTED_PROXY_CIDR`, `TLS_CERTIFICATE_FILE`, `TLS_CERTIFICATE_KEY_FILE`, `COMPOSE_FILE` | включение TLS и работа за обратным прокси |
| Копии | `BACKUP_ENCRYPTION_KEY_FILE` | где хранится ключ шифрования резервных копий; без этой переменной ключ создаётся в `.env.local` |

Ключи шифрования данных слушателей и токенов источников генерируются скриптом запуска. Их нужно хранить отдельно от резервных копий базы: потеря ключа означает потерю зашифрованных данных.

## Модули

Два модуля включены по умолчанию и выключаются флагами:

| Модуль | Переменная | Что включает |
|---|---|---|
| «Слушатели» | `MODULE_ENROLMENT_ENABLED` | раздел «Зачисление»: оплаты, анкеты слушателей, файл для загрузки в LMS, право «Оператор зачисления» |
| Кабинет вуза | `MODULE_PARTNER_ENABLED` | вход представителя вуза и материалы его вуза |

Чтобы выключить модуль, поставьте в `.env.local` значение `false` и запустите `./scripts/bootstrap-demo.sh` ещё раз.

## Подключение настоящих систем

Демонстрационные источники заменяются настоящими настройкой адресов и токенов, код менять не нужно. Значения задаются в `.env.local` либо администратором на экране «Источники данных» без перезапуска; значения с экрана заменяют значения из `.env.local`. Если адрес указывает на настоящую систему, соответствующий демонстрационный сервис не запускается.

| Система | Что задать | Что требуется от стороны заказчика |
|---|---|---|
| Keycloak или другой OIDC-вход (SSO) | `APP_OIDC_ISSUER_URI`, `APP_OIDC_PUBLIC_BASE_URL`, `APP_OIDC_INTERNAL_BASE_URL`, `APP_OIDC_CLIENT_SECRET` | поддержка OpenID Connect discovery и конфиденциальный клиент с адресом возврата `PUBLIC_ORIGIN/api/auth/callback/keycloak`; роли `crm-user`, `crm-leader`, `crm-admin`, `crm-management`, `crm-partner` у пользователей |
| Moodle | `MOODLE_BASE_URL`, `MOODLE_TOKEN`, `MOODLE_COURSE_IDS` | в Moodle включены веб-службы и протокол REST, создан отдельный пользователь с ролью только на чтение и внешний сервис с четырьмя функциями чтения; токен этого пользователя |
| Сайт: заявки и оплаты | `SITE_BASE_URL`, `SITE_TOKEN` | выдача заявок и оплат в предложенном формате, токен на чтение |
| Рынок труда | `LABOR_MARKET_BASE_URL`, `LABOR_MARKET_TOKEN` | источник месячных срезов вакансий по ИТ-направлениям, токен на чтение |
| CRM заказчика | `CRM_BASE_URL`, `CRM_TOKEN` | выдача организаций и контактов и приём событий работы с вузом, токен |

Адреса настоящих систем задаются по HTTPS. Токены не попадают в журнал и ответы API и хранятся зашифрованными. После настройки администратор нажимает «Проверить связь» и «Запустить синхронизацию» на экране «Источники данных» (см. [инструкции пользователей](Инструкции_пользователей.md), раздел для администратора).

## Публикация на сервере

Для доступа по HTTPS добавьте в `.env.local` внешний адрес, сертификат и включите публикационный вариант Compose:

```bash
cat >> .env.local <<'EOF'
PUBLIC_ORIGIN=https://crm.example.ru
TLS_CERTIFICATE_FILE=<путь к сертификату с цепочкой>
TLS_CERTIFICATE_KEY_FILE=<путь к закрытому ключу>
COMPOSE_FILE=compose.yaml:compose.prod.yaml
EOF
./scripts/bootstrap-demo.sh
```

В этом варианте web принимает HTTP и HTTPS, Keycloak работает в рабочем режиме, cookie сессии помечается как защищённая, консоль администратора Keycloak снаружи недоступна. Если HTTPS завершает отдельный прокси, используйте `compose.yaml` с `PUBLIC_ORIGIN=https://...`, `SESSION_COOKIE_SECURE=true` и адресом прокси в `TRUSTED_PROXY_CIDR`; для общего прокси нескольких проектов служит `compose.edge.yaml`.

## Резервное копирование и восстановление

```bash
./scripts/backup.sh <каталог копии>
./scripts/restore.sh <каталог копии>
```

Копия создаётся на работающей системе и включает базы CRM и Keycloak, вложения и готовые файлы отчётов. Каждый файл шифруется, при создании записываются контрольные суммы. Копию хранят вне сервера с ограниченным доступом, потому что в ней есть персональные данные. Файл `.env.local` в копию не входит и хранится отдельно: для восстановления нужен тот же `.env.local` и тот же `PUBLIC_ORIGIN`.

Восстановление заменяет текущие данные, проверяет контрольные суммы и ключ до любых изменений и поднимает сервисы снова. Скрипт `scripts/backup-scheduled.sh` позволяет делать копии по расписанию через cron или таймер systemd. Демонстрационный Moodle в копию не входит: его данные воспроизводит скрипт запуска.

## Проверка работоспособности

```bash
docker compose --env-file .env.local ps
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8081/healthz
curl -s -w '\n%{http_code}\n' http://localhost:8081/api/me
```

- все сервисы в состоянии `healthy`;
- `/healthz` отвечает кодом 200 (отвечает веб-сервер, без обращения к backend);
- `/api/me` без входа отвечает ответом с кодом 401 в формате JSON;
- Swagger UI открывается по адресу из таблицы выше;
- вход проходит и открывает раздел вашей роли.

Если backend не стартует, причина указана в его журнале: `docker compose --env-file .env.local logs backend`.

## Остановка, обновление, сброс

Остановка и удаление контейнеров (тома с данными сохраняются):

```bash
docker compose --env-file .env.local --profile '*' stop
docker compose --env-file .env.local --profile '*' down
```

Команда `down -v` удаляет и тома, то есть все данные. Демонстрационный Moodle — отдельный проект Compose, эти команды его не затрагивают.

Обновление:

1. Сделайте резервную копию.
2. Получите новую версию кода: `git pull`.
3. Запустите `./scripts/bootstrap-demo.sh` ещё раз: образы пересоберутся, схема базы данных обновится при старте backend, данные и пароли сохранятся.

Сброс демонстрационных данных к исходным — `./scripts/reset-demo-data.sh`; работает только на демонстрационном стенде и удаляет все изменения в данных CRM.

## Сборка и тесты без Docker

Backend: JDK 21, `cd backend && ./mvnw test`. Frontend: Node.js 24 и npm, `cd frontend && npm ci && npm run build`. Для запуска jar-файла нужны PostgreSQL, Keycloak и ClamAV с параметрами подключения из `compose.yaml`. Полная проверка перед сборкой — `bash scripts/release-gate.sh`.
