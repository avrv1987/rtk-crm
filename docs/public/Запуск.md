# Запуск CRM ИТ Школы РТК

Документ описывает, как поднять систему на своём компьютере или сервере, что при этом запускается, как войти, как подключить настоящие системы вместо демонстрационных, как делать резервные копии и обновлять систему. Устройство системы — в [описании архитектуры](Архитектура.md), работа по ролям — в [инструкциях пользователей](Инструкции_пользователей.md).

## Требования

- Linux x86_64 (например Ubuntu 22.04 или новее) или Windows с Docker Desktop (WSL2).
- Docker Engine и Docker Compose v2 не ниже 2.24.
- `bash` 4 и новее (в Windows без bash — PowerShell 7 и новее). Стандартный bash в macOS слишком старый. `openssl` нужен для резервных копий; запуск обходится без него — секреты тогда создаются из `/dev/urandom`.
- Память: 4 ГБ для демонстрации, от 6 ГБ при нагрузке с десятками пользователей и одновременными отчётами. Замер нагрузки на версии 2.3 (50 одновременных сессий, серия из 12 отчётов) пройден на общем сервере с 4 ядрами и 8 ГБ памяти, где работали и другие сервисы. Антивирусу нужно около 2 ГБ. Для ежемесячной проверки восстановления нужно ещё около 3 ГБ свободной памяти; порог задаёт переменная `RESTORE_CHECK_MIN_MEMORY_MB` при запуске скрипта.
- Доступ в интернет при первой сборке: образы Docker, зависимости Java и JavaScript, сигнатуры антивируса.

## Получение кода

```bash
git clone https://github.com/avrv1987/rtk-crm.git
cd rtk-crm
```

## Запуск демонстрационного стенда

Одна команда:

```bash
./scripts/bootstrap-demo.sh
```

В Windows без bash:

```powershell
pwsh -NoProfile -File ./scripts/bootstrap-demo.ps1
```

Скрипт:

1. создаёт файл `.env.local` со случайными паролями и ключами (он не попадает в git, права доступа ограничены владельцем);
2. поднимает базу данных и Keycloak, создаёт в Keycloak клиента системы, роли и демонстрационных пользователей;
3. поднимает демонстрационные источники (Moodle, заявки и оплаты, рынок труда, CRM заказчика);
4. собирает образы, запускает backend, антивирус и web;
5. заполняет демонстрационные данные: команды, менеджеров, организации, карточки работы, справочники и первую синхронизацию источников.

Первый запуск занимает от 5 до 15 минут: сборка образов, загрузка сигнатур антивируса, установка демонстрационного Moodle. Повторный запуск безопасен: пароли и данные сохраняются.

Варианты запуска:

```bash
DEMO_LMS=false ./scripts/bootstrap-demo.sh    # без демонстрационного Moodle
DEMO_DATA=false ./scripts/bootstrap-demo.sh   # пустая система с одним администратором
./scripts/reset-demo-data.sh                  # вернуть демонстрационные данные к исходным
```

## Что запускается

Сервисы объединены в профили Compose.

| Профиль | Сервисы | Назначение |
|---|---|---|
| `core` (без метки, запускается всегда) | `web`, `backend`, `postgres`, `keycloak` | обязательная часть: интерфейс и API, база данных, вход |
| `security` | `clamav` | антивирусная проверка вложений и загружаемых файлов |
| `demo` | демонстрационные источники заявок, рынка труда и CRM заказчика, заполнение демонстрационных данных; демонстрационный Moodle — отдельным проектом Compose | демонстрация без настоящих систем |

Без профиля `demo` система пустая. Без профиля `security` проверка файлов не пропускается, а закрывается отказом: вложения остаются в карантине, импорт файлов отклоняется с сообщением «Антивирусная проверка недоступна». Поэтому `security` включён в обе команды запуска.

Профили можно задать переменной `COMPOSE_PROFILES` в `.env.local`, скрипт запуска записывает её сам.

## Адрес и вход

После запуска приложение открывается по адресу `http://rtk.localhost:8081` (браузеры сами направляют имена `*.localhost` на локальный компьютер; работает и `http://localhost:8081`).

| Что | Адрес |
|---|---|
| Приложение | `http://rtk.localhost:8081` |
| Swagger UI (описание API) | `http://rtk.localhost:8081/swagger-ui/index.html` |
| Описание API в OpenAPI | `http://rtk.localhost:8081/openapi.yaml` |
| Страница учётной записи Keycloak | `http://rtk.localhost:8081/idp/realms/rtk-crm/account` |

Как войти: откройте приложение, нажмите «Войти» и введите логин и пароль демонстрационного пользователя. Логины демонстрационных пользователей: КАМ — `kam-a`, `kam-b`, `kam-c`, `kam-d`; руководитель — `leader`, `leader-b`; «Руководство» — `management`; администратор — `admin`; менеджер учебного процесса — `enrol`; координатор вуза — `partner`. Пароль демонстрационных учётных записей генерируется при первом запуске и записывается в `.env.local`. Его не публикуют и не передают другим.

При установке без демонстрационных данных создаётся один администратор; его начальный пароль также записывается в `.env.local`, при первом входе система просит задать свой.

## Установка без демонстрационных данных

Для рабочей установки создайте одного администратора и подключите настоящие источники:

```bash
cat >> .env.local <<'EOF'
DEMO_DATA=false
CRM_ADMIN_USERNAME=<логин администратора>
EOF
./scripts/bootstrap-demo.sh
```

Скрипт не поднимает демонстрационные источники, создаёт в Keycloak администратора и его профиль в CRM. Команды, сотрудников и организации администратор затем заводит в интерфейсе или импортом таблиц.

## Основные переменные окружения

Все переменные хранятся в `.env.local`. Образец имён без значений — `.env.example`. Значения секретов не публикуются и не добавляются в git.

| Группа | Переменные | Назначение |
|---|---|---|
| Адрес | `PUBLIC_ORIGIN` | внешний адрес системы без завершающей косой черты; от него зависят вход и ссылки |
| Режим | `DEMO_DATA`, `DEMO_LMS` | демонстрационные данные и демонстрационный Moodle: `true` или `false` |
| База данных | `CRM_DB_*`, `KEYCLOAK_DB_*`, `POSTGRES_SUPERUSER*` | имена баз и учётные записи; пароли генерируются автоматически |
| Вход | `CRM_OIDC_CLIENT_SECRET`, `CRM_ACCOUNT_SYNC_CLIENT_SECRET`, `KEYCLOAK_ADMIN_*` | секреты клиентов и администратор Keycloak; генерируются автоматически |
| Второй фактор | `MFA_REQUIRED_FOR_PRIVILEGED` | `true` — администраторы и менеджеры учебного процесса входят с одноразовым кодом из приложения-аутентификатора; в демонстрационном режиме выключен |
| Источники | `SITE_*`, `MOODLE_*`, `LABOR_MARKET_*`, `CRM_BASE_URL`, `CRM_TOKEN` | адреса и токены внешних систем, см. ниже |
| Расписание | `SOURCES_SYNC_CRON` | расписание плановой синхронизации источников (часовой пояс Москвы), `-` отключает |
| Модули | `MODULE_ENROLMENT_ENABLED`, `MODULE_PARTNER_ENABLED`, `MAX_ENABLED`, `MAIL_ENABLED` | включение модулей, см. ниже |
| ИИ-агенты | `MCP_ENABLED`, `MCP_REDIRECT_URIS`, `MCP_ALLOWED_ORIGINS`, `MCP_CALLS_PER_MINUTE` | сервер MCP, по умолчанию выключен, см. ниже |
| Слушатели | `ENROLMENT_LMS_LOGIN` | логин в LMS: `EMAIL` — почта целиком в нижнем регистре (по умолчанию), `EMAIL_LOCAL_PART` — часть почты до «@»; одно правило для передачи через API и для файлов Moodle |
| Почта | `MAIL_ENABLED`, `MAIL_PUBLIC_BASE_URL` | модуль почты, по умолчанию выключен; адрес для ссылок в письмах, по умолчанию `PUBLIC_ORIGIN` |
| Сроки хранения | `RETENTION_*`, `SOURCES_STALE_AFTER` | значения по умолчанию для сроков хранения файлов отчётов, неактивных контактов, журнала и анкет слушателей и для порога устаревания источников. Администратор меняет сроки, пороги сигналов, срок ответа на обращения субъектов ПДн и учёт согласий в «Администрирование → Настройки»: правка действует без перезапуска, пишется в журнал и заменяет значение из `.env.local` |
| Публикация | `SESSION_COOKIE_SECURE`, `TRUSTED_PROXY_CIDR`, `TLS_CERTIFICATE_FILE`, `TLS_CERTIFICATE_KEY_FILE`, `COMPOSE_FILE` | включение TLS и работа за обратным прокси |
| Копии | `BACKUP_ENCRYPTION_KEY_FILE`, `BACKUP_KEEP`, `BACKUP_OFFSITE_DIR`, `BACKUP_OFFSITE_COMMAND` | файл ключа шифрования копий (без него ключ создаётся в `.env.local`); число хранимых копий, по умолчанию 7; каталог или команда для копии вне сервера, по умолчанию пусто |

Ключи шифрования данных слушателей и токенов источников генерируются скриптом запуска. Их нужно хранить отдельно от резервных копий базы: потеря ключа означает потерю зашифрованных данных.

## Модули

Два модуля включены по умолчанию и выключаются флагами:

| Модуль | Переменная | Что включает |
|---|---|---|
| «Слушатели» | `MODULE_ENROLMENT_ENABLED` | раздел «Зачисление»: оплаты, анкеты слушателей, файл для загрузки в LMS, право «Менеджер учебного процесса» |
| Кабинет вуза | `MODULE_PARTNER_ENABLED` | вход представителя вуза и материалы его вуза |

Чтобы выключить модуль, поставьте в `.env.local` значение `false` и запустите `./scripts/bootstrap-demo.sh` ещё раз.

Включён ли модуль и как он работает, администратор видит в «Администрирование → Интеграции → Состояние модулей».

Модуль MAX (уведомления в мессенджере MAX и мини-приложение) по умолчанию выключен. Как включить:

1. Зарегистрируйте бота на платформе MAX для партнёров и включите в нём мини-приложение с адресом `PUBLIC_ORIGIN/max/`.
2. Корневой сертификат Минцифры уже лежит в `infra/max/russian_trusted_root_ca.crt` (Russian Trusted Root CA, действует до 2032 года): клиент MAX доверяет ему отдельно, общий набор сертификатов не меняется. При выпуске нового корня положите его файл `.crt` или `.cer` в тот же каталог.
3. В `.env.local` задайте `MAX_ENABLED=true`; адрес системы `PUBLIC_ORIGIN` должен начинаться с `https://`. Запустите `./scripts/bootstrap-demo.sh` ещё раз.
4. Токен бота: задайте `MAX_BOT_TOKEN` в `.env.local` — при запуске система сохранит его в зашифрованном виде, узнает имя бота и подпишет вебхук сама. Либо администратор: «Администрирование» → «Источники данных» → «Бот MAX» → вставьте токен бота → «Проверить связь» → «Подписать вебхук». Переменная не заменяет токен, уже сохранённый в системе. Если мини-приложение подключено к боту, отметьте это в карточке «Бот MAX».
5. Сотрудники подключают MAX сами: меню профиля → «Подключить MAX».

Подробности о настройке — в справке системы, раздел «MAX».

Модуль почты (уведомления на почту, приглашения со ссылкой вместо пароля на экране, сведения субъекту ПДн) по умолчанию выключен. Как включить:

1. В `.env.local` задайте `MAIL_ENABLED=true`; ссылки в письмах строятся от `PUBLIC_ORIGIN` (или отдельно `MAIL_PUBLIC_BASE_URL`). Запустите `./scripts/bootstrap-demo.sh` ещё раз.
2. Сразу после включения работает режим «Без отправки»: письма собираются целиком и сохраняются в журнал отправки, наружу ничего не уходит.
3. Чтобы письма уходили, администратор: «Администрирование» → «Почта» → режим «SMTP-сервер», сервер, порт, шифрование, логин и пароль почтового сервиса, адрес отправителя → «Сохранить» → «Проверить подключение» → «Отправить тестовое письмо себе». Пароль шифруется ключом `SOURCES_SETTINGS_KEY`.
4. Адрес сотрудника — почта его учётной записи в Keycloak.

## MCP для ИИ-агентов

Сервер MCP выключен по умолчанию. Он даёт MCP-клиенту инструменты на чтение от имени вошедшего сотрудника: КАМ — 8, руководителю команды — 15, «Руководству» — 14, включая аналитику на тех же расчётах, что экраны. КАМ и руководитель с дополнительным scope `crm-mcp.write` получают ещё семь инструментов: агент готовит план — итог встречи и следующий шаг, переход этапа, проблему или риск, решение проблемы, паузу или возобновление, — а записывает сотрудник на экране CRM по ссылке из ответа агента.

**Включение.**
1. В `.env.local` поставьте `MCP_ENABLED=true`.
2. В `MCP_REDIRECT_URIS` через запятую перечислите адреса возврата клиентов, которые будут подключаться. По умолчанию там адрес скрипта проверки `http://127.0.0.1:8976/callback` и MCP Inspector `http://localhost:6274/oauth/callback`.
3. Запустите `./scripts/bootstrap-demo.sh` (Windows: `scripts\bootstrap-demo.ps1`) ещё раз. Скрипт пересоберёт и перезапустит backend.

Скрипт идемпотентно настраивает в существующем realm Keycloak, не пересоздавая его:
- клиентский scope `crm-mcp` с маппером Audience: в токене доступа появляется назначение `crm-mcp` и роли CRM;
- необязательный scope `crm-mcp.write`: подготовка планов записи; клиент получает его, только если явно запросит;
- публичный клиент `crm-mcp-client`: вход по коду авторизации с PKCE, экран согласия, токен доступа на 5 минут, без `offline_access`.

Динамической регистрации клиентов нет. Новый клиент — это новый адрес возврата в `MCP_REDIRECT_URIS` и повторный запуск скрипта. При `MCP_ENABLED=false` клиент отключается.

**Адрес сервера:** `PUBLIC_ORIGIN/mcp`. Описание ресурса для клиентов: `PUBLIC_ORIGIN/.well-known/oauth-protected-resource/mcp`.

**Дополнительные настройки:**
- `MCP_ALLOWED_ORIGINS` — разрешённые значения заголовка `Origin` для браузерных клиентов; по умолчанию только `PUBLIC_ORIGIN`;
- `MCP_CALLS_PER_MINUTE` — лимит вызовов на сотрудника, по умолчанию 60.

**Подключение клиентов.** Во всех клиентах: адрес `PUBLIC_ORIGIN/mcp`, транспорт Streamable HTTP (HTTP), идентификатор клиента `crm-mcp-client`, без секрета, scope `crm-mcp`. Для записи через план — scope `crm-mcp crm-mcp.write`.
- **MCP Inspector:** `npx @modelcontextprotocol/inspector` (Node.js 22.19+). Transport Type — Streamable HTTP, URL — адрес сервера. В настройках OAuth укажите Client ID `crm-mcp-client` и scope `crm-mcp`, затем Open Auth Settings → Quick OAuth Flow. Для прямого подключения из браузера добавьте `http://localhost:6274` в `MCP_ALLOWED_ORIGINS`.
- **Другие MCP-клиенты** (локальные и облачные): укажите адрес сервера и идентификатор клиента, адрес возврата клиента добавьте в `MCP_REDIRECT_URIS`. Облачный клиент подключается из сети своего поставщика, поэтому `/mcp` должен быть доступен из интернета. Если модель работает за рубежом, передача ей ПДн — трансграничная, решение принимает оператор ПДн. Для демонстрации используйте стенд с демонстрационными данными.

**Проверка на стенде:** `CRM_URL=PUBLIC_ORIGIN node scripts/mcp-smoke.mjs`. Скрипт получает 401 и описание ресурса, печатает ссылку входа в Keycloak, после входа запрашивает описание сервера, список инструментов и вызывает два инструмента, проверяет отказ на чужой `Origin`. Токен не печатается.

Запись через план: `CRM_URL=PUBLIC_ORIGIN MCP_PLAN_INTERACTION_ID=<id взаимодействия КАМ> node scripts/mcp-smoke.mjs`. Скрипт запросит scope записи, подготовит план и напечатает ссылку на экран подтверждения. Откройте её в CRM под тем же сотрудником и нажмите «Записать» или «Отклонить»; скрипт дождётся итога.

## Подключение настоящих систем

Демонстрационные источники заменяются настоящими настройкой адресов и токенов, код менять не нужно. Значения задаются в `.env.local` либо администратором на экране «Источники данных» без перезапуска; значения с экрана заменяют значения из `.env.local`. Если адрес указывает на настоящую систему, соответствующий демонстрационный сервис не запускается.

| Система | Что задать | Что требуется от стороны заказчика |
|---|---|---|
| Keycloak или другой OIDC-вход (SSO) | `APP_OIDC_ISSUER_URI`, `APP_OIDC_PUBLIC_BASE_URL`, `APP_OIDC_INTERNAL_BASE_URL`, `APP_OIDC_CLIENT_SECRET` | поддержка OpenID Connect discovery и конфиденциальный клиент с адресом возврата `PUBLIC_ORIGIN/api/auth/callback/keycloak`; роли `crm-user`, `crm-leader`, `crm-admin`, `crm-management`, `crm-partner` у пользователей |
| Moodle | `MOODLE_BASE_URL`, `MOODLE_TOKEN`, `MOODLE_COURSE_IDS`; для передачи слушателей — `MOODLE_WRITE_ENABLED=true`, `MOODLE_WRITE_TOKEN`, `MOODLE_STUDENT_ROLE_ID` | в Moodle включены веб-службы и протокол REST; для чтения — отдельный пользователь с ролью только на чтение и внешний сервис с функциями `core_course_get_courses_by_field`, `core_enrol_get_enrolled_users`, `core_group_get_course_groups`, `core_completion_get_course_completion_status`; для передачи слушателей — ещё один пользователь с ролью записи (`moodle/user:create`, `enrol/manual:enrol`, `enrol/manual:unenrol`, `moodle/role:assign` с разрешением назначать роль студента, `moodle/course:managegroups`, `moodle/site:viewuseridentity`), ограниченный сервис с функциями `core_user_get_users_by_field`, `core_user_create_users`, `enrol_manual_enrol_users`, `enrol_manual_unenrol_users`, `core_group_add_group_members`, `core_group_delete_group_members`, `core_group_get_group_members`, `core_enrol_get_enrolled_users` и свой токен |
| Сайт: заявки и оплаты | `SITE_BASE_URL`, `SITE_TOKEN` | выдача заявок и оплат в предложенном формате, токен на чтение |
| Рынок труда | `LABOR_MARKET_BASE_URL`, `LABOR_MARKET_TOKEN` | источник месячных срезов вакансий по ИТ-направлениям, токен на чтение |
| CRM заказчика | `CRM_BASE_URL`, `CRM_TOKEN` | выдача организаций и контактов и приём событий работы с вузом, токен |

Адреса настоящих систем задаются по HTTPS. Токены не попадают в журнал и ответы API и хранятся зашифрованными. После настройки администратор нажимает «Проверить связь» и «Запустить синхронизацию» на экране «Источники данных» (см. [инструкции пользователей](Инструкции_пользователей.md), раздел для администратора).

## Публикация на сервере

Для доступа по HTTPS добавьте в `.env.local` внешний адрес, сертификат и включите публикационный вариант Compose:

```bash
cat >> .env.local <<'EOF'
PUBLIC_ORIGIN=https://crm.example.ru
TLS_CERTIFICATE_FILE=<путь к сертификату с цепочкой>
TLS_CERTIFICATE_KEY_FILE=<путь к закрытому ключу>
COMPOSE_FILE=compose.yaml:compose.prod.yaml
EOF
./scripts/bootstrap-demo.sh
```

В этом варианте web принимает HTTP и HTTPS, Keycloak работает в рабочем режиме, cookie сессии помечается как защищённая, консоль администратора Keycloak снаружи недоступна. Если HTTPS завершает отдельный прокси, используйте `compose.yaml` с `PUBLIC_ORIGIN=https://...`, `SESSION_COOKIE_SECURE=true` и адресом прокси в `TRUSTED_PROXY_CIDR`; для общего прокси нескольких проектов служит `compose.edge.yaml`.

## Резервное копирование и восстановление

```bash
./scripts/backup.sh <каталог копии>
./scripts/restore.sh <каталог копии>
```

Копия включает базы CRM и Keycloak, вложения и готовые файлы отчётов. Чтобы база и файлы совпадали, на время копии backend останавливается и затем запускается снова: интерфейс в это время не работает, обычно около минуты. Каждый файл шифруется. К копии прилагается манифест: версия, коммит, последняя миграция, время, число записей ключевых таблиц и файлов, контрольные суммы. После записи копия проверяется: файлы расшифровываются целиком, число файлов в архивах сверяется с томами. Копию хранят вне сервера с ограниченным доступом, потому что в ней есть персональные данные. Файл `.env.local` в копию не входит и хранится отдельно: для восстановления нужен тот же `.env.local` и тот же `PUBLIC_ORIGIN`.

Восстановление заменяет текущие данные, проверяет контрольные суммы и ключ до любых изменений и поднимает сервисы снова. Скрипт `scripts/backup-scheduled.sh` делает копии по расписанию через cron или таймер systemd. Число хранимых копий задаёт `BACKUP_KEEP` (по умолчанию 7), дополнительное место вне сервера — `BACKUP_OFFSITE_DIR` (каталог) или `BACKUP_OFFSITE_COMMAND` (команда, получает путь копии); по умолчанию они пусты. Демонстрационный Moodle в копию не входит: его данные воспроизводит скрипт запуска.

Пример для cron пользователя, от которого запущен Docker:

```
0 2 * * * cd /opt/rtk-crm && ./scripts/backup-scheduled.sh /var/backups/rtk-crm
0 4 1 * * cd /opt/rtk-crm && ./scripts/restore-check.sh /var/backups/rtk-crm
```

Без расписания «Обзор» предупреждает, если копии нет больше суток или проверки — больше 35 дней.

Проверка восстановления раз в месяц:

```bash
./scripts/restore-check.sh <каталог копий>
```

Скрипт восстанавливает последнюю копию в отдельный временный проект Compose без открытых портов, не трогая рабочую систему, и проверяет число записей по манифесту, каждое вложение по контрольной сумме, файлы отчётов, расшифровку анкет ключами из `.env.local` и вход в восстановленный Keycloak. Время восстановления и итог пишутся в журнал копий, временный проект удаляется. Проверке нужно около 3 ГБ свободной памяти. На «Обзоре» администратора видны дата и размер последней копии, дата последней проверки и предупреждение, если копии нет больше суток или проверки — больше 35 дней.

## Проверка работоспособности

```bash
docker compose --env-file .env.local ps
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8081/healthz
curl -s -w '\n%{http_code}\n' http://localhost:8081/api/me
```

- все сервисы в состоянии `healthy`;
- `/healthz` отвечает кодом 200 (отвечает веб-сервер, без обращения к backend);
- готовность backend и его базы показывает `actuator/health`: у сервиса `backend` в выводе `ps` состояние `healthy`, вручную — `docker compose --env-file .env.local exec backend curl -fsS http://localhost:8080/actuator/health` отвечает JSON со статусом `UP`;
- `/api/me` без входа отвечает ответом с кодом 401 в формате JSON;
- Swagger UI открывается по адресу из таблицы выше;
- вход проходит и открывает раздел вашей роли.

Если backend не стартует, причина указана в его журнале: `docker compose --env-file .env.local logs backend`.

## Ограничения установки

Поддерживается один экземпляр backend. Ограничение частоты запросов, счётчики MCP и очередь отчётов хранятся в памяти процесса: при запуске backend незаконченные задания отчётов помечаются прерванными. Несколько копий backend за балансировщиком считали бы ограничения раздельно и прерывали бы чужие задания.

Согласованная резервная копия останавливает backend на время копии, поэтому копию ставят на ночь. Хранилище вне сервера пока не выбрано: настройки места для дополнительной копии по умолчанию пусты, и без них копии лежат на том же сервере. Скрипты копии и проверки восстановления проверены автотестом на имитации Docker; первый живой прогон на сервере выполняет администратор.

## Остановка, обновление, сброс

Остановка и удаление контейнеров (тома с данными сохраняются):

```bash
docker compose --env-file .env.local --profile '*' stop
docker compose --env-file .env.local --profile '*' down
```

Команда `down -v` удаляет и тома, то есть все данные. Демонстрационный Moodle — отдельный проект Compose, эти команды его не затрагивают.

Обновление:

1. Сделайте резервную копию.
2. Получите новую версию кода: `git pull`.
3. Запустите `./scripts/bootstrap-demo.sh` ещё раз: образы пересоберутся, схема базы данных обновится при старте backend, данные и пароли сохранятся.
4. Если включена передача слушателей в Moodle (`MOODLE_WRITE_ENABLED=true`), с версии 2.5.3 добавьте во внешний сервис записи Moodle функции `core_group_delete_group_members` и `core_group_get_group_members`: без них перенос слушателя между группами одного курса завершится ошибкой. Отдельных прав роли не нужно, используется `moodle/course:managegroups`. Демонстрационный Moodle скрипт запуска дополняет сам.

Сброс демонстрационных данных к исходным — `./scripts/reset-demo-data.sh`; работает только на демонстрационном стенде и удаляет все изменения в данных CRM.

## Сборка и тесты без Docker

Backend: JDK 21, `cd backend && ./mvnw test`. Frontend: Node.js 24 и npm, `cd frontend && npm ci && npm run build`. Для запуска jar-файла нужны PostgreSQL, Keycloak и ClamAV с параметрами подключения из `compose.yaml`. Полная проверка перед сборкой — `bash scripts/release-gate.sh`.
