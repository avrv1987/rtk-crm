# Импорт каталогов из XLS/XLSX

Описание методов обработки данных при загрузке каталогов (ТЗ §4 п.1, §6.7; требование FR-07).

## Доступ

Импорт доступен только активному профилю CRM с ролью ADMIN: проверка выполняется сервером на каждом шаге (inspect, preview, чтение протокола, apply). Файл не создаёт профили КАМ, роли, учётные записи Keycloak и права; менеджер из файла должен уже существовать в CRM.

## Порядок работы

1. «Проверить файл» (`POST /api/imports/inspect`): сигнатура XLS/XLSX, размер до 5 МиБ, антивирус ClamAV, список листов и заголовков. Файл не сохраняется.
2. Сопоставление столбцов. Для профиля «Каталог по ТЗ (10 полей)» интерфейс сам сопоставляет заголовки ТЗ и их синонимы (регистр, лишние пробелы, «ё» и завершающие `:`/`*` не важны). Администратор может изменить выбор.
3. «Создать предпросмотр» (`POST /api/imports/preview`): файл читается повторно, по каждой строке строится план и протокол «было/станет». В БД сохраняется только план; каталоги не меняются.
4. Выбор строк и «Применить» (`POST /api/imports/{id}/apply` с `version` и `Idempotency-Key`). Применяются только строки «Создать», «Обновить», «Без изменений». Все выбранные строки сохраняются в одной транзакции; перед записью сервер сверяет версии записей с предпросмотром. Если данные изменились, ответ 409, ничего не записано, нужен новый предпросмотр. Повтор с тем же ключом возвращает прежний результат.

Шаблон файла: кнопка «Скачать шаблон файла» (`/catalog-import-template.xlsx`) — лист «Каталог», 10 столбцов ТЗ и 3 строки синтетических примеров. Перед загрузкой в примере нужно заменить ФИО менеджеров на ФИО реальных профилей КАМ.

## Формат файла

| Правило | Значение |
|---|---|
| Форматы | XLS (BIFF8) и XLSX; книга с паролем отклоняется |
| Размер | до 5 МиБ; распакованная часть XLSX до 12 МиБ на элемент архива, до 64 МиБ суммарно и не больше 200 частей архива — проверяется до открытия книги POI |
| Лист | выбирается администратором; не предлагаются листы без заполненных ячеек и листы с непригодной строкой заголовков (повтор заголовка, ошибка Excel или формула без значения в заголовке, больше 50 столбцов) — такой лист не мешает выбрать другой; если подходящих листов нет, показывается ошибка первого непригодного листа |
| Строка заголовков | первая строка листа, где есть хотя бы одна непустая ячейка; строки выше неё пропускаются |
| Заголовки | непустые и уникальные на листе; до 50 столбцов с заголовком; столбцы без заголовка и оформленные пустые ячейки справа игнорируются |
| Строки данных | до 5000 непустых строк; строки только с оформлением не считаются |
| Ячейка | до 4000 символов; пробелы по краям и повторные пробелы убираются |
| Формула | берётся значение, сохранённое Excel; формула без сохранённого значения — ошибка этой ячейки («откройте и сохраните файл в Excel»); формулы не вычисляются сервером |
| Дата | ячейка с форматом даты читается как `ГГГГ-ММ-ДД` |
| Число | по формату ячейки (`2027`, `00123` в текстовой ячейке сохраняет нули) |

Ошибки уровня файла называют лист и строку (например, «Лист «Каталог», строка 3: заголовок «ПО» повторяется»). Ошибки уровня ячейки попадают в протокол строки и делают строку «Ошибка», не останавливая остальные строки. Ошибка в несопоставленном столбце строку не блокирует.

## Десять полей ТЗ

| Поле ТЗ | Поле сопоставления | Куда записывается | Правило |
|---|---|---|---|
| Название ВУЗа | `organizationName`, обязательно | Organization.name | сопоставление с вузом CRM — см. ниже |
| Вендор | `vendorName`, обязательно | Vendor.name | каталог вендоров |
| ПО | `productName`, обязательно | Product.name внутри вендора | каталог ПО |
| Номер договора | `contractNumber` | ProductAgreement.contractNumber | строка как есть |
| Подписание лицензии | `licenseSigned` | ProductAgreement.licenseSigned | «да/нет», `true/false`, `1/0`, «подписана/не подписана»; дата (`ГГГГ-ММ-ДД` или `ДД.ММ.ГГГГ`) означает «да» — отдельного поля даты в модели нет, дата не сохраняется; пустое значение = «не указано», а не «нет» |
| Срок действия лицензии (год) | `licenseExpiryYear` | ProductAgreement.licenseExpiryYear | год 1900–3000 или дата, из которой берётся год |
| Статус по передаче | `transferStatus` | ProductAgreement.transferStatus | см. «Статус по передаче» |
| ФИО Менеджера | `managerName` | Organization.ownerManagerId | см. «Менеджер» |
| Ответственные от ВУЗа | `contactName` | Contact вуза | вся ячейка — один контакт, ФИО не делится |
| Комментарий | `comment` | событие COMMENTED взаимодействия | см. «Комментарий» |

Дополнительные необязательные поля (раздел «Дополнительно»): `organizationType` («вуз»/«школа», `UNIVERSITY`/`SCHOOL`), ключи `organizationExternalKey`, `vendorExternalKey`, `productExternalKey`, `agreementExternalKey`, `contactExternalKey`, реквизиты контакта `contactPosition`, `contactEmail`, `contactPhone`, `interactionId`.

Несопоставленное поле не меняет данные CRM: например, без столбца «Статус по передаче» статус существующего договора сохраняется. Пустая ячейка в сопоставленном столбце договора очищает значение (файл считается источником этого поля).

## Сопоставление с записями CRM

Нормализация названий: пробелы (включая неразрывные) схлопываются, края обрезаются, регистр не важен, «ё» = «е».

Порядок поиска записи для вуза, вендора, ПО, контакта и договора:

1. явный UUID строки из раздела «Дополнительно» (только вуз, КАМ, взаимодействие, договор) — важнее ключа и названия и в предпросмотре, и при применении;
2. внешний ключ (`external_key`) — из столбца ключа, а если столбец не сопоставлен или пуст, выводится из нормализованного названия:
   - вуз `org:<название вуза>`, вендор `vendor:<ключ вендора>`, ПО `product:<ключ вендора>|<ПО>` (ключ вендора — см. «Общее правило ключа вендора»);
   - контакт `contact:<ключ вуза>|<ФИО контакта>`;
   - договор `agreement:<ключ вуза>|<ключ ПО>|<номер договора>`;
   - ключ длиннее 200 символов заменяется на `<префикс>:<SHA-256>` той же нормализованной строки;
3. уникальное название, если по ключу ничего нет: вуз и вендор — по названию (уникальны в БД), ПО — по названию внутри вендора, контакт — по ФИО среди контактов вуза, договор — среди договоров того же вуза и ПО с тем же номером договора, а если номер в файле задан, но такого договора нет, — единственный договор этого вуза и ПО без номера (так дополняется договор, созданный из карточки взаимодействия). Если в файле задан собственный ключ, по названию находятся только записи без ключа.

### Общее правило ключа вендора

Вендор находится одним правилом `CatalogNames.vendorKey` во всех местах записи вендора: профиль «Каталог по ТЗ», профиль «Вендоры, продукты и контакты» и справочник вендоров (проверка дублей). Правило — нормализация названия (края и повторные пробелы, кавычки «» " ' и похожие, регистр, «ё» = «е») и удаление правовой формы в начале: ООО, ОАО, ПАО, АО, ЗАО, ИП. Поэтому «Базис», «ООО «Базис»» и «ооо базис» — один вендор. Название ПО внутри вендора сравнивается той же нормализацией без удаления правовой формы.

- Совпадение по правилу не переименовывает запись: у найденного вендора или ПО сохраняется прежнее название, в протоколе «было» и «станет» совпадают. Переименование — только в справочнике или по явному ключу из файла, если названия различаются не только правовой формой, кавычками и регистром.
- Сохранённые `external_key` не пересчитываются. Ключ, выведенный по правилу, ищется первым; если его нет, вендор находится по названию с любым прежним ключом, и этот ключ остаётся у записи.
- Два существующих вендора, совпадающих по правилу (например, «Базис» и «ООО «Базис»»), дают «Конфликт» строки; автоматического слияния нет, записи объединяет администратор в справочнике.

Запись, созданная из интерфейса или bootstrap без ключа и найденная по названию, показывается как «Обновить»: ей проставляется ключ (в протоколе «Ключ …: — → …»). Повторный импорт того же файла находит её уже по ключу и даёт «Без изменений».

Конфликт строки (строка не применяется, остальные применяются):

- найдено несколько записей с тем же нормализованным названием;
- запись с таким названием уже связана с другим ключом, а в файле задан собственный ключ;
- переименование по ключу или UUID на название, занятое другой записью (уникальность БД проверяется в предпросмотре, а не падением при применении);
- ключ и явный UUID указывают на разные записи;
- контакт или договор с этим ключом принадлежит другому вузу;
- строка меняет данные обезличенного контакта или контакта с ограниченной обработкой ПДн («Контакт обезличен или его обработка ограничена; уточнение — через «Субъект ПДн»»); строка с теми же данными такого контакта применяется без его изменения;
- номер договора из файла не найден, а у вуза по этому ПО уже есть договоры с другими номерами (ключ договора выведен из названия, UUID взаимодействия и договора не указаны). Импорт не угадывает, исправлен ли номер (Д-1 → Д-01) или это ещё один договор: для исправления администратор указывает UUID договора для строки (договор получит новый номер, «Обновить»), для нового договора — UUID взаимодействия или столбец ключа договора.

## Менеджер

«ФИО Менеджера» сравнивается с `display_name` активных профилей CRM с ролью USER и командой (профиль CRM не хранит email, поэтому сопоставление по email невозможно; значение с email не найдётся):

- одно совпадение — менеджер вуза;
- ни одного — строка «Ошибка» с текстом «Активный КАМ «…» не найден»;
- несколько — «Конфликт»: неоднозначное имя не выбирает человека случайно. Строка протокола показывает список кандидатов «ФИО — команда, вузов: N» (`managerCandidates`); выбранный КАМ передаётся как явный UUID строки (`rowTargets`), после чего предпросмотр перестраивается кнопкой «Перестроить предпросмотр». Тот же UUID можно по-прежнему указать в разделе «Дополнительно». Явный UUID должен принадлежать активному USER с командой; если ФИО в файле с ним не совпадает — конфликт.

Новый вуз создаётся в команде менеджера, поэтому для нового вуза менеджер обязателен. Достаточно указать его в одной строке вуза (объединённые ячейки, ФИО только в первой строке): строки того же нового вуза с пустым ФИО получают этого менеджера, в протоколе он показан в строке. Если ни в одной строке нового вуза менеджер не указан, а в форме выбрана «Команда для новых вузов без менеджера» (`mapping.unassignedTeamId`, только действующая команда), вуз создаётся в этой команде без ответственного: в протоколе «ФИО Менеджера: — → Требует назначения», КАМ затем назначает руководитель. Без выбранной команды такие строки получают ошибку «Для нового вуза укажите ФИО менеджера или выберите команду для вузов без менеджера»; разные менеджеры в строках одного нового вуза — ошибка «Для нового вуза укажите ФИО менеджера». Для существующего вуза менеджер другой команды — конфликт: передача между командами выполняется в карточке вуза. Смена менеджера внутри команды пишет событие назначения (кто, кому, администратор импорта) и отзывает кэш доступа обоих КАМ. Пустое ФИО у существующего вуза менеджера не меняет. Разные менеджеры одного вуза в одном файле — конфликт всех таких строк.

## Взаимодействие и договор

Договор (ProductAgreement) создаётся или обновляется, если в строке есть номер договора, подписание, срок, статус, комментарий, ключ договора или явный UUID взаимодействия/договора.

Строка только с вузом, вендором и ПО задаёт связь «у вуза есть это ПО». Если у вуза уже есть договор с этим ПО, строка его не меняет. Если договора нет и в файле нет другой строки с договором по этой же паре вуз — ПО, создаётся договор без номера и реквизитов (ключ `agreement:<ключ вуза>|<ключ ПО>|`) во взаимодействии по правилам ниже; строка показывается как «Создать». Такой договор позже дополняется строкой с номером (правило «единственный договор без номера» выше).

Договор всегда принадлежит взаимодействию вуза. Взаимодействие выбирается так: взаимодействие найденного договора; явный UUID взаимодействия (должен принадлежать этому вузу); единственное взаимодействие вуза, уже связанное с этим ПО; если таких несколько — конфликт с просьбой указать UUID. Если связанного взаимодействия нет, при применении создаётся новое по шаблону процесса по умолчанию — тем же кодом, что и при создании из карточки: копия этапов и переходов шаблона, начальный этап, событие CREATED. Название взаимодействия — название ПО, автор — администратор, выполнивший импорт. Если шаблона процесса по умолчанию нет, применение отклоняется целиком с сообщением «Нет шаблона процесса по умолчанию; создайте его перед импортом», данные не записываются. В протоколе это видно как «Взаимодействие: Новое взаимодействие «…» по базовому процессу»; следующие строки того же вуза и ПО показывают «Взаимодействие, создаваемое строкой N» и используют его же.

## Несколько ответственных от вуза

Ячейка «Ответственные от ВУЗа» делится на отдельные контакты по «;» и переводу строки. Запятая делит ячейку, только если каждая часть начинается с заглавной буквы («Сидорова Анна, Кузнецов Илья»), поэтому «Иванов, декан» остаётся одним контактом. Часть записи с «@» — почта контакта, часть с 10 цифрами после +7 или 8 — его телефон: «Иванов Олег, ivanov@example.test» даёт контакт «Иванов Олег» с этой почтой. Рядом с почтой или телефоном в записи должно быть одно ФИО; почта без домена или два ФИО в такой записи — ошибка строки. Значение столбца почты или телефона важнее значения из ячейки. Должность, email и телефон для нескольких ответственных указываются в том же порядке через «;»; другое число значений — ошибка строки. Каждый контакт ищется и создаётся отдельно по ключу `contact:<ключ вуза>|<ФИО>`; повтор файла — «Без изменений». Столбец ключа контакта допустим только при одном ФИО в ячейке. Формат согласован как допущение до ответа заказчика.

## Записи, которых нет в реестре

Предпросмотр профиля «Каталог по ТЗ» перечисляет действующие договоры вузов из файла, продукта которых нет ни в одной строке файла (`missingRecords`: вуз, вендор, продукт, номер договора, взаимодействие). По умолчанию они остаются; администратор отмечает «Архивировать» у нужных, и при применении (`archiveAgreementIds`, в подтверждении указано их число) договоры получают `archived_at`, а в журнал справочников пишется «Архивирование: договор … Нет в загруженном реестре». Архивный договор остаётся в карточке с меткой «Договор в архиве: нет в реестре» и в истории. Строка файла с этим договором снова делает его действующим («Договор в архиве: да → нет», событие восстановления в журнале). Архивировать можно только записи из списка текущего предпросмотра; другой идентификатор — `400`, поле `archiveAgreementIds`. Вуз при этом не архивируется: организации архивирует руководитель или администратор в интерфейсе.

Созданные и изменённые применением импорта организации, вендоры, продукты, ИТ-направления, программы и договоры пишутся в журнал справочников: автор — администратор импорта, Request ID — `catalog-import:<commandId>`, в подробностях изменённые поля и пометка «импорт каталога». Присвоение ключа записи без смены значений в журнал не пишется. Организация, созданная из заявки сайта, тоже пишется в журнал справочников («из заявки сайта»).

## Статус по передаче

Значение нормализуется. Если задан словарь сопоставления («значение в файле=значение в CRM») и значение в нём есть — сохраняется значение словаря. Иначе, если значение совпадает с уже известным статусом CRM (без учёта регистра/пробелов) — сохраняется написание CRM. Иначе без словаря значение принимается как есть; со словарём — ошибка строки. Словарь не угадывает этап workflow.

## Комментарий

Комментарий сохраняется событием COMMENTED на текущем этапе взаимодействия договора; автор — администратор импорта, время — момент применения (не выдаётся за исторический факт неизвестной даты). Ключ события — `comment:` + SHA-256 от ключа договора и текста. Повтор того же текста — «Без изменений», новое событие не создаётся; изменённый текст создаёт новое событие, прежнее остаётся в истории.

## Дубли внутри файла

После построения плана строки сверяются между собой:

- одна и та же запись (вуз, вендор, ПО, контакт) с разным написанием или значениями, одно название у разных записей, разные менеджеры одного вуза — «Конфликт» во всех таких строках с номером противоречащей строки;
- повтор того же договора (вуз, ПО, номер договора) — «Конфликт» в повторной строке («Этот договор уже указан в строке N»); если значения различаются, конфликтуют обе строки.

Корректные строки файла применяются независимо от конфликтных.

## Профиль «Направления и программы»

Поля: `directionExternalKey` и `directionName` обязательны; `programExternalKey`, `programName`, `programDirectionRef` — вместе. Ключ направления обязателен (по нему направление переименовывается); запись без ключа находится по уникальному названию и получает ключ. Программа ищется по ключу, затем по названию внутри направления; `programDirectionRef` должен совпадать с ключом направления строки.

## Профиль «Вендоры, продукты и контакты»

Профиль `VENDOR_CONTACTS` загружает справочник вендоров в формате файла организатора «Вендоры.xlsx»: каждая строка — компания, её продукты и контактное лицо по этим продуктам. Шаблон с вымышленными контактами — кнопка «Скачать шаблон «Вендоры, продукты и контакты»» (`/vendor-contacts-template.xlsx`, лист «Лист1», 5 компаний, 9 продуктов, 8 контактов на `example.test`).

| Столбец файла | Поле сопоставления | Куда записывается | Правило |
|---|---|---|---|
| Компания | `vendorName`, обязательно | Vendor.name | общее правило ключа вендора; строки одной компании — один вендор; новому вендору даётся название из первой строки |
| Продукт | `productNames` | Product.name внутри вендора | значения в «…» с учётом вложенных кавычек («Управление ИТ-проектами на базе ПО ПАО «Ростелеком»» — одно название); без «ёлочек» ячейка делится по «,» и «;»; хранится без внешних «ёлочек»; повтор в ячейке убирается |
| ФИО | `vendorContactName` | VendorContact.name | обязательно, если в строке есть телефон, почта или способ связи |
| Телефон | `vendorContactPhone` | VendorContact.phone | хранится как `+7XXXXXXXXXX`: 11 цифр с ведущей 7 или 8 либо 10 цифр, скобки, пробелы и дефисы допускаются. Иначе ошибка поля без значения в тексте |
| Почта | `vendorContactEmail` | VendorContact.email | края обрезаются, одна «@» и точка в домене; регистр хранится, сравнение без регистра; опечатки не исправляются |
| Способ связи | `vendorContactChannels` | `prefers_email`, `prefers_telegram` | «Почта», «Email», «E-mail» — почта; «Чат в ТГ», «ТГ», «Telegram», «Телеграм» — Telegram; несколько значений через запятую; неизвестное значение — ошибка поля. Пустая ячейка не меняет признаки существующего контакта |

Сопоставление:

- контакт ищется у найденного вендора по почте без учёта регистра, а без почты — по ФИО; ключ нового контакта `vendor-contact:<ключ вендора>|<почта или ФИО>`;
- почта найденного контакта у другого ФИО — «Конфликт»; несколько контактов вендора с одним ФИО без почты — «Конфликт»;
- у продукта один контакт (`products.vendor_contact_id`, контакт только своего вендора — составной внешний ключ); строка переносит продукт к контакту строки, в протоколе «Контакт у продуктов: было → станет»;
- пустая ячейка телефона не стирает сохранённый телефон; архивный контакт, снова указанный в файле, восстанавливается;
- контакт обезличенный или с ограниченной обработкой — «Конфликт».

Дубли внутри файла: один продукт у двух компаний — «Конфликт» обеих строк; один продукт с разными контактами — «Конфликт»; один контакт (почта или ФИО у вендора) с разными ФИО, телефоном или способом связи — «Конфликт».

Применение создаёт вендора, контакт и продукты строки в той же транзакции, что и остальные выбранные строки. Созданные вендоры и продукты, смена контакта продукта пишутся в журнал справочников с пометкой «импорт каталога». Создание и изменение контакта пишется в журнал справочников (вид «Контакт вендора») с названием вендора и списком изменённых полей, без телефона и почты. Повтор того же файла даёт «Без изменений».

Правит контакты также администратор в «Справочники → Вендоры → Контакты» (`/api/admin/catalogs/vendors/{vendorId}/contacts`): ФИО, телефон, почта, способ связи, продукты контакта, архив. Архивирование открепляет продукты. КАМ и руководитель видят действующий контакт у продукта в карточке («Продукты и соглашения») и в форме «Договор и лицензия»; архивный контакт и контакт с ограниченной обработкой не показываются.

## Ограничения

- Выведенный из названия ключ меняется вместе с названием: переименованный в файле вуз без столбца ключа будет создан как новый. Для переименований используйте столбец ключа или UUID вуза.
- Устаревший файл вернёт прежнее название записи, переименованной в CRM после импорта, если её ключ выведен из прежнего названия.
- Импорт ничего не удаляет; архивируются только договоры, отмеченные администратором в списке отсутствующих записей.
- Тип организации в столбце «Тип»: «вуз», «колледж» (или «СПО»), «школа».
- Предпросмотр и применение выполняются синхронно в запросе (лимиты выше), без фонового планировщика; каталоги для сопоставления читаются в память одним запросом на таблицу.
