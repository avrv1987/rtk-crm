# Workflow: этапы, переходы и контроль исполнения

Документ описывает, как CRM ведёт карточку взаимодействия по этапам пути ИТ Школы РТК (ТЗ §2 п.1–14, §3, ФТ2, ФТ6, ФТ9) и какие правила обработки данных при этом применяются (ТЗ §6.7, «используемые методы обработки данных»). Код правил графа находится в одном классе `backend/src/main/java/ru/rtk/crm/interaction/WorkflowGraph.java`; сервисы шаблонов и карточек вызывают его, собственных правил переходов не содержат.

## Модель

**Шаблон процесса** — упорядоченный список этапов (`name`, `order`, `optional`) и явный список переходов (`fromOrder`, `toOrder`, `commentRequired`). Базовый шаблон создаётся миграцией V8 и содержит 13 содержательных действий пути ТЗ: поиск контакта, уточнение актуальности, встреча, обмен документами, необязательная корректировка документов, подписание, передача материалов, сопровождение внедрения, обучение преподавателей, актуализация программы, занятия, обновление документации и материалов, повышение квалификации. Пункт 14 пути, «контроль за исполнением каждого этапа», реализован не отдельным этапом, а сроками, ответственным, историей и картой пути (раздел «Контроль исполнения»).

**Снимок (snapshot) карточки.** При создании взаимодействия этапы и переходы выбранного шаблона копируются в карточку с новыми UUID. Правка шаблона сама по себе действует только на новые карточки; идущие работы переводятся на новую версию шаблона отдельно, по решению руководителя (раздел «Версии маршрута»). Действующая карточка также правится локально командами `RENAME`, `ADD_AFTER`, `MOVE_AFTER`, `DELETE`. Название этапа в событиях истории хранится снимком на момент события, поэтому переименование не переписывает историю.

**Кто что меняет.** Шаблоны своей области создают и меняют руководитель (шаблоны команды) и администратор (общие шаблоны, включая базовый). Руководитель видит базовый шаблон в списке управляемых и читает его по идентификатору (`GET /api/admin/workflow-templates/{id}`) только как источник копии: кнопка «Создать на основе базового» открывает редактор с его этапами и переходами, а сохранение создаёт шаблон команды; изменить или удалить базовый шаблон руководитель не может, это проверяет сервер. Другие общие шаблоны руководителю по идентификатору не выдаются (`403`).

**Шаблон по умолчанию.** Новая карточка без явного выбора шаблона создаётся по шаблону команды по умолчанию (`teams.default_workflow_template_id`), а если он не выбран — по общему шаблону по умолчанию; так же работают импорт каталогов и применение записей источников. Руководитель кнопкой «Сделать шаблоном команды по умолчанию» выбирает шаблон своей команды, кнопкой «Вернуть общий шаблон по умолчанию» снимает выбор. Администратор кнопкой «Сделать шаблоном по умолчанию» переносит признак общего шаблона по умолчанию на другой общий шаблон (`POST /api/admin/workflow-templates/{id}/default`, `version`, `Idempotency-Key`; устаревшая версия — `409`). Шаблон чужой команды — `404`, КАМ — `403`. Идущие карточки не меняются: у них свой снимок. Удалённый шаблон команды снимается с команды (`ON DELETE SET NULL`). `GET /api/workflow-templates` возвращает `teamDefaultTemplateId`, и в форме нового взаимодействия пункт «Шаблон команды по умолчанию: …» называет выбранный шаблон. Карточку, её план и её этапы меняют ответственный КАМ (роль USER, организация назначена ему) и руководитель команды организации; автором события записывается тот, кто выполнил действие. Чужая карточка отвечает `404`, видимая карточка для роли без права изменения — `403` (роли и порядок проверок — `docs/roles.md`).

## Правила графа

### Переходы базового шаблона

Базовый шаблон V8 содержит переходы вперёд и назад между соседними этапами без комментария (24 перехода) и один пропуск «Обмен документами → Подписание» через необязательную «Корректировку документов» с обязательным комментарием (`commentRequired = true`). Шаблоны команд задают переходы явно и могут не содержать возвратов.

### Проверка графа

Проверка одинакова для шаблонов (`POST/PATCH /api/admin/workflow-templates`) и для правок карточки (`POST /api/interactions/{id}/stage-edits`). Граф отклоняется с `400`, если:

- нет стартового этапа (`order = 0`);
- переход ссылается на этап вне графа, ведёт в тот же этап или повторяется;
- переход между несоседними этапами (пропуск вперёд или возврат через этап назад) не помечен `commentRequired`;
- у этапа, кроме последнего, нет ни одного исходящего перехода;
- хотя бы один этап недостижим от стартового.

Сообщение об ошибке называет этапы по именам: «Этап «…» недостижим из начального этапа «…»: добавьте переход в него из предыдущего этапа», «Этапу «…» нужен исходящий переход…», «Переход «…» → «…» пропускает этапы…». Редактор шаблона проверяет те же правила до отправки и показывает то же понятное сообщение; при удалении этапа он соединяет каждый входящий переход с каждым исходящим (соседние этапы — без комментария, пропуск — с обязательным комментарием) и сообщает, какие переходы добавлены.

Так правило «пропуск допустим только с пояснением» становится проверкой данных: скрытого обхода обязательного этапа без комментария в сохранённом графе нет. Шаблон может явно разрешить пропуск обязательного этапа, но только как переход с обязательным комментарием.

### Правка этапов карточки

`RENAME` меняет только название и граф не трогает. `ADD_AFTER`, `MOVE_AFTER` и `DELETE` меняют переходы только вокруг затронутого этапа; переходы между этапами, которые остались соседями, не меняются. Операции одного запроса применяются к графу по очереди, в порядке запроса.

**Удаление этапа.** Каждый путь «A → удалённый этап → B» заменяется прямым переходом A → B. Комментарий для него обязателен, если он был обязателен хотя бы на одном из двух переходов пути. Если переход A → B уже был, остаётся менее строгий вариант: без комментария, если хотя бы один из двух способов пройти от A к B его не требовал. Соседи удалённого этапа соединяются только в тех направлениях, в которых через этап можно было пройти: шаблон без возвратов возвратов не получает.

**Вставка этапа N после этапа A** (следующий этап — B). Рёбра вставки повторяют разорванную пару A–B:

1. если был переход A → B, появляются A → N и N → B с тем же признаком комментария; если его не было, A → N и N → B создаются без комментария, чтобы новый этап был достижим;
2. переходы N → A и B → N появляются, только если был возврат B → A, и с его признаком комментария;
3. переходы вперёд через место вставки (из A или раньше в B или дальше):
   - для обязательного N переводятся на N (X → B становится X → N с тем же признаком): добавленный обязательный этап нельзя обойти, в том числе прежним пропуском с комментарием;
   - для необязательного N сохраняются и становятся пропуском с обязательным комментарием; прямой переход A → B превращается в пропуск N с комментарием.

При вставке после последнего этапа образцом служит пара «предыдущий этап — A»: A → N создаётся всегда, N → A — только если у A есть возврат к предыдущему этапу.

**Перемещение этапа** выполняется как удаление этапа с прежнего места и вставка после нового этапа-якоря: прежние соседи соединяются между собой, перемещённый этап получает переходы по образцу новой пары соседей.

После каждой правки отбрасываются переходы, которые перестали проходить проверку графа (например, прежний переход без комментария между этапами, между которыми вставлен этап), затем весь граф проходит проверку. Если правка оставляет этап без выхода или недостижимым, запрос отклоняется с `400`.

Ограничения правок не изменились: удалять и перемещать можно только будущие этапы, которые не упомянуты в событиях истории и вложениях; текущий этап не удаляется. Каждая правка увеличивает версию карточки и пишет в историю одно событие `STAGES_EDITED` с перечнем изменений («Добавлен обязательный этап «…» после «…»», «Этап «…» перемещён после «…»», «Удалён этап «…»», «Этап «…» переименован в «…»»).

## Версии маршрута

Процесс федеральный и может меняться раз в квартал, поэтому маршрут меняется без разработчика и без потери идущих работ (план доработки, п. 2.2; решение в базе знаний — «версии маршрута»).

**Версии шаблона.** Каждое сохранение шаблона (создание и любая правка, в том числе только названия) создаёт новую версию в `workflow_template_versions`: номер по порядку, название, этапы и переходы, автор, время, необязательный комментарий «Что изменилось». Старые версии не меняются и не удаляются вместе с правками; удаление шаблона удаляет и его версии. `WorkflowTemplate.routeVersion` — номер последней версии, `version` по-прежнему служит для проверки одновременной правки (`409`). Новая работа запоминает шаблон и версию (`interactions.workflow_template_id`, `workflow_version`), каждый этап работы — этап шаблона, из которого он скопирован (`interaction_stages.template_stage_id`).

**Устойчивый идентификатор этапа.** Этап шаблона сохраняет идентификатор между версиями: редактор передаёт `stages[].id` для сохранённых этапов, новый этап получает новый идентификатор. Переименование, перенос и смена обязательности идентификатор не меняют; удалённый и заново добавленный этап — это новый этап.

**История и сравнение.** `GET /api/workflow-templates/{id}/versions` отдаёт версии от новой к старой с числом идущих работ области на каждой (у администратора — без числа: работ он не видит). Экран «Администрирование → Шаблоны этапов → История версий» показывает версии, их этапы, сравнение двух версий (добавлены, удалены, переименованы, перемещены этапы, изменена обязательность, новые и убранные переходы, комментарий при переходе), кнопки «Скачать файл» и «Взять за основу» (версия загружается в редактор; сохранение создаёт новую версию, так шаблон возвращается к прежнему маршруту).

**Обновление работ до версии.** Руководитель открывает «Обновить работы до версии N» (`POST /api/admin/workflow-templates/{id}/versions/{number}/rollout-preview`). Предпросмотр берёт идущие (не завершённые) работы своей команды по этому шаблону на других версиях и показывает:
- для каждой исходной версии — число работ и сопоставление её этапов этапам версии N: «без изменений» и «переименован» — тот же идентификатор, «найден по названию» — идентификатор другой, название совпало, «этапа нет в новой версии» — работа с него переходит в следующий сохранившийся этап (если его нет — в предыдущий), «выбрано вручную» — выбор руководителя в списке «Куда перейдут работы»; ручной выбор отменяет автоматический для любого этапа и позволяет объединить этапы;
- каждую работу: где она сейчас, на каком этапе окажется, отметки «текущий этап исчезает» и «этапы меняли в карточке», перечень изменений.

Кнопка «Обновить выбранные работы» (`POST …/rollout`, `Idempotency-Key`) переводит отмеченные работы одной транзакцией. Для каждой работы сверяется её версия из предпросмотра: если работу изменили, всё отменяется с `409`, предпросмотр строится заново. Этапы и переходы работы становятся как в версии N, сохранённые этапы остаются теми же записями (история, файлы и отметки на них не трогаются), новые добавляются. История удалённого или объединённого этапа переходит на этап, в который он сопоставлен: ссылки событий и файлов переводятся на него, названия этапов в событиях остаются прежними, поэтому лента истории не меняется. Отметка выполнения удалённого этапа снимается (событие отметки в истории остаётся). В историю каждой работы пишется событие `STAGES_EDITED`: «Маршрут обновлён до версии N шаблона «…» (была версия M): текущий этап «X» → «Y»; этап «…» переименован в «…»; добавлен этап «…»; удалён этап «…»».

**Правки этапов в карточке.** Работа считается изменённой в карточке, если её этапы, их названия, обязательность, порядок или переходы отличаются от её версии. Такие работы в мастере не отмечены по умолчанию; чтобы обновить их, руководитель отмечает их и подтверждает «Заменить этапы, изменённые в карточке, этапами версии N» (`replaceLocalChanges = true`, иначе `400`). Правки при этом не переносятся, а заменяются версией, и это записывается в событие истории. Перенос правок не выбран сознательно: правка карточки — исключение для конкретного вуза, а автоматическое слияние двух изменений маршрута даёт результат, который никто не утверждал.

**Откат.** Тот же механизм с прежней версией: «Вернуть работы к версии N» на строке старой версии. Событие истории — «Маршрут возвращён к версии N».

**Файл шаблона.** «Скачать файл» выгружает версию в JSON:
```json
{
  "format": "rtk-crm-workflow",
  "formatVersion": 1,
  "name": "Базовый процесс ИТ Школы РТК",
  "sourceVersion": 3,
  "stages": [{ "key": "uuid этапа", "name": "Поиск контакта", "optional": false }],
  "transitions": [{ "from": 0, "to": 1, "commentRequired": false }]
}
```
`from` и `to` — номера этапов в списке с нуля, `key` — устойчивый идентификатор. «Загрузить этапы из файла» в редакторе проверяет файл и заполняет редактор: без открытого шаблона получается новый шаблон, при открытом — новая версия этого шаблона. Граф проверяется до сохранения в редакторе и на сервере теми же правилами. При загрузке в другой стенд идентификаторы не совпадут, и при обновлении работ этапы сопоставятся по названию.

**Права.** Версии и файл шаблона видит тот, кто видит шаблон (`GET /api/workflow-templates`): руководитель и КАМ — общие и своей команды, администратор и «Руководство» — общие; PARTNER — `403`. Создают версии те же, кто ведёт шаблоны: руководитель — шаблоны команды, администратор — общие и базовый. Обновлять работы может только руководитель и только работы своей команды — по шаблонам команды и по общим шаблонам (общий маршрут меняет администратор, работы каждой команды переводит её руководитель). Администратор и «Руководство» — `403`, шаблон чужой команды — `404`, работа чужой команды — `404`.

**Отчёты.** Отчёты группируют этапы по названию, а не по идентификатору:
- «Портфель» — по названию текущего этапа работы. Работы на разных версиях с переименованным этапом попадут в разные строки, пока их не обновят до одной версии; после обновления — в одну.
- «Состояние на дату» — по названию этапа в последнем событии до даты среди `CREATED`, `TRANSITIONED`, `STAGES_EDITED`, `PLAN_UPDATED`. Событие обновления маршрута несёт новое название текущего этапа, поэтому срез после обновления показывает новое название, до обновления — прежнее.
- «Длительность этапов» — по названию этапа в событиях входа (`CREATED`, `TRANSITIONED`). Время, прожитое на этапе до переименования, остаётся под прежним названием; если работа при обновлении перешла с удалённого этапа на другой, время до следующего перехода засчитывается этапу, в который она входила.
- Отчёты не ломаются: события хранят название этапа на момент события и ссылаются на существующий этап работы.

## Переход и комментарий

Переход и комментарий — серверные команды с `Idempotency-Key` и `version`. Порядок проверки: видимость карточки (иначе `404`), роль (иначе `403`), повтор ключа (тот же payload возвращает прежний результат, иной — `409 IDEMPOTENCY_CONFLICT`), версия (иначе `409 VERSION_CONFLICT`), существование целевого этапа и перехода, обязательность комментария. Изменение этапа, событие, комментарий и привязка очищенных вложений сохраняются одной транзакцией.

Обе команды принимают необязательный объект `nextStep` (`nextAction`, `nextActionAt`). Если он передан, следующий шаг и срок заменяются в той же транзакции, а событие перехода или комментария хранит новый план. Если `nextStep` не передан, план не меняется.

## Отметка выполнения этапа вне текущего

У карточки один текущий этап, но работу по другим этапам маршрута можно вести параллельно, например обучать преподавателей во время сопровождения внедрения. Полноценных параллельных веток графа нет.

- `POST /api/interactions/{id}/stage-completions` (`version`, `stageId`, `completedOn`, необязательные `comment` до 4000 символов и `attachmentIds`) отмечает выполненным любой этап снимка, кроме текущего. Текущий этап не меняется: его завершает обычный переход. Дата выполнения обязательна и не может быть позже сегодняшней даты по Москве.
- Повторная отметка того же этапа заменяет дату и комментарий и пишет новое событие. `attachmentIds` — очищенные файлы, уже загруженные в этот этап и ещё не привязанные к событию; они привязываются к событию отметки, как при переходе.
- `DELETE /api/interactions/{id}/stage-completions/{stageId}?version=…` снимает отметку. Файлы остаются привязанными к событию отметки, событие остаётся в истории.
- Обе команды проверяются так же, как переход: видимость карточки (`404`), роль USER или LEADER (`403`; КАМ — свои вузы, руководитель — вузы своей команды), `Idempotency-Key` (повтор возвращает прежний результат, иной payload — `409 IDEMPOTENCY_CONFLICT`), `version` (`409 VERSION_CONFLICT`). Каждая команда увеличивает версию карточки и пишет одно событие: `STAGE_COMPLETED` с текстом «Дата выполнения: ДД.ММ.ГГГГ. Комментарий» или `STAGE_COMPLETION_CLEARED` с текстом «Снята отметка о выполнении ДД.ММ.ГГГГ». Отчёт «События» подписывает их «Этап отмечен выполненным» и «Снята отметка выполнения этапа».
- Отметка хранится в `interaction_stage_completions` (одна на этап, ссылка на событие) и приходит в карточке списком `stageCompletions` в порядке маршрута. Этап с событием отметки считается использованным: его нельзя удалить или переместить правкой этапов.
- Переход в отмеченный этап выполняется по обычным правилам графа; отметка при этом сохраняется, и карта пути показывает у текущего этапа дату отметки.

## Контроль исполнения этапа

Контроль каждого этапа (ТЗ §2 п.14) складывается из четырёх данных карточки:

| Данные | Где хранится | Как меняется |
|---|---|---|
| Текущий этап | `interactions.current_stage_id` | переход |
| Следующий шаг и срок | `interactions.next_action`, `next_action_at` | создание, `PATCH /api/interactions/{id}`, `nextStep` в переходе или комментарии |
| Ответственный | `organizations.owner_manager_id`, снимок в каждом событии | назначение КАМ |
| История | `interaction_events` | каждая команда карточки |

`PATCH /api/interactions/{id}` принимает `version` и любую комбинацию полей `nextAction`, `nextActionAt`, `programId`, `productIds`. Отсутствующее поле оставляет текущее значение, `null` очищает его. Новая программа и добавляемые продукты должны быть активными записями каталога; уже связанные архивные значения можно сохранить. Продукт, у соглашения которого заполнены номер договора, лицензия, срок или статус передачи, снять нельзя: это защищает данные договора от потери. Условие проверяется до изменения и повторяется в самом удалении: удаляются только соглашения без договорных данных, и если после удаления у снимаемых продуктов остались заполненные соглашения (их успел заполнить импорт каталога), команда отклоняется с `400` и откатывается целиком. Запрос без полей отклоняется, запрос без фактических изменений возвращает карточку без новой версии и события. Изменение пишет событие `PLAN_UPDATED`: новый следующий шаг и срок хранятся структурно, изменения программы и продуктов — кратким текстом.

В событиях истории сохраняются тип, этап и снимок его названия, прежний и новый этапы перехода, комментарий, новый план (`nextStep`), автор (UUID профиля и ФИО из CRM-профиля), снимок ответственного КАМ, версия карточки и время. История упорядочена по версии карточки, затем по времени и идентификатору: версия растёт на единицу с каждой командой под блокировкой строки, поэтому порядок не зависит от точности часов сервера.

## Карта пути в карточке

Карта пути показывает все этапы снимка по порядку с нумерацией от 1:

| Состояние | Правило | Что показано |
|---|---|---|
| Текущий | `currentStageId` карточки | выделен рамкой; сколько дней карточка находится на этапе |
| Выполнен | этап отмечен выполненным командой `stage-completions` и не является текущим | дата выполнения из отметки |
| Пройден | этап был целевым в событии `CREATED` или `TRANSITIONED` и не является текущим | дата и время последнего входа |
| Пропущен | этап раньше текущего по порядку, входа в него не было | приглушён |
| Впереди | этап после текущего, входа в него не было | приглушён |

Необязательные этапы помечены. Текущий пункт списка имеет `aria-current="step"`, состояние дублируется текстом, а не только цветом. Дни на этапе считаются в браузере как целое число суток от последнего входа в текущий этап до текущего момента. Просрочка следующего шага показывается, когда срок раньше текущего времени браузера.

## Методы обработки данных

- Перестроение графа и проверка графа выполняются детерминированно по порядку этапов и флагу `optional`; пользовательские формулы, скрипты, SQL и SpEL в workflow не допускаются.
- Сравнение срока при изменении плана выполняется по моменту времени, а не по записи смещения часового пояса.
- Повтор команды с тем же ключом не создаёт второе событие; иной payload под тем же ключом отклоняется.
- Список взаимодействий вуза загружается страницами по 25 записей, связанные контакты и продукты страницы читаются двумя пакетными запросами. Кнопка «Показать ещё» догружает следующую страницу и только на это время показывает «Загружаем…». После команды список обновляется в фоне одним запросом на все показанные записи (до 100 записей за запрос, сверх этого — дополнительными запросами по 100).
- Черновики комментария, перехода, правки этапов, плана, статуса, отметок, данных работы и правки контакта хранятся в `sessionStorage` отдельно для каждой карточки и очищаются при выходе из системы вместе с остальными черновиками профиля.
- Черновик плана хранит только изменённые пользователем поля: для следующего шага, срока и программы — новое значение и значение карточки на момент первого изменения, для продуктов — явно отмеченные и снятые продукты. Сохранение отправляет только эти поля, а продукты — как текущий набор карточки с отмеченными и снятыми пользователем. Поэтому после `409` и «Обновить карточку» изменения другого пользователя в полях, которые пользователь не трогал, не откатываются. Если поле, которое пользователь меняет, изменилось в карточке, форма показывает текущее значение карточки и предупреждает, что при сохранении останется значение пользователя.

## Циклы работы и обучение преподавателей

- «Начать новый цикл» в карточке (КАМ и руководитель, `POST /api/interactions/{id}/cycles`, `Idempotency-Key`): создаётся новая работа с тем же вузом, программой, продуктами и контактами по выбранному шаблону (по умолчанию предлагается шаблон, в названии которого есть «цикл»), в `interaction_cycles` сохраняются ссылка на прошлую работу и дата начала цикла. Дата начала нового цикла должна быть позже начала прошлого; у работы может быть только один следующий цикл — повтор с тем же ключом возвращает уже созданную работу, другой запрос — `400` с названием существующего цикла. Проверка идёт под блокировкой строки прошлой работы, поэтому два одновременных запроса с разными ключами не создают два цикла: второй получает тот же `400`. В обеих карточках блок «Циклы работы» показывает ссылки «Предыдущий цикл» и «Следующий цикл» (`GET /api/interactions/{id}/cycle`).
- Данные LMS цикла: снимок потока относится к работе того цикла, в интервал которого попадает дата начала потока (от начала цикла до начала следующего). Второй поток того же курса с новыми датами добавляет администратор (`docs/integrations.md`, «Сохранённые сопоставления»), поэтому у нового цикла свои числа, а числа прошлого остаются на дату его закрытия.
- Блок «Обучение преподавателей (повышение квалификации)» (`GET/POST /api/interactions/{id}/teacher-trainings`, `Idempotency-Key`, `version` карточки — `409` при устаревшей): дата (не позже сегодня), курс, записано, завершили (не больше записанных; пусто — «нет данных»), документ о ПК из загруженных на текущем этапе вложений, дата следующего цикла ПК (позже даты обучения). Запись — это комментарий в истории на текущем этапе с этим текстом и документом плюс строка `teacher_trainings`. Флажок «Напомнить» ставит следующим шагом карточки «Следующий цикл повышения квалификации преподавателей» со сроком в 10:00 даты следующего цикла, поэтому он попадает в «Мою работу» и в напоминания по сроку. Преподаватели из этих записей не входят в «Обучающихся» и в DEMAND.

## Моя работа: список взаимодействий по всем вузам

`GET /api/interactions` без `organizationId` возвращает взаимодействия всех вузов из области профиля. Область задаёт тот же SQL-фрагмент `OrganizationRepository.visibilityScope`, что и список вузов и отчёты: `i.organization_id IN (SELECT id FROM organizations WHERE …)`. КАМ получает взаимодействия своих вузов своей команды, руководитель — всех вузов команды, администратор без бизнес-области — пустую страницу. С `organizationId` поведение прежнее: чужой или невидимый вуз даёт `404`, фильтры применяются внутри вуза.

- `q` — часть названия взаимодействия или вуза без учёта регистра; `%`, `_` и `\` экранируются и ищутся как обычные символы.
- `due=OVERDUE` — срок следующего шага раньше текущего момента, даже если текст шага не задан; `due=THIS_WEEK` — текст шага задан, срок в текущей календарной неделе по Москве, с понедельника 00:00 до следующего понедельника (включая уже прошедшие дни недели); `due=NO_NEXT_STEP` — нет текста следующего шага или его срока.
- Любой прошедший срок — просрочка. Работа с прошедшим сроком без текста шага попадает и в `OVERDUE`, и в `NO_NEXT_STEP`; в строке «Моей работы» она подписана «Просрочен с …, шаг не задан». Проверка — `InteractionServiceTest.anyPastDeadlineIsOverdueEvenWithoutNextActionText`.
- `status` — статус работы (`interactions.work_status`, вводит пакет карточки): без параметра показываются только активные работы (`ACTIVE`), `PAUSED` и `COMPLETED` — только приостановленные или завершённые, `ALL` снимает отбор. Поэтому завершённые работы по умолчанию скрыты.
- `responsible` — идентификатор профиля ответственного КАМ вуза или `UNASSIGNED` («Требует назначения»: ответственного нет или он больше не активный КАМ команды вуза). Отбор виден руководителю и роли «Руководство»; список КАМ для выбора — `GET /api/report-filters/managers`.
- `minDaysOnStage` — работа находится на текущем этапе не меньше указанного числа суток (1–3650). Вход в этап — время последнего события, целевым этапом которого был текущий этап, а если такого нет — время создания карточки.
- `stage` — точное название текущего этапа; список названий для выбора — `GET /api/report-filters/stages` той же области.
- `licenseExpiresBy` — год 2000–2100: взаимодействия, у которых хотя бы у одного продукта год окончания лицензии не позже заданного; на экране — отбор «Лицензия истекает» с годами от прошлого до шестого следующего.
- `sort=nextActionAt,asc` — ближайшие и просроченные сроки первыми, взаимодействия без срока в конце.
- `status` — статус работы. Без параметра возвращаются только активные работы, поэтому приостановленная и завершённая работа уходит из «Моей работы»; `PAUSED` или `COMPLETED` отбирают такие работы, `ALL` снимает отбор. Карточка вуза запрашивает `ALL` и показывает все работы вуза с меткой статуса.
- `flag` — одна отметка: `WAITING_UNIVERSITY` (ждём вуз), `WAITING_RTK` (ждём РТК), `PROBLEM` (есть открытая проблема в реестре), `RISK` (открытый риск любого уровня), `RISK_OR_PROBLEM` (открытый риск или проблема; используется плитками пультов). Отметки приходят в строке списка и в карточке в поле `marks`: ожидание, число открытых проблем и рисков, наибольший уровень открытого риска и их описания.

Строка списка дополнительно содержит `lastEventType` и `lastEventAt` (вид и время последнего события истории), `stageEnteredAt` (вход в текущий этап; экран показывает «Дней на этапе») и активного заместителя вуза (`deputyManagerName`, `deputyEndsOn`). Индекс `interaction_events_stage_entry_idx` (V18) обслуживает поиск входа в этап.

Страница и общее число считаются в SQL. Название вуза, программы и ФИО ответственного КАМ приходят в той же строке (`organizationName`, `programName`, `ownerManagerName`) через JOIN, контакты и продукты страницы — двумя пакетными запросами, без запроса на каждую строку. Отдельного индекса по сроку нет: номера миграций V13–V16 закреплены за другими пакетами, а на объёме хакатона выборка по индексу организаций достаточна.

## Статус работы, отметки и данные работы

Работа (взаимодействие) имеет статус независимо от этапа: `ACTIVE` «Активна», `PAUSED` «Приостановлена», `COMPLETED` «Завершена». Приостановка требует причины, завершение — итога, возобновление — нет. Из любого статуса можно перейти в любой другой; завершённая работа не блокируется: в ней можно оставить комментарий или возобновить её. Смена статуса пишет событие `STATUS_CHANGED` с причиной или итогом. Работы в статусе, отличном от активного, остаются в карточке вуза, в истории и в отчётах (колонка «Статус работы» рядом с колонкой «Этап»).

Отметки ведутся у работы, а не у вуза: риск вуза выражается риском его работ. Ожидание одно: либо «Ждём вуз», либо «Ждём РТК», с необязательным пояснением до 500 символов. Команда `POST /api/interactions/{id}/flags` передаёт отметку ожидания; изменение пишет событие `DETAILS_UPDATED` с описанием, что поставлено и что снято, автором и временем. Повтор того же значения событие не создаёт.

### Реестр проблем и рисков

С версии миграции V37 у работы может быть несколько проблем и рисков (таблица `interaction_issues`; прежние поля `problem`, `risk_level`, `risk_reason` перенесены в реестр и удалены). Запись: вид (проблема или риск), описание до 1000 символов (обязательно), для риска уровень «средний» или «высокий», ответственный, необязательный срок решения, статус «открыта» или «решена» и при решении — обязательный комментарий «Как решили». Ответственным можно выбрать активного КАМ или руководителя команды вуза; без выбора им становится КАМ вуза, а если КАМ не назначен — автор записи.

- Добавить, изменить (описание, уровень, ответственного, срок; вид не меняется) и отметить решённой могут те, кто ведёт карточку: КАМ своих вузов и руководитель команды. «Руководство» видит реестр только для чтения, администратор и представитель вуза реестр не видят; в кабинет вуза записи не попадают.
- Каждая команда проверяет права на сервере, требует `Idempotency-Key` и CSRF, передаёт `version` работы и повышает её; устаревшая версия — `409 VERSION_CONFLICT`. Решённую запись изменить нельзя (`400`, поле `status`).
- Кто и когда добавил, изменил или решил запись, пишется событием `DETAILS_UPDATED` в историю работы («Добавлена проблема: «…». Ответственный: …, срок …», «Изменён риск «…»: уровень: средний → высокий», «Решена проблема «…». Решение: …»); эти события видны и в ленте «История» карточки вуза.
- Все счётчики и отборы считают только открытые записи: плашки «Проблемы: N» и «Риск: высокий» (наибольший открытый уровень), отбор `flag`, плитки и колонки «С риском или проблемой» на пультах, колонки «Проблема» и «Риск» отчётов «Портфель» и «Разбор КАМ».

В шапке карточки работы плашки кликабельны и открывают окно «Проблемы и риски»: открытые записи (описание, вид и уровень, ответственный, срок, кто и когда отметил), переключатель «Показать решённые», кнопки «Добавить проблему», «Добавить риск», «Изменить», «Решено». В меню «⋯» есть пункты «Проблемы и риски…» и «Чего ждём…». Плашки в «Моей работе» ведут в карточку работы с открытым окном (`#/organizations/<вуз>/<работа>?issues=1`).

Страница «Проблемы и риски» (пункт верхнего меню для КАМ, руководителя и «Руководства», `GET /api/issues`) показывает записи по работам в области видимости роли с отборами «Вид», «Уровень риска», «Ответственный», «Вуз», «Статус» (открытые, решённые, все) и «Только с прошедшим сроком»; колонки — работа, вуз, КАМ, вид, описание, ответственный, срок, возраст (дней с отметки до сегодня или до решения). Сначала идут записи со сроком, ближайший раньше. Кнопка «Скачать XLSX» выгружает те же строки (`GET /api/issues/file`, предел `app.reports.max-rows`, скачивание пишется в журнал безопасности).

Название, дата последнего контакта и связанные контакты правятся той же командой `PATCH /api/interactions/{id}`: переданное поле меняется, непереданное остаётся. В событии `DETAILS_UPDATED` записывается было и стало: «Название: «…» → «…»», «Дата последнего контакта: … → …» (по Москве), «Добавлены контакты: …», «Удалены контакты: …». Добавленные и убранные контакты хранятся ссылками в `interaction_event_contacts`, а имя подставляется из записи контакта при чтении истории и отчётов, поэтому переименованный или обезличенный контакт не сохраняет прежнее имя в событии. Контакт с отметкой «Не актуален» нельзя добавить ни к новой, ни к существующей работе (`400`, поле `contactIds`); из работы, где он уже был, его можно убрать, его имя в прежних записях остаётся.

Все три команды проверяют права так же, как план: невидимая работа — `404`, роль без права вести карточку — `403`, повтор ключа с тем же телом — прежний результат, с другим — `409 IDEMPOTENCY_CONFLICT`, устаревшая `version` — `409 VERSION_CONFLICT`.

## Контакты вуза

Контакт правится `PATCH /api/organizations/{id}/contacts/{contactId}` с `version` и `Idempotency-Key`; контакт чужого или невидимого вуза даёт `404`. Роль во взаимодействии — `SIGNATORY` «Подписант (ЛПР)», `IMPLEMENTER` «Исполнитель (внедрение)», `TEACHER` «Преподаватель», `APPROVER` «Согласует документы», `OTHER` «Другое». Основной контакт у вуза один: отметка нового основного снимает отметку у прежнего и пишет в его историю отдельную запись. Неактуальный контакт не может быть основным; он скрыт из выбора для новых работ и остаётся в прежних. «Контакт подтверждён» (`confirm: true`) сохраняет дату и автора; повторное подтверждение обновляет дату, прежняя остаётся в истории. Каждое изменение пишет в `contact_events` список изменённых полей с прежним и новым значением; при обезличивании контакта прежние и новые значения ФИО, должности, почты и телефона в его `contact_events` очищаются вместе с самим контактом. Вуз, который раньше вёл другой КАМ, отдаётся с `inherited: true` и помечается «Унаследован», пока текущий ответственный после получения вуза не подтвердит хотя бы один контакт.

## Шаг выполнен

`POST /api/interactions/{id}/step-completions` (`Idempotency-Key`, тело `version`, необязательные `result` до 4000 символов и `nextStep`) отмечает текущий следующий шаг выполненным. Порядок проверок тот же, что у других команд карточки: видимость (`404`), роль (`403`, изменять могут только USER и LEADER), повтор ключа, версия (`409`). Если у работы нет ни текста шага, ни срока, команда отклоняется с `400` (поле `nextStep`). В одной транзакции план заменяется новым шагом из `nextStep` (без него шаг и срок очищаются) и пишется событие `PLAN_UPDATED` с комментарием «Шаг выполнен: «<шаг>» (срок ДД.ММ.ГГГГ ЧЧ:ММ). Результат: …» и новым планом. Отдельный тип события не вводится: тип `PLAN_UPDATED` уже учитывают отчёты по событиям, а ограничение типов событий меняет пакет карточки. В карточке кнопка «Шаг выполнен» открывает форму с результатом и полями нового шага; если новый шаг не задан, экран напоминает, что работа останется без плана.

## Ограничения

- Миграция V38 переносит каждый существующий шаблон как версию 1 и привязывает существующие работы к версии 1: к шаблону, этапы которого совпадают с этапами работы по названиям, обязательности и порядку, а если такого нет — к шаблону команды по умолчанию или к общему шаблону по умолчанию; этапы работы связываются с этапами шаблона по названию. Работы, не совпавшие с шаблоном, показываются в мастере как изменённые в карточке.
- В мастере обновления руководитель видит общие шаблоны только через базовый шаблон в своём списке; работы, начатые по другому общему шаблону, через экран не обновляются (API это позволяет).
- Подсказки LMS ищут этап по названию «Занятия»; если версия переименует этот этап, подсказки по такой работе перестанут появляться.

- Шаблоны, сохранённые до введения проверки комментария для пропусков, при следующем сохранении нужно привести к правилам графа. Карточки на их основе при структурной правке этапов теряют недопустимые переходы без комментария.
- Структурная правка может оставить этап без выхода, если через удаляемый этап шаблон позволял пройти только назад; такая правка отклоняется с `400`, граф карточки не меняется.
- Дни на этапе и просрочка в карточке и в строке «Моей работы» вычисляются по часам браузера пользователя; отборы `due`, `minDaysOnStage` и показатели руководителя — по часам сервера.
- Миграция V12 расширяет допустимые типы событий (`STAGES_EDITED`, `PLAN_UPDATED`) и добавляет в события поля плана, V16 — типы `DETAILS_UPDATED` и `STATUS_CHANGED`. Отчёты по событиям подписывают их «Изменены данные работы» и «Изменён статус работы».
- Миграция V17 добавляет типы `AGREEMENT_UPDATED` (изменены договор и передача) и `ATTACHMENT_DELETED` (удалён документ); в отчёте «События» они подписаны «Изменены договор и передача» и «Удалён документ».
- Миграция V25 добавляет типы событий `STAGE_COMPLETED` и `STAGE_COMPLETION_CLEARED` и таблицу `interaction_stage_completions`. Отметка выполнения не является параллельной веткой: разрешённые переходы, «Моя работа» и отчёты по текущему этапу её не учитывают.
