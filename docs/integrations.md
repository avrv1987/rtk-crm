# Интеграции: сайт (JSON), LMS Moodle и общий конвейер источников

Документ описывает, как CRM забирает данные внешних источников, и относится к ТЗ §4 ФТ5 («забирать по API информацию из веб-сайта и LMS по утверждённым полям в формате JSON с последующим добавлением в существующий или новый workflow»), «Пользователь» п.2, §5 и §2 (ранжирование программ).

Доступа к API сайта заказчика и к его тестовым стендам нет, поэтому критерий приёмки — соответствие контракту и работа на заглушке. Как устроены заглушки всех внешних интеграций, включая файл «Загрузка пользователей» и Keycloak/IdP заказчика, и как подключить реальные системы — `docs/integrations/Заглушки.md`.

## Статус

- **Сайт на Laravel — предложенный контракт.** Заказчик не передал API сайта. CRM реализует HTTP-адаптер по контракту, который предлагает сама: `docs/integrations/site-api.yaml`. Демонстрационный стенд `infra/site-fixture` отдаёт страницы в этом формате и проверяет адаптер CRM, но не совместимость с сайтом заказчика. На экране администратора источник помечен «Предложенный контракт, DEMO». Критерий приёмки FR-10 — соответствие контракту и работа на заглушке; сверка с настоящим сайтом остаётся невозможной до получения доступа.
- **Moodle** подключён через ограниченный веб-сервис REST на чтение (раздел «Moodle» ниже). Адаптер проверен на локальном настоящем Moodle 4.5; Moodle заказчика недоступен, поэтому его функции, роли и курсы не проверялись. Пока `MOODLE_BASE_URL`, `MOODLE_TOKEN` или `MOODLE_COURSE_IDS` пусты, запуск отвечает `409 SOURCE_NOT_CONFIGURED`, а колонки Moodle в DEMAND показывают «нет данных».

## Предложенный контракт сайта

`GET {SITE_BASE_URL}/api/crm/records?updated_since=<ISO 8601>&page=<N>`, заголовок `Authorization: Bearer <SITE_TOKEN>`. Ответ:

```json
{"items": [{"externalId": "...", "type": "partnership_request", "createdAt": "...", "updatedAt": "...",
            "status": "new", "organization": {"externalId": "...", "name": "...", "type": "UNIVERSITY"},
            "program": {"name": "..."}, "product": {"name": "..."},
            "contact": {"name": "...", "email": "...", "phone": "...", "position": "..."},
            "applicationsCount": 1, "message": "..."}],
 "nextPage": 2}
```

Полные поля, ограничения длины и правила — в `docs/integrations/site-api.yaml`. Главное:

- ключ записи — `type` + `externalId`; версия — `updatedAt`;
- `updated_since` включительный, страницы с 1, на последней `nextPage: null`;
- `partnership_request` — заявка вуза на сотрудничество; `learning_application` — заявка на обучение, только для статистики спроса;
- отзыв заявки на обучение — та же запись со `status: withdrawn` и более поздним `updatedAt`;
- у `learning_application` объект `contact` CRM отбрасывает до сохранения: персональные данные обучающихся не хранятся.

## Конфигурация и секреты

| Переменная `.env.local` | Свойство backend | Смысл |
|---|---|---|
| `SITE_BASE_URL` | `app.sources.website.base-url` | адрес сайта; пустое значение — источник «не настроен», запуск отклоняется |
| `SITE_TOKEN` | `app.sources.website.token` | Bearer-токен только на чтение |

Переменные — начальные значения: администратор меняет адрес и токен в разделе «Источники данных», блок «Подключение» (см. «Настройки подключения на экране» ниже). Токен не попадает в ответы API, интерфейс, журнал и логи; в БД он хранится только зашифрованным. Сообщения об ошибках содержат только код HTTP или класс сетевой ошибки. HTTP-клиент — `java.net.http.HttpClient` из JDK: проверка TLS по умолчанию, переадресации не выполняются (токен не уходит на другой хост), тайм-ауты соединения 5 с и чтения 20 с, страница ответа не больше 5 МБ, не больше 100 страниц за синхронизацию (`app.sources.website.*` в `application.yml`).

`scripts/bootstrap-demo.sh` и `scripts/bootstrap-demo.ps1` заполняют пустой `SITE_BASE_URL` адресом демонстрационного стенда `http://site-fixture:8080`, генерируют случайный `SITE_TOKEN` и поднимают сервис `site-fixture` (профиль Compose `demo`), только если `SITE_BASE_URL` указывает на этот стенд. Чтобы подключить настоящий сайт, в `.env.local` задаётся его адрес и токен; стенд тогда не запускается. Вне bootstrap-скрипта переменные по умолчанию пустые, и сайт не опрашивается.

### Настройки подключения на экране

- Таблица `source_settings` (миграция V34) — одна строка: адрес, токен, курсы и роли Moodle, адрес и токен сайта, расписание, кто и когда сохранил. Пока строки нет, действуют значения окружения (`.env.local` → `app.sources.*`). После сохранения на экране действуют сохранённые адреса, курсы, роли и расписание; токен — сохранённый на экране, а если его на экране не задавали, то из окружения. «Вернуть значения конфигурации развёртывания» (`DELETE /api/admin/source-settings`) удаляет строку вместе с токенами.
- API: `GET/PUT/DELETE /api/admin/source-settings`, `POST /api/admin/sources/{source}/check`. Только ADMIN, права проверяются в сервисе на каждый запрос. Ответ не содержит токенов: только `origin` (`NONE`, `ENVIRONMENT`, `SCREEN`, `UNREADABLE`) и время смены.
- Проверки полей на сервере: адрес — `https://` с хостом, без логина, параметров и якоря; адрес, совпадающий с адресом из окружения, принимается как есть (внутренний `http://moodle:8080` демо-стенда); курсы — целые положительные, не больше 100; роли — краткие имена `[a-z0-9_]`, хотя бы одна роль обучающихся; токен — до 500 символов без пробелов; расписание — cron Spring из шести полей по Москве, не чаще раза в 5 минут, пусто — выключено.
- Шифрование: AES-256-GCM средствами JDK (`javax.crypto`), случайный 12-байтовый IV на каждое сохранение, тег 128 бит, AAD `source-settings:<ИСТОЧНИК>:token` (токен Moodle нельзя подставить в поле сайта). Ключ — отдельная переменная `SOURCES_SETTINGS_KEY` (`app.sources.settings-key`, 32 байта в Base64), не ключ модуля «Слушатели»: тот выключен вне демо и связан с ротацией анкет. Без ключа адреса, курсы и расписание сохраняются, а токен на экране — нет (400); неверная длина ключа останавливает запуск backend. Токен, который не расшифровывается текущим ключом (ключ сменили), не используется: источник считается не настроенным, экран просит задать токен заново.
- «Проверить связь» — пробный вызов по значениям формы без сохранения: Moodle — `core_course_get_courses_by_field` по списку курсов (ответ называет найденные курсы или перечисляет недоступные), сайт — первая страница `GET /api/crm/records?updated_since=<сейчас>`. Пустой токен в форме заменяется действующим. Ошибка связи возвращается как `ok=false` с тем же понятным текстом, что у запуска синхронизации.
- Сохранение и сброс пишутся в журнал администратора (`SOURCE_SETTINGS_CHANGED`, категория «Синхронизация источников»): что изменилось — адреса, курсы, роли, расписание — и «токен … заменён», без значений токенов.
- Сервисы синхронизации читают настройки из хранилища при каждом запуске, а плановое расписание перестраивается сразу после сохранения (`SourceSyncScheduling`), поэтому перезапуск backend не нужен. Тайм-ауты, пределы ответа и число страниц по-прежнему задаются в `application.yml`.

## Синхронизация

1. Администратор нажимает «Запустить синхронизацию» (`POST /api/admin/sources/WEBSITE/sync`, CSRF). Сервер проверяет роль ADMIN, что источник настроен и что нет активного запуска, пишет `sync_runs` в `PENDING` и отдаёт задачу ограниченному исполнителю: 1 поток и очередь на 1 задачу (`app.sources.slots`, `app.sources.queue-capacity`). HTTP-поток сайт не опрашивает. Ответ `202 {runId}`; второй запуск того же источника — `409 SYNC_ALREADY_RUNNING`, переполненный исполнитель — `503 SYNC_CAPACITY_EXCEEDED`.
2. Исполнитель условным `UPDATE … WHERE status = 'PENDING'` переводит запуск в `RUNNING` и запоминает `updated_since`.
3. Адаптер читает **все** страницы до первого изменения данных. Ошибка HTTP, неверный токен (`401/403`), тайм-аут, некорректный JSON, нарушение пагинации или лимитов — запуск `FAILED` с кодом `SOURCE_UNAVAILABLE`, `SOURCE_UNAUTHORIZED` или `SOURCE_INVALID_RESPONSE`. Ни одна запись при этом не меняется, метка `updated_since` не сдвигается, прежние заявки и взаимодействия остаются (NFR-06: ошибка источника не заменяет данные нулями).
4. Каждая запись применяется в своей транзакции (`SiteRecordApplier`), поэтому ошибка одной записи не откатывает другие:
   - записи без `externalId`, `type` или `updatedAt` не сохраняются (нечем их однозначно ключевать) и считаются в `failed`, их число пишется в сообщение запуска;
   - такая же версия уже применённой или пропущенной записи (`updatedAt` не новее) — `skipped`, данные не меняются: повтор синхронизации не дублирует события и не увеличивает спрос;
   - более поздний `updatedAt` заменяет прежнюю версию той же строки `source_records`;
   - запись в `NEEDS_MAPPING` или `FAILED` с тем же `updatedAt` применяется заново: вдруг сопоставление уже появилось.
5. После всех записей запуск становится `SUCCEEDED` со счётчиками, затем `updated_since` сдвигается на наибольший `updatedAt` полученных записей (по часам сайта, не CRM). Записи на границе придут повторно и будут пропущены.
6. При старте приложения незавершённые запуски прошлого процесса получают `FAILED SYNC_INTERRUPTED`. Непредвиденная ошибка — `FAILED SYNC_FAILED`, подробности только в журнале сервера.
7. Плановый запуск: расписание `SOURCES_SYNC_CRON` (`app.sources.sync-cron`, cron Spring из шести полей по Москве, `-` отключает; демо-стенд — каждый час) ставит те же запуски в тот же исполнитель для каждого настроенного источника от имени активного администратора, который последним запускал этот источник. Источник, который никто ещё не запускал, по расписанию не синхронизируется; занятый источник или исполнитель пропускает очередной плановый запуск с записью в журнале сервера. На демо-стенде первый запуск обоих источников делает `backend-bootstrap` от имени `admin` (`docs/deploy.md`, раздел «Демо-Moodle»).

Счётчики: `created` — новая запись применена; `updated` — известная запись применена в новой версии; `skipped` — повтор версии, отозванная заявка на обучение, неизвестный тип; `needsMapping` — нет вуза или программы; `failed` — нарушение контракта или ошибка применения.

## Применение записи

Вуз ищется по порядку: сопоставление администратора → `organizations.external_key` равен внешнему ID → точное совпадение названия. Организации по данным сайта не создаются: неизвестный вуз — `NEEDS_MAPPING` с причиной «Вуз «…» (внешний ID …) не сопоставлен». Запись без организации — `FAILED`.

Программа (если указана): сопоставление → единственная активная программа с точно таким названием. Не найдена или неоднозначна — `NEEDS_MAPPING`. Продукт (если указан) берётся, только если ровно один активный продукт с таким названием; иначе он остаётся только в тексте события.

**`partnership_request`** (ФТ5, «в существующий или новый workflow»):

- существующее взаимодействие: то, к которому уже применялась прежняя версия этой заявки; иначе последнее изменённое взаимодействие вуза с той же программой, а без программы — с тем же продуктом, а без обоих — взаимодействие вуза без программы и продуктов. Отдельного статуса «закрыто» в модели нет, поэтому кандидатом считается любое взаимодействие вуза с этими признаками;
- если кандидата нет, создаётся новое взаимодействие «Заявка с сайта: <программа | продукт | партнёрство>» по базовому шаблону (`InteractionService.createSourceInteraction` → тот же `startInteraction` и снимок этапов, что у ручного создания и импорта) с программой, продуктом и контактом;
- во взаимодействие добавляется событие `COMMENTED` на текущем этапе: «Заявка с сайта: <текст>» (для новой версии — «Заявка с сайта обновлена: …»), внешний ID, статус на сайте, дата подачи по Москве, программа, продукт, контакт. Версия карточки увеличивается, поэтому открытая у КАМ карточка при следующем сохранении получит обычный `409` и предложение обновить;
- контакт ищется в вузе по email (без учёта регистра), без email — по точному ФИО; обезличенные контакты не учитываются; если его нет, создаётся и привязывается к взаимодействию. Если совпал контакт с ограниченной обработкой ПДн, заявка применяется без привязки контакта: дубль не создаётся, в комментарии вместо данных контакта — «обработка персональных данных ограничена, данные не перенесены», в `source_records.error` — пояснение «Контакт заявки не привязан: обработка его персональных данных ограничена» (`docs/roles.md`, «Безопасность и персональные данные»);
- автор события — администратор, запустивший синхронизацию; ответственный — текущий КАМ вуза. Этап не меняется: внешний JSON не выполняет переходов и не меняет роли;
- у каждой применённой версии своя запись `command_idempotency_records` (`APPLY_SOURCE_RECORD`, ключ из id записи и `updatedAt`), на неё ссылается событие.

**`learning_application`** не создаёт workflow на обучающегося. Запись в `APPLIED` с вузом, программой (или без неё) и `applicationsCount` (по умолчанию 1) пополняет спрос. Отозванная (`withdrawn`) — `SKIPPED` с причиной и в спросе не учитывается. Поскольку строка одна на внешний ID, исправление и отзыв заменяют прежнее значение, а не прибавляются.

## Оплаченные заявки (`paid_order`)

Формат — массив «Данные оплат» организатора (схема `OrdersV1` в `docs/integrations/site-api.yaml`), разбор — `PaidOrderParser` (`docs/enrolment.md`, раздел «Разбор оплат»). Один разбор принимает оба входа:

- **Файл оператора зачисления.** Раздел «Зачисление» → «Загрузка оплат» (`POST /api/enrolment/paid-orders`, multipart, CSRF, `Idempotency-Key`). Пока модуль «Слушатели» выключен (`MODULE_ENROLMENT_ENABLED=false`, по умолчанию), раздела нет и метод отвечает `404` всем: оплаты приходят только синхронизацией сайта. Во включённом модуле метод доступен только профилю USER или LEADER с флагом «Оператор зачисления»; флаг читается из БД при каждом запросе, остальным — `403 FORBIDDEN`, в том числе ADMIN. Сервер создаёт запуск источника «Сайт» с `run_trigger = UPLOAD` и автором-оператором и выполняет его в том же запросе: второй активный запуск сайта — `409 SYNC_ALREADY_RUNNING`. Ответ — протокол: получено, пустых элементов, создано, изменено, без изменений, требуют сопоставления курса, не принято, потоки файла (курс, номер, заявок) и замечания по элементам без значений ПДн. Повтор с тем же ключом возвращает прежний протокол.
- **Ответ сайта.** Если `GET /api/crm/records` вернул JSON-массив, адаптер разбирает его тем же `PaidOrderParser` и применяет в том же запуске (вручную, по расписанию). Метка `updated_since` для массива не сдвигается: в формате нет `updatedAt`. Запуск из карточки вуза записи оплат не применяет.

Запись в `source_records`:

| Поле | Значение |
|---|---|
| `record_type`, `external_id` | `paid_order`, «Номер заявки» (уникальность — существующий ключ `source, record_type, external_id`) |
| `payload` | только `externalId`, `type`, момент получения, служебная организация, `program.name` = «Курс», `streamNo`, `payloadHash`. Фамилии, имени, отчества, телефона и email нет |
| `organization_id` | «Открытый набор (физлица)», находится по `external_key = open-enrolment` без ручного сопоставления |
| `program_id` | PROGRAM-сопоставление курса (ключ `name:<курс>`) или единственная активная программа с тем же нормализованным названием; иначе `NEEDS_MAPPING` «Курс «…» не сопоставлен с программой CRM» |
| `stream_no`, `payload_hash` | номер потока и SHA-256 от курса и номера потока |
| `external_updated_at`, `submitted_at` | момент первого получения; при замене записи не меняются. Период DEMAND к оплатам не применяется |

Версия записи — `payload_hash`: та же версия — «Пропущено», другой курс или поток — запись заменяется («Изменено»), запись `NEEDS_MAPPING` или `FAILED` с той же версией применяется заново. Отсутствие заявки в следующем файле отзывом не считается. Ошибки номера заявки, курса или номера потока не дают записи; ошибки ФИО, телефона и email — предупреждения, запись принимается. Пустые элементы и повторы номера в файле не падают: счётчики — в протоколе и в сообщении запуска.

Запуск `UPLOAD` виден администратору в «Истории запусков» сайта («загрузка файла оплат оператором зачисления», автор — оператор) и в журнале администратора («Сайт: загрузка файла оплат»), но не считается полной синхронизацией сайта: не меняет «последнюю успешную синхронизацию», пометку «данные устарели», первый запуск при старте и строку состояния карточек. Файл на сервере не сохраняется.

Разбор: запись `paid_order` в «Записях для разбора» показывает тип «Оплаченная заявка (сайт)», служебную организацию, курс и номер потока. Администратор выбирает только программу («Сопоставить и применить»); сопоставление организации для оплат отклоняется `400` с полем `organizationId`. Сопоставление курса применяется ко всем записям этого курса.

В той же транзакции записи модуль «Слушатели» принимает ФИО, телефон и email в зашифрованную анкету: поток по курсу и номеру, слушатель по отпечаткам и ФИО, зачисление со ссылкой на запись. Шаг выполняется и для «Пропущено», и для «Требует сопоставления», поэтому повторная загрузка достраивает недостающие зачисления, а оплата курса, который администратор сопоставит позже, уже зачислена. При синхронизации сайта шаг выполняет служебный актор «Система» (событие `LEARNERS_SYNCED`), инициатор запуска видит только счётчики. Пока модуль выключен, шаг не выполняется и персональные данные оплат отбрасываются. Правила — `docs/enrolment.md`, раздел «Приём оплат в модуль».

## Разбор записей администратором

Раздел `#/admin` → «Источники данных»:

- состояние источников: настроен ли, последняя успешная синхронизация, метка `updated_since`, последний запуск со статусом и счётчиками, код и текст ошибки, число записей для разбора; пока запуск активен, экран опрашивает состояние раз в 2 секунды;
- «Запустить синхронизацию» — неактивна, если источник не настроен или запуск уже идёт; причина показана рядом;
- «Записи для разбора» — до 200 последних записей `NEEDS_MAPPING` и `FAILED`: тип, внешний ID, вуз и программа на сайте, причина. Для записи без вуза нужно выбрать вуз CRM из списка, для ненайденной программы можно выбрать программу. «Сопоставить и применить» (`POST /api/admin/source-records/{id}/apply`) сохраняет сопоставление, применяет запись заново и повторяет до 500 других записей `NEEDS_MAPPING` того же источника: одна привязка «Университет Д» → организация закрывает все его заявки. Для `FAILED` кнопка называется «Применить повторно». Повторный запрос безопасен: уже применённая запись не меняется. Для курса или группы Moodle вместо данных сайта показаны название и краткое имя курса, а вуз и программа обязательны оба.

Для записи сайта без вуза можно не сопоставлять, а создать организацию: «Вуза нет в CRM — создать организацию» (`POST /api/admin/source-records/{id}/organization`, название по умолчанию — из заявки, команда обязательна). Организация создаётся без ответственного («Требует назначения»), сопоставление сохраняется, заявка и другие заявки того же вуза применяются заново. Название, которое уже есть в CRM, отклоняется `400` с полем `name`: нужно сопоставить с существующей организацией.

Для курса или группы Moodle выбирается и вид потока: «Занятия студентов» (по умолчанию) или «Обучение преподавателей». Поток обучения преподавателей не входит в «Обучающихся» ни в карточке, ни в отчёте DEMAND и показывается в карточке отдельно.

Списки для выбора — `GET /api/admin/source-mapping-options` (все организации и активные программы; ADMIN не получает бизнес-доступа к карточкам, но сопоставление источников — административная настройка). Все эндпоинты `/api/admin/sources*` и `/api/admin/source-*` проверяют роль ADMIN на сервере, иначе `403`.

## Расписание, устаревание и уведомление о сбое

- У каждого настроенного источника экран показывает плановую синхронизацию человеческим текстом («каждый час в 00 мин. (МСК)») и время следующего запуска (`DataSource.schedule`, `nextRunAt`, вычисляется по расписанию из блока «Подключение»; начальное значение — `SOURCES_SYNC_CRON`). Если по источнику ещё не было запуска администратора, следующий плановый запуск не назначен, и экран это объясняет.
- Экран источников, баннер и первая загрузка при старте демо-стенда учитывают только полные запуски (вручную, по расписанию, первая загрузка). Запуск из карточки обновляет один вуз, поэтому не скрывает сбой полного запуска, не сбрасывает «данные устарели» и не отменяет первую загрузку; в истории запусков он виден, а строку состояния своей карточки обновляет.
- «Данные устарели» — у настроенного источника нет успешной синхронизации дольше порога `SOURCES_STALE_AFTER` (`app.sources.stale-after`, по умолчанию 26 ч; в `.env.example` — 3 ч под часовое расписание демо-стенда). Пометка видна на экране источников и в строке состояния карточки.
- Уведомление администратору: в начале раздела «Администрирование» баннер «Синхронизация «…» завершилась ошибкой <время>: <причина>. Данные в CRM не изменены; последняя успешная синхронизация — …» (и отдельно — об устаревших данных) с переходом к источникам. Баннер строится по `GET /api/admin/sources` при открытии раздела и раз в минуту, пока раздел открыт; он исчезает после следующего успешного запуска. Почта и мессенджер не подключены (решение в базе знаний).
- «История запусков» у каждого источника (`GET /api/admin/sources/{source}/runs`, последние 50): время, кто и как запустил (вручную, по расписанию от имени администратора, из карточки с названием вуза, первая загрузка), статус, счётчики и ошибка.

## Сохранённые сопоставления

Раздел «Сохранённые сопоставления» на экране источников (`GET /api/admin/source-mappings`, только ADMIN) — все сопоставления: курс или группа Moodle → вуз, программа, даты и вид потока, число участий и время наблюдения снимка; вуз сайта → организация; программа сайта → программа. У каждой строки — кто и когда последним изменил, пометки «поток завершён» и «нет в Moodle при последней синхронизации» (снимок старше последней полной успешной синхронизации — курс убран из `MOODLE_COURSE_IDS` или группа удалена).

- «Изменить» (`PUT /api/admin/source-mappings/{id}`, в теле `version`): для потока — вуз, программа, даты и вид; для вуза или программы сайта — цель. Устаревшая версия — `409 VERSION_CONFLICT` с `currentVersion`, список перечитывается. Версию увеличивает любое изменение сопоставления, в том числе «Сопоставить и применить» в «Записях для разбора». Перенос потока на другой вуз или программу пересчитывает его снимок (снимок остаётся потоку, взаимодействие выбирается заново), смена цели сайта пересопоставляет уже применённые заявки.
- «Снять» (`DELETE …?version=`): поток удаляется вместе со снимком, последний поток курса или группы возвращает запись в «Записи для разбора»; снятое сопоставление сайта возвращает заявки в разбор, и повторное сопоставление не дублирует события.
- «Добавить поток» (`POST /api/admin/source-mappings/{id}/runs`): новый поток того же курса или группы с другими датами (например, для нового цикла работы). Потоки одного курса не пересекаются по датам — иначе `400` с полем `runStartsOn`. Каждый поток публикует свой снимок и относится к работе того цикла, в который попадает его дата начала (раздел «Циклы» в `docs/workflow.md`).
- «Удалить снимок» (`DELETE /api/admin/source-mappings/{id}/snapshot`): убирает снимок из карточек и отчётов, сопоставление остаётся. Если поток ещё идёт, а курс или группа есть в Moodle, снимок появится снова при следующей синхронизации.

## Заявки, ожидающие разбора, у руководителя и КАМ

`GET /api/source-records` (раздел «Вузы», панель «Заявки источников, ожидающие разбора»): до 200 записей сайта в `NEEDS_MAPPING` или `FAILED` с причиной, датой подачи, вузом и программой на сайте.

- КАМ видит заявки своих вузов, руководитель — вузов команды и заявки вузов, которых ещё нет в CRM. Вуз заявки — сохранённый в записи, а если его нет — найденный тем же порядком, что и при применении (сопоставление, внешний ID, название). Заявка вуза, уже сопоставленного с организацией другой команды, руководителю не видна, даже если её применение упало: запись `FAILED` хранит найденный вуз. Область — тот же `OrganizationRepository.visibilityScope`; чужая запись — `404`.
- Руководитель сопоставляет заявку с организацией команды (`POST /api/source-records/{id}/resolve`, организация проверяется по области) или создаёт организацию из заявки (`POST /api/source-records/{id}/organization`): она создаётся в его команде без ответственного («Требует назначения»), заявка и другие заявки того же вуза применяются заново. КАМ список только видит: программы сопоставляет администратор, новые вузы — руководитель (`403 FORBIDDEN`).
- Записи `paid_order` в этот список не попадают: организация у них служебная, а курс с программой сопоставляет администратор.
- Уже сопоставленная кем-то запись или вуз, для которого сопоставление уже есть, — `409 CONFLICT` «Запись уже сопоставлена с организацией». Сопоставление из заявки только добавляется и никогда не перезаписывает существующее: одновременные запросы отсекает уникальный индекс `source_mappings_reference_key`, создание организации идёт под блокировкой записи.

## Строка состояния и обновление источников в карточке

Блок «Обучение (LMS)» карточки начинается со строки состояния (`GET /api/interactions/{id}/source-status`): «LMS: обновлено <время>» и «Сайт: обновлено <время>» по последней успешной синхронизации, затронувшей вуз карточки; после неё — «ошибка источника <время>: <причина>; данные на <время наблюдения снимков>», пометка «данные устарели» или «не подключён в конфигурации CRM».

Если снимков нет, вместо общего текста показана точная причина: программа не указана; LMS не подключена; курсы не сопоставлены; потоки программы относятся к другому циклу; у потока нет дат; последняя синхронизация LMS завершилась ошибкой; поток закончился до первого наблюдения; курсы сопоставлены, но ещё не синхронизированы.

«Обновить данные источников» (КАМ и руководитель, `POST /api/interactions/{id}/sources/refresh`) обновляет оба источника по сопоставлениям карточки без участия администратора и возвращает результат по каждому: LMS — как прежний эндпоинт `learning-snapshots/sync` (только курсы, сопоставленные с вузом и программой карточки); сайт — запрос изменений с общей метки `updated_since` и применение только записей, которые относятся к вузу карточки. Метка сайта при этом не сдвигается, поэтому заявки других вузов дождутся общего запуска. В предложенном контракте нет отбора по вузу, поэтому отбор выполняет CRM после получения страницы. Ошибка одного источника не мешает другому, прежние данные сохраняются; запуск пишется в историю с отметкой «из карточки» и вузом.

## Отчёт DEMAND «Востребованность программ»

Правила отчёта — в `docs/reports.md`, раздел «Отчёт DEMAND». Кратко: строка — ИТ-программа, колонки «Заявки (сайт)», «Оплаченные заявки (сайт)», «Потоки с оплатами (сайт)», «Обучающиеся (Moodle)», «Параллельные потоки (Moodle)», сортировка по выбранному показателю, без единого индекса. Заявки считаются только по вузам в области текущего профиля и только по записям `learning_application` в статусе `APPLIED`; `NEEDS_MAPPING`, отозванные и заявки вузов на партнёрство не входят. Колонки Moodle берутся из последних снимков потоков обучения — курсов и групп, сопоставленных с датами (раздел «Moodle»); параллельные потоки — потоки, которые идут на последний день периода или, если он не задан, на день формирования. У программы без снимков колонки Moodle — «нет данных», а не 0.

## Moodle

Требования: FR-09 и ФТ5 ТЗ в части LMS. Moodle подключён только на чтение: адаптер отдаёт агрегаты без персональных данных учащихся, а данные о ходе обучения попадают в workflow тем же способом, что и заявки сайта. Контракт Moodle Web Services REST — общий для Moodle, а не предложенный CRM; проверен на Moodle 4.5.4 (`bitnamilegacy/moodle:4.5.4-debian-12-r0`).

### Настройка

| Переменная `.env.local` | Свойство backend | Смысл |
|---|---|---|
| `MOODLE_BASE_URL` | `app.sources.moodle.base-url` | адрес Moodle, совпадающий с его `wwwroot` (на переадресацию адаптер отвечает ошибкой) |
| `MOODLE_TOKEN` | `app.sources.moodle.token` | токен ограниченного внешнего сервиса |
| `MOODLE_COURSE_IDS` | `app.sources.moodle.course-ids` | разрешённые курсы через запятую; другие курсы CRM не запрашивает |

В `application.yml` заданы начальные роли обучающихся (`student-roles: student`) и преподавателей (`teacher-roles: editingteacher,teacher`) по коротким именам ролей курса, тайм-ауты соединения 5 с и чтения 20 с, предел ответа 5 МБ. Источник считается настроенным, только когда заданы адрес, токен и хотя бы один курс. Адрес, токен, курсы и роли администратор меняет в «Источники данных» → «Подключение» без перезапуска backend, там же проверяет связь; переменные выше — начальные значения («Настройки подключения на экране»). Токен в ответы API, интерфейс и журнал не попадает, в БД хранится зашифрованным.

Каждый вызов — `POST {MOODLE_BASE_URL}/webservice/rest/server.php` с формой `wstoken`, `wsfunction`, `moodlewsrestformat=json` и параметрами функции. Токен передаётся только в теле запроса, в URL его нет. Moodle сообщает об ошибке ответом HTTP 200 с объектом `{"exception","errorcode","message"}`, поэтому каждый ответ проверяется на это поле. Ошибки доступа (`invalidtoken`, `accessexception`, `nopermissions`, `accessdenied`, `requireloginerror`, `errorcoursecontextnotvalid`, `cannotviewreport`, `usernotfullysetup`, `servicerequireslogin`, HTTP 401/403) — код запуска `SOURCE_UNAUTHORIZED`; недоступность, тайм-аут, HTTP ≠ 200 и переадресация — `SOURCE_UNAVAILABLE`; прочие ошибки Moodle, неверная форма JSON, курс из списка, которого Moodle не вернул, — `SOURCE_INVALID_RESPONSE`. В сообщение попадают имя функции и `errorcode`, но не текст запроса.

### Сервис и права в Moodle

`scripts/moodle-demo.sh` настраивает локальный Moodle через `infra/moodle/demo-setup.php`; для Moodle заказчика те же шаги выполняет его администратор в «Администрирование → Сервер → Веб-службы»:

1. Включить веб-службы и протокол REST.
2. Создать пользователя сервиса (`crm-ws`, способ входа — ручной, пароль не используется) и системную роль (`crmwsreader`) только с правами из таблицы; назначить роль пользователю в контексте системы.
3. Создать внешний сервис (`crm_readonly`) «только для авторизованных пользователей», добавить в него четыре функции и авторизовать только `crm-ws`; выпустить постоянный токен этого пользователя для сервиса.

Роль содержит ровно семь прав. Что происходит без каждого из них, проверено на Moodle 4.5.4 снятием права по одному:

| Право | Для чего | Без него |
|---|---|---|
| `webservice/rest:use` | протокол REST | ни один вызов не проходит |
| `moodle/course:view` | вход в курс без зачисления | курсы приходят без `enablecompletion`, группы и участники — `errorcoursecontextnotvalid`, запуск `FAILED` |
| `moodle/course:enrolreview` | `core_enrol_get_enrolled_users` с `onlyactive=1` (этого права Moodle достаточно и для списка участников, `moodle/course:viewparticipants` не нужен) | `nopermissions`, запуск `FAILED` |
| `moodle/course:managegroups` | `core_group_get_course_groups` требует именно его; изменить группы токен не может — функций записи в сервисе нет | `nopermissions`, запуск `FAILED` |
| `moodle/site:accessallgroups` | участники курсов в режиме раздельных групп и поле `groups` | Moodle молча возвращает пустой список участников, статус завершения — `accessdenied`. Пустой список при наличии групп адаптер считает ошибкой доступа, чтобы не опубликовать ноль |
| `moodle/user:viewdetails` | Moodle отдаёт участника только при праве видеть его профиль | в списке остаются только контакты курса (преподаватель): обучающиеся молча пропадают. Адаптер этого отличить не может, поэтому право обязательно, а число обучающихся сверяется со страницей «Участники» курса при подключении |
| `report/completion:view` | статус завершения чужого пользователя | `cannotviewreport`, запуск `FAILED` |

Функции сервиса: `core_course_get_courses_by_field` (`field=ids`) — название, краткое имя, `enablecompletion`; `core_group_get_course_groups` — группы; `core_enrol_get_enrolled_users` (`onlyactive=1`, `userfields=id,roles,groups`) — активные зачисления, роли в курсе, группы; `core_completion_get_course_completion_status` — завершил ли участник курс. Функция вне сервиса отвечает `accessexception`.

`userfields=id,roles,groups` отсекает email и прочие поля профиля, но полное имя (`fullname`) Moodle 4.5 отдаёт всегда; адаптер читает из ответа только `id`, `roles` и `groups`, имя нигде не сохраняется. `idnumber` курса Moodle отдаёт только с правом `moodle/course:update`, поэтому адаптер его не запрашивает; подсказкой для сопоставления служит краткое имя курса.

### Что считается

Для каждого курса из `MOODLE_COURSE_IDS`: одно чтение курсов, затем группы, участники и — только если в курсе включено отслеживание завершения — статус завершения по каждому обучающемуся (N + 2 запроса на курс плюс один общий, последовательно на одном потоке синхронизации). В курсе с выключенным отслеживанием Moodle на `core_completion_get_course_completion_status` отвечает `cannotviewreport`, поэтому для таких курсов функция не вызывается. Все курсы читаются до первого изменения данных.

| Показатель | Правило |
|---|---|
| `participants` | активные зачисления (`onlyactive=1`) с ролью из `student-roles`; приостановленное зачисление не считается |
| `teachers` | активные зачисления с ролью из `teacher-roles` |
| `completed`, `notCompleted` | `completionstatus.completed` = `true`/`false`; если в курсе отслеживание выключено (`enablecompletion=0`) или не задано ни одного условия (`nocriteriaset`), оба значения `null` — «нет данных», а не 0 |
| `unknown` | обучающиеся без известного статуса: все при выключенном отслеживании, отдельные — при `usernotenroled`/`notenroled` |
| `groupsCount` | группы курса, в которых есть хотя бы один обучающийся; число групп не равно числу потоков |

Снимок группы считает её членов по тем же правилам. Идентификаторы пользователей Moodle живут только в памяти одного запуска. Email, оценки и ответы учащихся не запрашиваются; ФИО (`fullname`) Moodle отдаёт вместе со списком участников и контактами курса, адаптер их отбрасывает при разборе и нигде не хранит. `source_records.payload` Moodle-записи содержит только названия курса и группы и числа.

Завершение курса в Moodle не равно аттестации, а дата наблюдения — не дата завершения.

### Сопоставление курса или группы

Каждый курс даёт запись `moodle_course` (внешний ID — номер курса), каждая группа — `moodle_group` (`курс:группа`). Администратор в «Источниках данных» выбирает для записи вуз, программу, первый и последний день потока — все поля обязательны; сопоставление хранится в `source_mappings` (`COURSE` или `GROUP`) и является подтверждённым потоком обучения (TrainingRun) с интервалом `[run_starts_on, run_ends_on)`: интерфейс передаёт в `runEndsOn` день после последнего дня потока, сервер проверяет, что окончание позже начала (`400 VALIDATION_ERROR`, поля `runStartsOn`, `runEndsOn`). Автоматического сопоставления по названию нет: курс не сопоставлен, пока администратор явно не выбрал вуз, программу и даты.

- Курс, сопоставленный целиком, — один поток и один снимок; его группы получают `SKIPPED` («Курс сопоставлен целиком одним потоком; учащиеся группы учтены в нём») и отдельными потоками не считаются.
- Наблюдение относится к потоку, чей интервал `[начало, окончание)` содержит дату наблюдения (по Москве). До начала первого потока наблюдение относится к ближайшему будущему потоку. Между потоками (прошлый закончился, следующий ещё не начался) запись получает `SKIPPED` с причиной «между потоками», снимки не меняются и событие не пишется: состав прошлого потока не попадает в карточку нового цикла.
- Поток закрыт, когда дата наблюдения (по Москве) не раньше `run_ends_on`. Снимок закрытого потока больше не обновляется и событие не пишется: остаётся последнее наблюдение до окончания, текущий состав переиспользованного курса к нему не относится. Если поток закончился до первого наблюдения, запись получает `SKIPPED` с объяснением и снимка нет — в отчёте «нет данных».
- Сопоставление без дат (сохранённое до миграции V15) снимок не публикует: запись возвращается в `NEEDS_MAPPING` с причиной «Не указаны даты потока», прежний снимок в отчёт не попадает, пока администратор не сопоставит запись заново с датами. Демо-bootstrap добавляет даты к своим демо-сопоставлениям сам.
- Смешанный курс (группы разных вузов) сопоставляется по группам: каждая сопоставленная группа публикует свой снимок, сам курс получает `SKIPPED`, несопоставленные группы остаются в разборе.
- Курс целиком и его группы одновременно не сопоставляются: вторая попытка отклоняется `400 VALIDATION_ERROR`. Проверка выполняется под блокировкой строки курса в `source_records` (`SELECT … FOR UPDATE`), поэтому два одновременных запроса — на курс и на его группу — не проходят её оба. Одни и те же учащиеся не попадают в отчёт дважды.
- Пока ничего не сопоставлено, курс и его группы — `NEEDS_MAPPING`; после выбора вуза и программы запись применяется сразу, соседние записи источника применяются повторно. Причина `NEEDS_MAPPING` не повторяет названия курса и группы (они показаны рядом), поэтому длинные названия Moodle не переполняют поле `error` (500 символов); более длинный текст ошибки обрезается при сохранении. Название курса хранится до 1333 символов — предел Moodle.
- Запись `FAILED` (например, нет шаблона процесса по умолчанию или конфликт версии взаимодействия) применяется кнопкой «Применить повторно» без нового выбора: запрос без вуза и программы использует сохранённое сопоставление, а если его нет, запись возвращается в `NEEDS_MAPPING`. Для записи `NEEDS_MAPPING` вуз и программа обязательны.

### Публикация снимка и событие в workflow (ФТ5)

1. Синхронизация читает все разрешённые курсы. Любая ошибка — запуск `FAILED`, ни одна запись, ни один снимок и ни одно взаимодействие не меняются: в CRM остаётся последняя полная публикация.
2. Для сопоставленного курса или группы числа сравниваются с предыдущим снимком. Первый снимок или изменившиеся числа (или сопоставление) — в `learning_snapshots` пишется новый снимок с `changed_at` и в историю взаимодействия добавляется событие `COMMENTED`:

   > Данные LMS: курс «Демо: Java-разработчик», обучающихся 6, завершили 3, не завершили 3, статус неизвестен 0, групп 2, преподавателей 1. Наблюдение 24.09.2026 18:40 (МСК)

   При выключенном отслеживании завершения — «завершили: нет данных (завершение курса в Moodle не отслеживается)»; у группы вместо числа групп указано её название.
3. Взаимодействие: то, в которое уже писались данные этого курса или группы; иначе последнее изменённое взаимодействие вуза с той же программой; иначе новое «Обучение в LMS: <курс>» с этой программой по базовому шаблону (`InteractionService.createSourceInteraction`, как у заявок сайта). Автор события — администратор, запустивший синхронизацию; ответственный — текущий КАМ вуза; этап не меняется. У каждой публикации своя запись `command_idempotency_records` (`APPLY_SOURCE_RECORD`, ключ из записи и времени наблюдения).
4. Числа не изменились — события нет, у снимка обновляется только `observed_at`. Повторная синхронизация не удваивает ни снимки, ни события.
5. История наблюдений (`learning_observations`): вместе со снимком пишется строка истории с ключом «поток + `changed_at` снимка». Изменились числа — новая строка (`observed_from` = время наблюдения), как и событие; одинаковые подряд наблюдения новой строки не дают, у последней строки обновляется только `confirmed_at`. Строка хранит те же агрегаты, что снимок, без идентификаторов и имён учащихся. «Удалить снимок» и изменение потока, при котором снимок удаляется, удаляют и историю потока; перенос потока на другой вуз или программу переносит историю вместе с ним (вуз и программа берутся из сопоставления).

Счётчики запуска для Moodle: `fetched` — курсы и группы; `created` — первый снимок; `updated` — изменившийся снимок; `skipped` — числа не изменились или запись не публикуется по правилу выше; `needsMapping` — курс или группа без сопоставления.

Адаптер и права роли `crmwsreader` проверены на настоящем Moodle 4.5.4: сохранённые ответы Moodle используются как фикстуры автотестов (`backend/src/test/resources/ru/rtk/crm/source/moodle/`), а тест `SourceSyncServiceTest.liveMoodleMatchesDemoDataAndKeepsPublicationOnRepeatAndFailure` при заданных `MOODLE_TEST_URL`, `MOODLE_TEST_TOKEN`, `MOODLE_TEST_COURSE_IDS` прогоняет полный конвейер (чтение → сопоставление → снимки, включая повтор и ошибку токена) против настоящего сервера; без этих переменных тест пропускается.

### Карточка и отчёт

- Карточка взаимодействия — блок «Обучение (LMS)»: последние снимки курсов и групп, сопоставленных с тем же вузом и программой, что у взаимодействия (`GET /api/interactions/{id}/learning-snapshots`). Взаимодействие проверяется по области видимости в том же запросе; чужое — `404`. Без программы блок объясняет, что данные не сопоставляются.
- Строка состояния источников, точная причина отсутствия данных и кнопка «Обновить данные источников» — раздел «Строка состояния и обновление источников в карточке» выше; прежний эндпоинт LMS сохранён.
- Кнопка «Обновить данные LMS» (прежний эндпоинт) (КАМ и руководитель, `POST /api/interactions/{id}/learning-snapshots/sync`): сервер проверяет область видимости (чужая карточка и администратор — `404`) и право вести карточку, берёт из `source_mappings` только курсы и группы, сопоставленные администратором с вузом и программой карточки, и только из `MOODLE_COURSE_IDS`, читает из Moodle эти курсы и применяет только единицы, сопоставленные с этой парой вуз–программа, — группы того же курса, сопоставленные с другим вузом, не трогаются. Запуск пишется в `sync_runs` от имени пользователя и подчиняется тому же правилу одного активного запуска (`409 SYNC_ALREADY_RUNNING`); выполняется в потоке запроса, потому что читает один-два курса. Токен остаётся на сервере. Изменившийся снимок добавляет событие «Данные LMS» от имени пользователя; без изменений — только новое время наблюдения. Нет сопоставления или программы — `409 LMS_NOT_MAPPED`, ошибка Moodle — `502 LMS_SYNC_FAILED`, прежний снимок сохраняется. Проверки: `SourceSyncServiceTest.cardRefreshReadsOnlyCoursesMappedToVisibleInteraction`, `wave2-smoke.mjs` (фаза `lms-card`, на 360 px — с клавиатуры).
- Блок «Обучение (LMS)» показывает у каждого снимка «Поток обучения: с … по …» (последний день — `runEndsOn` минус один день) или «даты не подтверждены администратором».
- Потоки вида «Обучение преподавателей» показаны в блоке отдельным списком «Обучение преподавателей (LMS)»: записано, завершили, даты, наблюдение. Ручные записи о повышении квалификации — блок «Обучение преподавателей» (`docs/workflow.md`).
- Когда у потока «Обучение преподавателей» этой же работы есть число завершивших, а этап «Обучение преподавателей» или «Повышение квалификации» в маршруте этой работы ещё не пройден и не отмечен вручную, в разделе «Обучение» карточки появляется предложение «Отметить этап выполненным по данным LMS» (для «Повышения квалификации» — ещё и «Запустить новый цикл»). Действие только по кнопке с явным подтверждением: подтверждение заполняет запись «Обучение преподавателей» (ручной блок) данными потока — дату, курс, число преподавателей — пользователь может их поправить, затем отмечает этап через существующую отметку этапа вне текущего или через переход, если этап текущий. Автоматически ничего не меняется. Права — как у ведения карточки (USER, LEADER); область видимости проверяется на тех же серверных эндпоинтах (`stage-completions`, `transitions`, `teacher-trainings`).
- Запись преподавателей вуза на курс ПК в LMS CRM не делает: вкладка «Преподаватели на ПК» выдаёт файл «Загрузка пользователей» для LMS-команды, импорт — у администратора LMS (`docs/enrolment.md`, «Тот же файл для преподавателей вуза»). Результат импорта виден после синхронизации: вкладка сравнивает «Передано LMS-команде» с числом записанных в потоке «Обучение преподавателей» с тем же названием курса и группы.
- Отчёт DEMAND: «Обучающиеся (Moodle)» и «Завершили (Moodle)» — по потокам занятий студентов, которые шли в периоде хотя бы один день (участия, не уникальные люди), число потока — наблюдение из истории, действовавшее на конец последнего дня периода; «Параллельные потоки (Moodle)» — число её потоков, активных на ту же дату; дата — в заголовках колонок (`docs/reports.md`).
- «Динамика обучения» (`GET /api/reports/learning-dynamics`) и «Тренд обучения» в сводке «Руководства» (`GET /api/work/learning-trend`) считаются по той же истории (`docs/reports.md`).

### Сигналы LMS

Сервис `LmsSignalService` (пакет `work`) превращает снимки в подсказки для работы. Берутся незавершённые работы (`work_status = ACTIVE`) и последние снимки потоков вида «Занятия студентов» с датами, сопоставленных той же паре вуз–программа, в окне цикла работы — те же потоки, что в блоке «Обучение (LMS)». «Сегодня» и дата наблюдения — по Москве, поток — `[run_starts_on, run_ends_on)`. Поток идёт, если дата наблюдения не раньше начала и раньше окончания, а сегодня раньше окончания.

| Сигнал | Условие | Действие |
|---|---|---|
| «В LMS появились обучающиеся» (`STUDENTS_APPEARED`) | поток идёт, обучающихся > 0, текущий этап маршрута раньше этапа `classes-stage-name` («Занятия»; нет такого этапа — нет сигнала) | кнопка «Перейти к этапу «Занятия»…» открывает обычный диалог перехода (`POST /api/interactions/{id}/transitions`); кнопка есть, только если маршрут работы разрешает переход из текущего этапа прямо к «Занятиям», иначе сигнал объясняет, что пройти промежуточные этапы или добавить переход |
| «Поток идёт, обучающихся нет» (`NO_STUDENTS`) | поток идёт, от начала до даты наблюдения больше `no-students-after-days` дней, обучающихся 0 | — |
| «Низкая доля завершивших» (`LOW_COMPLETION`) | наблюдение не раньше начала, сегодня не раньше `run_ends_on − completion-window-days` (закрыт или близок к концу), отслеживание завершения включено (`completed` не `null`), обучающихся > 0, завершили × 100 < `low-completion-percent` × обучающихся | — |

Пороги — `app.lms-signals` в `application.yml`: `classes-stage-name: Занятия`, `no-students-after-days: 14`, `low-completion-percent: 50`, `completion-window-days: 7`. Автоматических переходов нет.

Скрытие (`POST /api/interactions/{id}/lms-signals/dismissals`, USER и LEADER области работы) пишет в `lms_signal_dismissals` (миграция V31) работу, поток, вид сигнала и версию данных — время последнего изменения снимка и версию сопоставления. Новое наблюдение без изменений сигнал не возвращает; изменились числа или сопоставление — сигнал снова виден. Отметка общая для работы: скрыл КАМ — не видит и руководитель.

Где видно: рабочий стол КАМ (плитка и группа ленты), пульт руководителя (колонка по КАМ и список), вкладка «Обучение» карточки работы (включая скрытые). API: `GET /api/lms-signals` (КАМ — свои вузы, руководитель — команда, «Руководство» — все, администратор — 403), `GET /api/interactions/{id}/lms-signals` (чужая работа — 404). Проверки: `LmsSignalServiceTest`.

Демо-стенд: `infra/moodle/demo-setup.php` создаёт курсы «Демо: веб-разработка» (3 обучающихся, завершил 1) и «Демо: информационная безопасность» (без обучающихся); `scripts/moodle-demo.sh` передаёт их номера в `MOODLE_DEMO_WEB_COURSE` и `MOODLE_DEMO_EMPTY_COURSE`, а bootstrap сопоставляет оба с «Школа № 1 (демо)» (КАМ Г): веб-разработку — с программой «Демо-программа: цифровой университет», информационную безопасность — с программой «Демо-программа: анализ данных», чтобы у каждого курса была своя работа, с датами `run-started-days-ago`/`run-ends-in-days` (60/4 и 30/90 дней от дня bootstrap). Сигналы на стенде: «появились обучающиеся» у «Университет А» (курс Java), у «Университет Б» (группа Б1) и у школы; «низкая доля» и «обучающихся нет» — у школы. Если bootstrap добавил новое сопоставление на стенде, где Moodle уже синхронизировался, он сразу запускает синхронизацию Moodle.

### Ограничения

- LMS заказчика может оказаться не Moodle. Адаптер изолирован: HTTP-вызовы и разбор JSON Moodle — только в `MoodleClient`, который отдаёт `LearningUnit` (курс или группа и числа). Сопоставление, снимки, событие в workflow, карточка и отчёт работают с `LearningUnit` и от Moodle не зависят; другой LMS нужен свой клиент с тем же результатом.
- Moodle заказчика недоступен: версия, набор функций, роли и курсы не проверены.
- Плановый запуск идёт от имени последнего запускавшего источник администратора: отдельной служебной учётной записи CRM нет.
- История наблюдений начинается с миграции V30 (перенесённый последний снимок) или с первой синхронизации потока: для даты раньше первой строки истории у потока «нет данных». Между двумя строками действует более ранняя: CRM знает, когда числа изменились, но не хранит каждое промежуточное подтверждение. Для нового цикла обучения в том же курсе администратор добавляет второй поток с новыми датами («Добавить поток»).
- Демо-bootstrap дописывает к каждому демо-сопоставлению пять синтетических наблюдений (15-го числа пяти месяцев до первой строки истории, `demo = true`): первое сопоставление растёт, второе падает к реальному значению из Moodle; начало демо-потока сдвигается на первый синтетический месяц. Повторный запуск bootstrap синтетику не дублирует.
- Курс, убранный из `MOODLE_COURSE_IDS`, или удалённая в Moodle группа сохраняют последний снимок с пометкой «нет в Moodle при последней синхронизации»; администратор удаляет его кнопкой «Удалить снимок».
- `cannotviewreport` у курса с включённым отслеживанием завершения (нет `report/completion:view` или отслеживание выключено на уровне сайта) — ошибка запуска, а не «нет данных»: так видна ошибка настройки прав.
- На курс с тысячами обучающихся уходит столько же запросов статуса завершения; предел — тайм-аут чтения на каждый запрос.

## Ограничения

- Контракт сайта предложен CRM и не согласован; формат, авторизация, пагинация, статусы и удаление записей на сайте заказчика неизвестны. Удалённые на сайте записи адаптер не видит: отзыв должен приходить записью со статусом.
- В предложенном контракте сайта нет фильтра по вузу: обновление из карточки получает все изменения с общей метки и применяет только записи вуза карточки. На большом сайте это лишний трафик; фильтр `organization_external_id` стоит добавить в контракт при согласовании.
- Правило «действительной» заявки — всё, кроме `withdrawn`; это гипотеза до ответа заказчика.
- Кандидат для добавления заявки ищется по программе/продукту без статуса «закрыто» (его нет в модели).
- `source_records.payload` хранит JSON записи сайта, включая контакт представителя вуза (как и таблица контактов); у заявок на обучение контакт не сохраняется.
- Проверено на H2; на настоящем PostgreSQL и в контейнере nginx стенд не запускался.
