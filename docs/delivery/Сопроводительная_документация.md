## 1. Термины

| Термин | Значение в CRM |
|---|---|
| CRM | система управления взаимоотношениями с вузами и школами (ТЗ, раздел 1) |
| КАМ | менеджер по вузам (key account manager), роль «пользователь» по ТЗ |
| Руководитель | руководитель команды КАМ |
| Администратор | технический специалист ИТ Школы РТК, управляет доступом, справочниками и настройками |
| Вуз, организация | учебное заведение: вуз или школа |
| Взаимодействие | карточка работы с вузом по одной ИТ-программе (или без программы) и одному или нескольким ИТ-продуктам; проходит этапы процесса |
| Этап | шаг процесса взаимодействия (в ТЗ — «статус»), например «Встреча» или «Подписание» |
| Шаблон процесса (workflow) | упорядоченный набор этапов и разрешённых переходов между ними; при создании взаимодействия копируется в карточку |
| ИТ-направление, ИТ-программа, ИТ-продукт | каталоги ТЗ, раздел 1; программа относится к направлению, продукт — к вендору |
| Договор (соглашение по продукту) | связь взаимодействия с ИТ-продуктом: номер договора, подписание лицензии, срок лицензии (год), статус передачи |
| LMS | система управления обучением; у ИТ Школы РТК — Moodle |
| Источник данных | внешняя система, из которой CRM забирает записи: сайт ИТ Школы РТК (заявки на сотрудничество и на обучение, оплаченные заявки) и Moodle (числа по обучению) |
| Синхронизация | один запуск получения данных источника (вручную или планово); результат — счётчики и записи для разбора администратором |
| Поток обучения (learning stream) | курс Moodle или его группа, сопоставленные администратором с вузом, программой и датами; для оплат — пара «курс + номер потока» без Moodle |
| Слушатель | физическое лицо — заказчик и обучающийся по договору об оказании платных образовательных услуг открытого набора; анкета хранится в модуле «Слушатели» зашифрованной |
| Оператор зачисления | признак (флаг) в профиле CRM: даёт доступ к разделу «Зачисление» — загрузке файла оплат, работе с потоками и анкетами, заполненному шаблону и файлу для LMS |
| Вендор | компания-правообладатель ИТ-продукта; у вендора — контактное лицо по каждому продукту |
| MANAGEMENT | роль «Руководство»: читает все вузы и сводку по всем командам, не меняет данные |
| Keycloak | сервер учётных записей и входа (OIDC), обязателен по ТЗ |
| requestId | уникальный номер запроса к серверу; показывается в сообщении об ошибке и записывается в журнал сервера |

## 2. Назначение и состав системы

### 2.1. Назначение

CRM помогает сотрудникам ИТ Школы РТК вести работу с каждым вузом по пути из 14 шагов, описанному в разделе 2 ТЗ: от поиска контакта до повышения квалификации преподавателей. Для каждого вуза видно, на каком этапе находится работа по каждой программе и продукту, какой следующий шаг и срок, кто ответственный и что происходило раньше. Раздел «Моя работа» собирает у руководителя показатели по каждому КАМ команды (просрочено, без следующего шага, требует назначения, дольше N дней на этапе) с переходом к спискам; роль «Руководство» видит сводку по всем командам. Заявки и оплаченные заказы с сайта и числа обучения из Moodle попадают в карточки через общий конвейер источников, а справочник вендоров с контактами и приём оплат за открытый набор слушателей ведутся в отдельных разделах. По этим данным строятся отчёты и диаграммы за период.

### 2.2. Пользователи

| Роль | Что делает в CRM | Какие данные видит |
|---|---|---|
| КАМ (роль USER) | ведёт контакты, взаимодействия, этапы, комментарии, файлы; подтверждает заявки источников; строит отчёты; с флагом «Оператор зачисления» — грузит файл оплат | только вузы, назначенные ему (или где он временный заместитель), в пределах своей команды |
| Руководитель (LEADER) | все действия КАМ по любому вузу команды наравне с ним; назначает, меняет и снимает ответственного КАМ (включая себя); массовая передача вузов; временный заместитель на период; ведёт шаблоны процесса команды; видит показатели «Моя работа» по КАМ команды | все вузы своей команды, включая вузы без КАМ |
| Администратор (ADMIN) | управляет профилями CRM (роль, команда, активность, флаг «Оператор зачисления»), командами, переносом вузов, справочниками (направления, программы, вендоры и их контакты, продукты), импортом каталогов, источниками данных (синхронизация, разбор, сопоставления), журналом и функциями субъекта ПДн, сроками хранения | бизнес-данных вузов (карточки, история, отчёты) не видит; только служебные списки: профили, команды, вузы без контактов и взаимодействий |
| Руководство (MANAGEMENT) | только читает; ничего не меняет | все вузы всех команд и сводка по ним |

Руководитель ведёт карточки вузов своей команды наравне с КАМ: добавляет контакты и взаимодействия, переводит этапы, комментирует, меняет план, правит этапы карточки, загружает файлы. Автором события в истории указывается тот, кто выполнил действие, а не ответственный КАМ.

### 2.3. Состав

| Компонент | Назначение | Версия |
|---|---|---|
| Веб-клиент (React SPA) | интерфейс пользователя в браузере | React 19.3.0, Vite 8.3.0, TypeScript 5.9.3 |
| Сервер приложения (Spring Boot) | REST API, вход через Keycloak, бизнес-правила, синхронизация источников, фоновое построение отчётов, ночная задача сроков хранения | Java 21, Spring Boot 3.5.16 |
| PostgreSQL | БД CRM и отдельная БД Keycloak | 16.11 |
| Keycloak | учётные записи, пароли, вход | 26.7.4 |
| ClamAV | антивирусная проверка загружаемых файлов | 1.4.6 |
| nginx | единый адрес для клиента, API и входа; TLS в публикационном варианте | 1.29.2 |
| Демо-Moodle | настоящий Moodle для демонстрации интеграции LMS; часть демо-стенда, отдельный проект Compose `infra/moodle` | Moodle 4.5, MariaDB |
| Демонстрационный стенд API сайта (`site-fixture`) | отдаёт заявки и оплаты по предложенному контракту CRM (раздел 6.5); только профиль Compose `demo` | — |
| Docker Compose | запуск всех компонентов на Linux-сервере | Docker Compose v2 не ниже 2.24 |

Все компоненты запускаются одной командой (раздел 8). Система — отдельный самостоятельный сервис со своей БД, веб-интерфейсом и API (ТЗ, п. 6.3). Модуль «Слушатели» (анкеты, оплаты, потоки) включён на демо-стенде и переменной `MODULE_ENROLMENT_ENABLED`; по умолчанию выключен до решений оператора персональных данных (раздел 11).

## 3. Соответствие ТЗ

Статусы в таблице:

- **Проверено** — сценарий выполнен на запущенном стенде, результат записан;
- **Реализовано** — функция есть в коде, проходят автоматические тесты и сборка, приёмка на стенде после последних изменений не проводилась;
- **Частично** — реализована часть требования, недостающее названо;
- **Не испытывалось** — механизм есть, испытание не проводилось;
- **Заблокировано** — нет внешнего условия (доступа, контракта).

Автоматические тесты сервера и клиента проходят без ошибок (один тест LMS пропускается без адреса и токена тестового Moodle); нагрузочная проверка НФТ1/6/7 — раздел 3.2 и `docs/load-testing.md`.

## 4. Функциональная архитектура

Модель в формате Archi: `docs/delivery/archi/rtk-crm.archimate`, представление «Функциональная архитектура». Как открыть — `docs/delivery/archi/README.md`.

[Скриншот: представление «Функциональная архитектура» в Archi]

**Роли.** Сотрудник ИТ Школы РТК выступает в одной из ролей: КАМ, руководитель, администратор платформы или «Руководство» (только чтение, раздел 2.2). Представитель вуза — внешний участник без кабинета в CRM: его контакты, документы и договорённости вносит КАМ. Оператор зачисления — КАМ или руководитель с отдельным флагом доступа к разделу «Зачисление».

**Основной процесс** — «Взаимодействие с вузом» из 14 шагов ТЗ. Шаги 1–13 идут друг за другом; шаг 5 «Корректировка документов» необязателен, и от обмена документами можно перейти сразу к подписанию, указав причину в комментарии. Шаг 14 «Контроль за исполнением каждого этапа» — не отдельный этап, а постоянная функция: сроки, ответственный, история, отчёты. Процесс выполняет КАМ; руководитель ведёт карточки наравне с КАМ и отвечает за контроль и назначение ответственных.

**Вспомогательные процессы:** назначение, передача и временное замещение ответственного КАМ (руководитель), отчётность за период (КАМ и руководитель), приём заявок и оплат из внешних источников (сайт, Moodle), приём оплат за открытый набор слушателей (оператор зачисления), сопровождение CRM — доступ, команды, каталоги, вендоры, источники данных, шаблоны, персональные данные (администратор).

## 5. Компонентная архитектура

Представления «Компонентная архитектура» и «Развёртывание» в той же модели Archi.

[Скриншот: представление «Компонентная архитектура» в Archi]

### 5.1. Компоненты и связи

1. Пользователь открывает CRM в браузере по единому адресу. Контейнер `web` (nginx) отдаёт веб-клиент, передаёт запросы `/api/`, Swagger UI и `/openapi.yaml` серверу приложения, а `/idp/` — Keycloak.
2. Веб-клиент обращается только к REST API `/api`. Сервер работает по схеме BFF (backend for frontend): вход через Keycloak выполняет сервер, браузер получает только cookie сессии; токены OIDC в браузер не передаются.
3. Сервер приложения хранит данные в PostgreSQL, проверяет файлы в ClamAV, получает сведения об учётных записях из Keycloak.
4. Moodle и сайт — внешние системы за общим конвейером источников (пакет `source`): Moodle подключается ограниченным веб-сервисом только на чтение, сайт — по контракту, который предлагает сама CRM. На демо-стенде их заменяют контейнеры демо-Moodle и `site-fixture` (раздел 5.4).

### 5.4. Развёртывание

[Скриншот: представление «Развёртывание» в Archi]

Контейнеры `compose.yaml`: `web` (nginx), `backend` (Spring Boot), `postgres`, `keycloak` (эти четыре — профиль `core`, без метки), `clamav` (профиль `security`), `backend-bootstrap` (одноразовое заполнение демо-данных) и `site-fixture` (демонстрационный API сайта) под профилем `demo`, отдельный проект Compose `infra/moodle` — демо-Moodle. Наружу опубликован только `web`: порт 8081 в демо-варианте, 80 и 443 в публикационном (`compose.prod.yaml`). На сервере владельца, где TLS и маршрутизацию по доменам уже выполняет общий обратный прокси (Caddy в сети Docker `edge`, общий с другими проектами), вместо `compose.prod.yaml` накладывается `compose.edge.yaml`: он не публикует 80/443 сам, а добавляет в общий прокси блок маршрутизации на контейнер `web` (подробно, включая пример конфигурации прокси, — `docs/deploy.md`, раздел «Размещение за общим обратным прокси»). Данные хранятся в томах `postgres-data`, `attachments-data`, `reports-data` (готовые файлы отчётов), `clamav-data`. Подробно — `docs/deploy.md`.

Публичный репозиторий — github.com/avrv1987/rtk-crm: код, конфигурация сборки и запуска, README, документы поставки и описание непрерывной сборки (GitHub Actions). Публичная посадочная страница (`frontend/src/features/landing/LandingPage.tsx`) открывается неавторизованным пользователям вместо формы входа и даёт ссылки на репозиторий, демо-Moodle и материалы для проверки.

## 6. Методы обработки данных

### 6.1. Workflow: этапы, переходы, контроль

Подробное описание — `docs/workflow.md`.

- **Шаблон процесса** — упорядоченный список этапов (название, порядок, признак «необязательный») и явный список переходов с признаком «нужен комментарий». Базовый шаблон создаётся при установке и содержит 13 этапов пути ТЗ.
- **Снимок.** При создании взаимодействия этапы и переходы выбранного шаблона копируются в карточку. Изменение шаблона действует только на новые карточки; действующую карточку КАМ правит локально (раздел 13.4).
- **Проверка графа.** Шаблон и правка этапов карточки отклоняются, если нет стартового этапа, есть переход в тот же этап или повтор, пропуск этапа без обязательного комментария, этап без выхода (кроме последнего) или недостижимый этап (раздел 13.3).
- **Переход и комментарий** — команды с защитой от повтора и от устаревших данных (разделы 13.1, 13.2). Этап, событие истории, комментарий, новый следующий шаг и привязка файлов сохраняются вместе или не сохраняются вовсе.
- **Контроль исполнения** складывается из текущего этапа, следующего шага и срока, ответственного и истории. На карте пути видно, сколько дней карточка на текущем этапе, какие этапы пройдены (с датой входа), пропущены и впереди; просроченный срок отмечается.
- **История** хранит тип события, этап и его название на момент события, прежний и новый этапы, комментарий, новый план, автора, ответственного КАМ на момент события, версию карточки и время. Переименование этапа не переписывает историю.
- Пользовательские формулы, скрипты и запросы в workflow не допускаются: правила графа фиксированы в коде (`interaction/WorkflowGraph.java`).

### 6.2. Импорт каталогов

Подробное описание — `docs/import.md`.

- Импорт выполняет только администратор. Файл не создаёт профили, роли и учётные записи.
- Порядок: проверка файла (формат XLS или XLSX по содержимому, до 5 МиБ, антивирус, список листов и заголовков) → сопоставление столбцов (для 10 полей ТЗ — автоматически по заголовкам) → предпросмотр с протоколом «было/станет» по каждой строке → выбор строк и применение.
- До применения в БД сохраняется только план; каталоги не меняются. Применение идёт одной транзакцией со сверкой версий записей: если данные изменились после предпросмотра, ничего не записывается, нужен новый предпросмотр (раздел 13.8).
- Сопоставление записей: явный UUID → внешний ключ (из столбца ключа или выведенный из нормализованного названия) → уникальное название. Нормализация: регистр, лишние пробелы, «ё» = «е».
- «ФИО Менеджера» ищется среди активных КАМ; неоднозначное имя не выбирает человека случайно — строка получает статус «Конфликт».
- Статусы строк: «Создать», «Обновить», «Без изменений», «Конфликт», «Ошибка». Ошибка в одной строке не останавливает остальные.
- Пределы: 5 000 строк, 50 столбцов, 4 000 символов в ячейке; формулы не вычисляются — берётся сохранённое Excel значение.

### 6.3. Отчёты, статистика и диаграммы

Подробное описание — `docs/reports.md`.

- **Виды отчётов.** «Портфель взаимодействий» — одна строка на взаимодействие, этап и ответственный текущие; период отбирает созданные в нём взаимодействия или взаимодействия с событиями в периоде. «События за период» — одна строка на событие; ответственный — КАМ на момент события, автор — отдельной колонкой.
- **Период** — даты включительно; сервер переводит их в интервал `[начало первого дня; начало дня после последнего)` по московскому времени.
- **Область данных.** Строки берутся только из вузов, видимых пользователю, по тому же правилу, что и список вузов. Фильтр по вузам сужает, но не расширяет видимое.
- **Фильтры** объединяются через «И», значения внутри фильтра — через «ИЛИ». Пустые направление, программа, продукты, ответственный показываются как «Не указано» и не пропадают незаметно.
- **Один набор строк.** Предпросмотр, файлы всех форматов и статистика используют один построитель условий; несколько продуктов у взаимодействия не умножают строки и счётчики.
- **Статистика** считается группировкой в БД; «Не указано» — отдельная категория, не ноль; пустые месяцы показываются с нулём.
- **Диаграммы:** горизонтальные столбцы, шкала с нуля, число у каждого столбца, подпись с периодом и фильтрами, в PDF — таблица основания. Если столбцов больше 100, файл не строится, чтобы не исказить данные обрезкой.
- **Форматы:** XLSX; XLS — настоящий формат Excel 97–2003, не переименованный XLSX (не больше 65 536 строк на листе вместе с шапкой); PDF (A4, альбомная, шрифт Liberation Sans с кириллицей); JSON с описанием периода, фильтров и полноты данных; PNG и PDF для диаграмм. Текст, похожий на формулу, записывается в Excel как текст.
- **Фоновое построение** — через задания и пул из 10 построений (раздел 13.6).
- Отчёт о спросе (заявки, участия, потоки) не строится, пока нет данных LMS и сайта: файл с нулями вместо отсутствующих данных не выдаётся.

### 6.4. Вложения и антивирусная проверка

- Допустимые форматы — 10 форматов ТЗ и фото HEIC/HEIF с телефона: PNG, JPEG, HEIC/HEIF, PDF, ZIP, GZIP, RAR, DOC, DOCX, XLS, XLSX; формат определяется по расширению и проверяется по сигнатуре содержимого (для HEIC/HEIF — блок `ftyp` с маркой HEIF); `jpg` и `gz` считаются JPEG и GZIP.
- Размер — до 20 МБ.
- Порядок: проверка формата → сохранение под случайным ключом в закрытом томе → проверка ClamAV → статус «Проверен», «Отклонён» или «Не удалось проверить» (раздел 13.7).
- Скачать можно только проверенный файл вуза из своей области данных. Отклонённый файл удаляется с диска.
- Архивы не распаковываются и не исполняются сервером; зашифрованные архивы антивирус отклоняет.

### 6.5. Интеграции с LMS и сайтом: общий конвейер источников

Подробное описание — `docs/integrations.md`. Сайт и Moodle приводятся к одной модели `source_records` (тип записи, внешний идентификатор, версия): это упрощает разбор администратором и общую строку состояния источников в карточке.

- **Moodle** подключается ограниченным веб-сервисом REST только на чтение: настраиваемый адрес и тайм-аут, токен технического пользователя, список разрешённых курсов, явное сопоставление курса или группы с потоком обучения, ручная и плановая синхронизация. В CRM попадают только количественные показатели (участники, завершившие, не завершившие, неизвестно), без ФИО и почты обучающихся. Ошибка синхронизации показывается как «нет данных», а не как ноль. Адаптер проверен на локальном настоящем Moodle 4.5 (демо-стенд); Moodle заказчика недоступен.
- **Сайт** — заказчик не передал API, поэтому CRM реализует HTTP-адаптер по контракту, который предлагает сама: `docs/integrations/site-api.yaml` (заявки на сотрудничество, заявки на обучение для статистики спроса, оплаченные заявки — раздел 6.9). Повтор одной и той же записи (по ключу «тип + внешний ID») не создаёт дубль. Демонстрационный стенд `infra/site-fixture` отдаёт страницы в этом формате и проверяет адаптер CRM, но не совместимость с сайтом заказчика; на экране администратора источник помечен «Предложенный контракт, DEMO».
- Заявки, ожидающие разбора, администратор сопоставляет с существующим вузом или создаёт новый прямо из записи источника (`docs/integrations.md`, «Разбор записей администратором»); руководитель и КАМ видят только причину, по которой заявка их вуза не применилась.

Доступа к API сайта и стендам заказчика нет, поэтому все внешние интеграции (сайт-заявки, сайт-оплаты, Moodle, файл «Загрузка пользователей», Keycloak/IdP заказчика) работают через заглушки; как они устроены и как подключить реальные системы — `docs/integrations/Заглушки.md`.

### 6.6. Кэш действий пользователя

По ТЗ (ФТ 13) и заданию на разработку кэш трактуется так: выбор фильтров и колонок отчётов и черновики текста (комментарий, переход, план, правка этапов) сохраняются в `sessionStorage` браузера отдельно для каждого профиля и карточки. Они доступны при возврате в раздел в той же вкладке и удаляются при выходе из CRM и при потере профиля. Токены, ответы сервера и файлы в браузере не сохраняются. Автоматического повтора операций при потере сети нет: повтор делает пользователь, а сервер не создаёт дубль (раздел 13.1).

### 6.7. Время

Все моменты времени хранятся с часовым поясом (`timestamp with time zone`) и передаются в API в формате ISO 8601 со смещением. Периоды отчётов считаются по московскому времени (`Europe/Moscow`). Дни на этапе и просрочка на экране считаются по часам браузера.

### 6.8. Справочник вендоров и продуктов

Подробное описание — `docs/roles.md`, раздел «Организации и справочники». Направления, программы, вендоры и продукты — общий справочник администратора с одинаковыми правилами: добавление, переименование, архивирование и восстановление с проверкой версии; дубль по нормализованному названию внутри того же родителя отклоняется, в том числе среди архивных. Ключ и поиск вендора — одно правило нормализации (`CatalogNames.vendorKey`): регистр, лишние пробелы, «ё» = «е» и отбрасывание организационно-правовой формы в начале названия (ООО, ОАО, ПАО, АО, ЗАО, ИП), поэтому «Базис» находит «ООО «Базис»» и не создаёт второго вендора при импорте с другим написанием формы. У продукта — необязательный контакт вендора (ФИО, телефон в формате `+7XXXXXXXXXX`, email, признак канала «Почта» или «Telegram»); контакт правит администратор в справочнике, а КАМ и руководитель видят его в карточке продукта и в форме «Договор и лицензия» без права правки. Импорт справочника — файлом организатора «Вендоры.xlsx» (`VendorContactImport`): вендоры, продукты и контакты одной операцией, построчные ошибки не останавливают остальные строки, повтор того же файла не меняет ничего лишнего.

### 6.9. Оплаты открытого набора и модуль «Слушатели»

Подробное описание — `docs/integrations.md` (раздел «Оплаченные заявки») и `docs/enrolment.md`.

- **Приём оплаты.** Файл или ответ сайта с типом записи `paid_order` разбирается в общем конвейере источников (раздел 6.5): непрозрачный номер заявки, курс (сопоставляется с программой один раз), номер потока и версия — хеш разрешённых полей. Организация — служебная «Открытый набор (физлица)» (тип `OPEN_ENROLLMENT`), находится без ручного сопоставления. Загружает файл только сотрудник с флагом «Оператор зачисления» (раздел «Зачисление»); при выключенном модуле «Слушатели» раздела нет и API отвечает `404` всем.
- **Одна транзакция на запись.** Поиск или создание потока, слушателя и зачисления происходят в той же транзакции, что и запись источника (`SiteRecordApplier`, `docs/integrations.md:57`). Сбой на любом шаге откатывает всё: запись получает `FAILED` без значений ПДн в причине и применяется заново при следующей загрузке — повтор не дублирует слушателей и зачисления, но достраивает недостающее (идемпотентно, включая уже «Пропущенные» записи).
- **Анкета слушателя.** Хранится в таблице `learners`: все 30 полей шаблона организатора «Загрузка пользователей» шифруются по отдельности (AES-256-GCM, версия ключа в записи для ротации, `LearnerDataCipher`), AAD содержит версию ключа, идентификатор слушателя и код поля. Поиск и дедупликация — по отпечаткам HMAC (email, телефон, СНИЛС, фамилия и имя), без расшифровки таблицы; дубль по СНИЛС переносит зачисления к существующему слушателю с записью в журнал.
- **Ротация ключа.** `LearnerRekeyJob` перешифровывает анкеты старой версии ключа порциями по 100 (по анкете в своей транзакции), пересчитывает отпечатки и пропускает нерасшифровываемые записи с журналом без значений.
- **Маскирование и журнал.** Анкета показывается в масках (телефон, email, СНИЛС, номер паспорта), полное значение — по кнопке «Показать» с записью в журнал категории `LEARNER`; то же для просмотра списка, изменения, поиска, импорта и выгрузки.
- **Срок хранения.** По умолчанию 3 года после окончания потока (настраивается, допущение владельца до решения оператора ПДн), затем обезличивание анкеты с сохранением зачислений, потоков и номеров заявок для агрегатов; поток без даты окончания не трогается. Счётчик анкет в блоке «Сроки хранения» предупреждает при приближении к порогу 100 000 (условие УЗ-4, раздел 11).
- **Файл для LMS и полный экран «Зачисление»** (заполнение анкеты оператором, список потоков, отметка «Передано») — подробности в разделе 13.11.

## 7. Условия и ограничения

**Условия работы:**

- сервер Linux x86_64 (Ubuntu 22.04+, CentOS Stream 9 или аналог), 4 ГБ оперативной памяти и больше (ClamAV использует до 2 ГБ);
- Docker Engine и Docker Compose v2 не ниже 2.24;
- доступ в интернет при первой сборке (образы, библиотеки, сигнатуры ClamAV) и для обновления сигнатур;
- современный браузер; интерфейс рассчитан на экраны от 360 px в ширину.

**Ограничения продукта:**

| Ограничение | Пояснение |
|---|---|
| Один процесс сервера | второй экземпляр сервера одновременно запускать нельзя: задания отчётов не рассчитаны на несколько исполнителей |
| Один КАМ на вуз | все взаимодействия вуза наследуют ответственного; разные КАМ по программам одного вуза не поддерживаются |
| Список вузов | в разделе «Вузы» показываются 25 последних изменённых вузов области; полнотекстовый поиск по всему каталогу вне области не реализован |
| Контакты | контакт можно добавить и уточнить через функции субъекта ПДн, но не изменить произвольно и не удалить в обычном интерфейсе; уточнение — повторным импортом каталога |
| Удаление данных | явного удаления взаимодействий, файлов и истории нет; сроки хранения настроены и запускаются ночной задачей для файлов отчётов, неактивных контактов, отключённых профилей, журнала и анкет слушателей (раздел 11, `docs/roles.md`) — значения по умолчанию, а не решение оператора ПДн |
| Отчёты | до 50 000 строк в файле, до 20 000 строк в PDF, в XLS — не больше 65 536 строк на листе вместе с шапкой; до 100 столбцов в диаграмме; при превышении файл не строится, данные не обрезаются молча |
| Файлы отчётов | не удаляются автоматически (кроме срока хранения) и хранятся в контейнере `backend` без отдельного тома: после пересоздания контейнера скачать прежний файл нельзя |
| Импорт | 5 МиБ, 5 000 строк; импорт не удаляет записи, которых нет в файле; несколько ответственных в одной ячейке сохраняются одним контактом |
| Период отчётов | часовой пояс фиксирован — московское время |
| Диаграмма в файле | может отличаться от показанной на экране, если данные изменились между показом и заказом; время формирования подписано на обоих |
| Нагрузка | НФТ6 (50 пользователей) выполнено, НФТ1 и НФТ7 выполняются только при выделенных ресурсах сервера — раздел 3.2, `docs/load-testing.md` |
| Интеграции | Moodle и предложенный контракт сайта работают на демо-стенде; настоящие LMS и сайт заказчика не проверены (внешнее ограничение, раздел 3.4) |
| Модуль «Слушатели» | по умолчанию выключен (`MODULE_ENROLMENT_ENABLED=false`) до решений оператора ПДн об основаниях и сроках хранения; включён на демо-стенде |
| Экран «Зачисление» | реализован целиком (загрузка оплат, потоки, анкета, заполненный шаблон, файл для LMS, раздел 13.11); статус — выполнено, не проверено вживую |
| Публикация | HSTS не включён; в демо-варианте консоль Keycloak доступна по `/idp/admin/`; в публикационном закрыта |

## 8. Компиляция, сборка и установка

### 8.1. Установка на Linux (рекомендуемый способ)

Требования — раздел 7. Команды:

```bash
git clone <адрес репозитория> rtk-crm
cd rtk-crm
printf 'PUBLIC_ORIGIN=http://<адрес сервера>:8081\n' >> .env.local
./scripts/bootstrap-demo.sh
docker compose --env-file .env.local ps
```

`PUBLIC_ORIGIN` — адрес CRM, который набирают в браузере: имя или IP-адрес сервера с портом 8081, без `/` в конце. Из него строятся адрес Keycloak, адрес возврата после входа и настройки клиента `crm-bff`, поэтому вход работает только по этому адресу. Если строку с `PUBLIC_ORIGIN` не создавать, скрипт подставит `http://rtk.localhost:8081`: этот адрес открывается только в браузере на самом сервере, а с другого компьютера кнопка «Войти» уведёт на `rtk.localhost` этого компьютера. Сменить адрес позже: исправить строку `PUBLIC_ORIGIN` в `.env.local` и снова запустить скрипт, он обновит настройки клиента в Keycloak. Файл `.env.local` после первого запуска не перезаписывать: в нём пароли БД и секреты.

Скрипт:

1. дополняет `.env.local` случайными паролями и секретами, заданные значения сохраняет (права 600, в git не попадает);
2. поднимает PostgreSQL и Keycloak, применяет настройки realm `rtk-crm` (парольная политика, журнал событий), создаёт клиент `crm-bff` и демо-пользователей;
3. собирает образы сервера и клиента, поднимает все сервисы и ждёт их готовности;
4. заполняет демо-данные: два КАМ, руководитель, администратор, три вуза (один без КАМ), контакты, взаимодействие, программа и продукт.

Первый запуск занимает 5–15 минут: сборка образов и загрузка сигнатур ClamAV. Повторный запуск безопасен: пароли и данные сохраняются.

Проверка после запуска: все сервисы в состоянии `healthy` (у `web` — `running`); в браузере открывается адрес из `PUBLIC_ORIGIN`; кнопка «Войти» ведёт на страницу входа Keycloak по тому же адресу (`<PUBLIC_ORIGIN>/idp/…`).

### 8.2. Публикация с TLS

В `.env.local` добавляются внешний адрес, пути к сертификату и ключу и `COMPOSE_FILE=compose.yaml:compose.prod.yaml`, затем снова запускается `./scripts/bootstrap-demo.sh`. ### 8.4. Резервное копирование и восстановление

```bash
./scripts/backup.sh /srv/backup/rtk-crm/2026-09-24
./scripts/restore.sh /srv/backup/rtk-crm/2026-09-24
```

Копия содержит зашифрованные AES-256 дампы БД CRM и Keycloak, архивы томов вложений и отчётов и контрольные суммы; ключ — `BACKUP_ENCRYPTION_KEY` в `.env.local`, без него копию не восстановить. Она содержит персональные данные, хеши паролей и секрет клиента `crm-bff` из БД Keycloak, а также действующие на момент копирования сессии CRM (таблицы `spring_session`, `spring_session_attributes`): зная идентификатор сессии, можно работать в CRM от имени пользователя без пароля, пока сессия не завершена. Копию хранят вне сервера с ограниченным доступом. При утечке копии нужно завершить все сессии CRM (пользователи войдут заново), сменить секрет клиента `crm-bff` в Keycloak и в `.env.local` и пароли пользователей:

```bash
docker compose --env-file .env.local exec -T postgres sh -c 'psql --username="$POSTGRES_USER" --dbname="$CRM_DB_NAME" --command="DELETE FROM spring_session"'
```

Если копию всё же нужно передать другим лицам, её восстанавливают на отдельном стенде, выполняют там ту же команду и снимают новую копию. Для восстановления нужен тот же `.env.local` и тот же внешний адрес. Подробно — `docs/deploy.md`, раздел «Резервное копирование и восстановление». Восстановление в отдельный проект Compose проверено сравнением числа строк во всех таблицах CRM, числа пользователей realm `rtk-crm` и контрольной суммы файла вложений; вход демо-пользователей вернул те же профили. Содержимое таблиц построчно не сравнивалось.

### 9.1. Где смотреть

- Swagger UI: `<адрес CRM>/swagger-ui/index.html`, где `<адрес CRM>` — значение `PUBLIC_ORIGIN` (раздел 8.1), например `http://<адрес сервера>:8081/swagger-ui/index.html`.

### 9.2. Аутентификация и общие правила

- Вход — `GET /api/auth/login` (перенаправление в Keycloak); после входа браузер получает cookie `SESSION` (HttpOnly). Выход — `POST /api/auth/logout`: сервер завершает сессию и возвращает адрес завершения сессии Keycloak.
- Запрос без сессии получает `401`, учётная запись без активного профиля CRM — `403` с кодом `CRM_PROFILE_REQUIRED`; перенаправления на HTML-страницу для `/api` нет.
- Изменяющие запросы передают заголовок `X-CSRF-TOKEN` со значением из `GET /api/csrf`. В Swagger UI кнопка «Try it out» работает в сессии браузера на том же адресе: сначала нужно войти в CRM и получить токен.
- Команды передают заголовок `Idempotency-Key`; повтор с тем же ключом и телом возвращает прежний результат (раздел 13.1).
- Изменение карточки передаёт ожидаемую `version`; при устаревшей версии — `409 VERSION_CONFLICT` с `currentVersion` (раздел 13.2).
- Даты — `YYYY-MM-DD`, моменты времени — ISO 8601 со смещением, идентификаторы — UUID.
- Списки возвращают `{items, page, size, total}`.

### 9.4. Коды ошибок

Ошибка всегда возвращается в формате `{code, message, requestId}`; дополнительно могут быть `fieldErrors` (ошибки по полям) и `currentVersion`. `requestId` совпадает с заголовком ответа `X-Request-Id` и с записью в журнале сервера. Трассировка стека и секреты в ответ не попадают.

| Код | HTTP | Когда возникает |
|---|---|---|
| `VALIDATION_ERROR` | 400 | неверные данные запроса; подробности в `fieldErrors` |
| `BAD_REQUEST` | 4xx | прочие ошибки запроса |
| `UNAUTHENTICATED` | 401 | нет сессии или она истекла |
| `FORBIDDEN` | 403 | роли не хватает прав; неверный или отсутствующий CSRF-токен |
| `CRM_PROFILE_REQUIRED` | 403 | вход выполнен, но профиля CRM нет или он заблокирован |
| `NOT_FOUND` | 404 | объект не существует или находится вне области данных пользователя |
| `METHOD_NOT_ALLOWED` | 405 | метод не поддерживается |
| `CONFLICT` | 409 | прочий конфликт состояния |
| `VERSION_CONFLICT` | 409 | данные изменил другой пользователь; в ответе `currentVersion` |
| `IDEMPOTENCY_CONFLICT` | 409 | тот же `Idempotency-Key` использован с другим содержимым |
| `PAYLOAD_TOO_LARGE` | 413 | файл больше допустимого |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | неверный тип содержимого запроса |
| `RATE_LIMITED` | 429 | зарезервирован; ограничение частоты запросов в продукте не настроено |
| `INTERNAL_ERROR` | 500 | непредвиденная ошибка; подробности — в журнале сервера по `requestId` |
| `DEPENDENCY_UNAVAILABLE` | 503 | недоступен зависимый сервис |
| `REPORT_CAPACITY_EXCEEDED` | 503 | заняты все 10 построений и очередь; повторить через 30 секунд |
| `REPORT_NOT_READY` | 409 | файл отчёта ещё не построен |
| `REPORT_ACCESS_CHANGED` | 410 или ошибка задания | права пользователя изменились после заказа отчёта |
| `REPORT_RESULT_UNAVAILABLE` | 410 | файл отчёта больше не хранится |
| `REPORT_ROW_LIMIT`, `REPORT_XLS_ROW_LIMIT`, `REPORT_PDF_ROW_LIMIT`, `REPORT_CHART_LIMIT` | ошибка задания | превышен предел строк или столбцов диаграммы |
| `REPORT_INTERRUPTED` | ошибка задания | сервер перезапустился во время построения |
| `REPORT_FAILED` | ошибка задания | непредвиденная ошибка построения |

Коды ошибок заданий отчётов приходят в поле `errorCode` задания (`GET /api/report-jobs/{id}`).

## 11. Информационная безопасность

Полный пакет — `docs/delivery/security/`: перечень ПДн, уровень защищённости, применимость нормативных актов, модель угроз, меры защиты, включая модуль «Слушатели» и контакты вендоров. Это рабочая оценка команды разработки до решений оператора ПДн.

Кратко:

- В CRM обрабатываются «иные» персональные данные: контакты представителей вузов, сведения о сотрудниках, контакты вендоров и (в модуле «Слушатели») анкета слушателя открытого набора — ФИО, паспорт, СНИЛС, адрес и сведения об образовании. Рабочая оценка уровня защищённости по ПП РФ № 1119 — УЗ-4, при условии не более 100 000 анкет слушателей одновременно в CRM (раздел 6.9).
- Приказ ФСТЭК России № 117 распространяется на государственные информационные системы и системы госорганов, ГУП и госучреждений; правовой статус оператора CRM в ТЗ не указан. Приказ использован как ориентир, для ИСПДн применимы ПП № 1119 и приказ ФСТЭК № 21.
- Реализованные меры: вход только через Keycloak с парольной политикой и защитой от подбора; серверная проверка прав в каждом запросе к данным; CSRF; cookie `HttpOnly`, `SameSite=Lax`, `Secure` в публикационном варианте; TLS 1.2/1.3; антивирусная проверка каждого файла; журналы действий с автором и `requestId`; пределы размера файлов и нагрузки; проверенное резервное копирование; секреты вне репозитория.
- Реализованы функции по запросам субъекта ПДн (поиск, выгрузка сведений, уточнение, ограничение обработки, обезличивание с сохранением истории), сроки хранения с ночной задачей, единый журнал администратора и безопасности с выгрузкой, отключение учётной записи Keycloak при блокировке профиля. Реестр мер со ссылками на автотесты и сценарии — `docs/delivery/security/6_Реестр_мер.md`.
- Второй фактор входа (TOTP) для администратора и оператора зачисления реализован и включается переменной `MFA_REQUIRED_FOR_PRIVILEGED=true` при переходе в эксплуатацию; резервные копии шифруются AES-256. Не реализовано: автоматическая проверка уязвимостей. Сроки хранения действуют по умолчанию до решения оператора ПДн.
- Соответствие 152-ФЗ и приказу № 117 не заявляется: это рабочая оценка, а не аттестация.

## 12. Отступление от п. 6.5 ТЗ: комментарии в коде

Пункт 6.5 ТЗ требует сопровождать сложные технические и логические детали решения комментариями.

Владелец продукта поставил обязательное требование: собственный исходный код, миграции и конфигурация не содержат поясняющих комментариев, Javadoc, закомментированного кода и пометок «сделать позже». Причины:

- комментарий в коде не проверяется компилятором и тестами и со временем расходится с кодом; устаревший комментарий вводит в заблуждение сильнее, чем его отсутствие;
- понятность кода обеспечивается предметными именами классов и методов, небольшими функциями, явными типами и тестами, описывающими поведение;
- сложные правила нужны не только разработчику, но и аналитику, администратору и заказчику, поэтому им место в документации рядом с описанием сценария.

Чтобы требование ТЗ по существу было выполнено, все сложные технические и логические детали описаны в разделе 13 этого документа и в тематических документах `docs/workflow.md`, `docs/import.md`, `docs/reports.md`, `docs/deploy.md` (приложения к этому документу). Для каждой детали указан класс или файл, где она реализована. Обязательные лицензионные уведомления сторонних компонентов сохранены.

## 13. Сложные технические и логические детали

Пути к коду сервера даны относительно `backend/src/main/java/ru/rtk/crm/`.

### 13.1. Защита команд от повтора (идемпотентность)

**Задача.** Пользователь может нажать кнопку дважды, а сеть — оборваться после того, как сервер уже выполнил команду. Повтор не должен создавать второй переход, второй комментарий или второй файл.

**Как устроено.** Каждая изменяющая команда (создание контакта и взаимодействия, переход, комментарий, изменение плана и этапов, загрузка файла, назначение КАМ, блокировка профиля, операции с шаблонами, применение импорта) передаёт заголовок `Idempotency-Key` — строку до 255 символов, которую клиент создаёт один раз на действие.

1. Сервер проверяет видимость объекта и права пользователя.
2. Из содержимого команды вычисляется отпечаток — SHA-256 от JSON нормализованной команды (`interaction/CommandFingerprint.java`).
3. В той же транзакции, что и само изменение, сервер пытается вставить запись «пользователь + вид операции + ключ» в таблицу `command_idempotency_records` (`INSERT … ON CONFLICT DO NOTHING`, `interaction/CommandIdempotencyRepository.java`).
4. Если запись вставлена — команда выполняется, результат сохраняется в той же записи.
5. Если такая запись уже есть: при совпадающем отпечатке возвращается сохранённый результат, новое событие не создаётся; при другом отпечатке — ответ `409 IDEMPOTENCY_CONFLICT`.

Права проверяются до обращения к записи повтора, поэтому пользователь, у которого отобрали доступ, не получит результат даже повтором старого запроса. Уникальность ключа обеспечивает ограничение БД, поэтому два одновременных повтора не выполнят команду дважды. Задания отчётов используют тот же принцип с собственной таблицей `report_jobs`.

Экран создаёт ключ один раз на действие и отправляет тот же ключ, если пользователь повторяет действие после сетевой ошибки.

### 13.2. Версии данных и конфликт 409

**Задача.** Два пользователя (или две вкладки) меняют одну карточку; второе изменение не должно молча затереть первое.

**Как устроено.** У взаимодействий, вузов, профилей, шаблонов, контактов, договоров и предпросмотров импорта есть поле `version`. Клиент передаёт версию, которую видел. Сервер меняет запись условием `WHERE id = … AND version = …` и увеличивает версию на 1. Если ни одна строка не изменилась, значит, запись уже изменена другим: ответ `409 VERSION_CONFLICT` с текущей версией `currentVersion`.

Изменение карточки выполняется под блокировкой строки, поэтому версия растёт строго на единицу с каждой командой, а история упорядочивается по версии, а не по часам сервера.

Интерфейс при конфликте сохраняет введённый текст и предлагает «Обновить карточку». Черновик плана хранит только поля, которые пользователь сам изменил, поэтому после обновления чужие изменения других полей не откатываются.

### 13.3. Граф этапов и правила пропусков

**Задача.** Процесс должен быть настраиваемым, но так, чтобы обязательный этап нельзя было обойти незаметно.

**Правила проверки графа** (`interaction/WorkflowGraph.java`, одни и те же для шаблонов и для правки карточки). Граф отклоняется с `400`, если:

- нет стартового этапа;
- переход ссылается на этап вне графа, ведёт в тот же этап или повторяется;
- переход между несоседними этапами (пропуск вперёд или возврат через этап) не помечен «нужен комментарий»;
- у этапа, кроме последнего, нет ни одного выхода;
- хотя бы один этап недостижим от стартового.

Следствие: шаблон может разрешить пропуск этапа только как переход с обязательным комментарием. В базовом шаблоне это единственный пропуск «Обмен документами → Подписание» через необязательную корректировку документов.

**Правка этапов карточки** меняет переходы только вокруг затронутого этапа:

- при удалении этапа каждый путь «A → удаляемый → B» заменяется прямым переходом A → B; комментарий на нём обязателен, если был обязателен хотя бы на одном из двух исходных переходов;
- при вставке этапа N между A и B создаются переходы A → N и N → B с тем же признаком, что у A → B; возвраты появляются, только если был возврат B → A; прежние переходы через место вставки для обязательного N перенаправляются на N (обойти новый обязательный этап нельзя), а для необязательного N остаются пропуском с обязательным комментарием;
- перемещение этапа — удаление с прежнего места и вставка на новое.

Удалять и перемещать можно только будущие этапы, которые не упомянуты в истории и во вложениях; текущий этап не удаляется. Каждая правка увеличивает версию карточки и пишет в историю одно событие со списком изменений.

### 13.4. Снимок шаблона на карточке

**Задача.** Изменение процесса не должно переписывать уже идущую работу и её историю.

**Как устроено.** При создании взаимодействия этапы и переходы выбранного шаблона копируются в таблицы `interaction_stages` и `interaction_stage_transitions` с новыми идентификаторами. Дальше карточка живёт своей копией:

- изменение шаблона влияет только на новые взаимодействия; массового обновления действующих карточек нет;
- КАМ может локально переименовать этап карточки, добавить, переместить или удалить будущий этап (раздел 13.3);
- событие истории хранит название этапа на момент события, поэтому переименование не меняет прошлые записи;
- отчёты сравнивают этапы разных карточек по названию, поэтому фильтр «Этап» предлагает названия в порядке маршрута.

### 13.5. Область данных пользователя

**Задача.** КАМ не должен увидеть чужой вуз ни в списке, ни по прямой ссылке, ни в файле, ни в отчёте. Скрытая кнопка защитой не является.

**Как устроено.**

1. Каждый запрос к API находит активный профиль CRM по паре «издатель токена + идентификатор пользователя Keycloak» (`access/CurrentProfileService.java`). Нет профиля или он заблокирован — `403 CRM_PROFILE_REQUIRED`. Блокировка действует со следующего запроса.
2. Условие видимости строится в одном месте — `catalog/OrganizationRepository.java`, метод `visibilityScope`:
   - КАМ (USER): вузы, где он текущий ответственный или временный заместитель, в его команде;
   - руководитель (LEADER): все вузы своей команды, включая вузы без КАМ;
   - «Руководство» (MANAGEMENT): все вузы всех команд, только чтение;
   - администратор (ADMIN): пустая область — бизнес-данных вузов (карточки, контакты, история, отчёты) нет, только служебные списки без них.
3. Условие подставляется прямо в SQL-запрос к данным: список и карточка вуза, контакты, взаимодействия, история, файлы, отчёты, статистика, списки фильтров. Отбор после чтения в памяти не используется.
4. Чужой объект отвечает `404` (его существование не раскрывается); видимый объект, который роль не может менять, — `403`.
5. Блокировка профиля, смена роли, команды или флага «Оператор зачисления», а также передача вуза увеличивают счётчик `access_revision` профиля (`docs/roles.md`, «Правила администратора»). Задание отчёта запоминает его при заказе и сверяет перед построением и при скачивании: если права изменились, файл не строится и не выдаётся (`410 REPORT_ACCESS_CHANGED`).

При блокировке КАМ его вузы атомарно снимаются с него и появляются у руководителя как «Требует назначения».

### 13.6. Задания отчётов и пул из 10 построений

**Задача.** Выдерживать не менее 10 одновременно строящихся отчётов (НФТ 7), не блокируя интерактивную работу.

**Как устроено** (`report/ReportJobService.java`, `report/ReportJobExecutor.java`):

1. `POST /api/reports` проверяет запрос, сохраняет задание со статусом «в очереди» вместе с ролью, командой и `access_revision` владельца и отвечает `202 {jobId}`.
2. Пул исполнителей — ровно 10 потоков и ограниченная очередь на 40 заданий. Если заняты и потоки, и очередь, задание не сохраняется, клиент получает `503 REPORT_CAPACITY_EXCEEDED` с заголовком `Retry-After: 30`.
3. Исполнитель переводит задание в «выполняется» условным обновлением (две попытки одного задания невозможны), заново читает профиль владельца и сверяет права.
4. Строки читаются одной транзакцией с согласованным снимком, транзакция закрывается, и только потом рендерится файл — долгий рендеринг не держит соединение с БД.
5. Файл пишется во временный `.part`, затем атомарно переименовывается; только после этого задание получает статус «готово». Частичный файл не выдаётся.
6. Скачать результат может только владелец с неизменившимися правами.
7. При запуске сервера незавершённые задания получают ошибку `REPORT_INTERRUPTED`, временные файлы удаляются; автоматического повтора нет.

Пул соединений с БД — 20, поэтому 10 построений не отнимают соединения у интерактивных запросов. Предпросмотр (до 200 строк на страницу) и статистика (группировка в БД) выполняются сразу, без очереди.

### 13.7. Антивирусный конвейер вложений

**Задача.** Принимать документы 10 форматов ТЗ и фото HEIC/HEIF и не выдавать пользователям заражённые или непроверенные файлы, даже если антивирус недоступен.

**Как устроено** (`attachment/AttachmentService.java`, `attachment/AttachmentContentValidator.java`, `attachment/ClamAvAttachmentScanner.java`):

1. Проверка области данных и права на изменение, проверка, что этап принадлежит карточке.
2. Проверка файла: из имени убирается путь, имя с управляющими символами или длиннее 255 символов отклоняется; формат определяется по расширению и сверяется с сигнатурой начала файла; размер не больше 20 МБ; считается SHA-256.
3. Резервирование ключа повтора (раздел 13.1).
4. Файл записывается в закрытый каталог под случайным UUID, а не под именем пользователя.
5. Файл передаётся в ClamAV потоком по протоколу clamd (`INSTREAM`) во внутренней сети. Ответ «OK» — «проверен»; «FOUND» — «отклонён»; любой другой ответ, тайм-аут или обрыв связи — «не удалось проверить». Сбой сканера никогда не превращается в «проверен».
6. Запись о файле создаётся со статусом «карантин» и сразу получает итоговый статус. Отклонённый файл удаляется с диска.
7. Скачивание разрешено только для статуса «проверен» и только в пределах области данных; ответ содержит `X-Content-Type-Options: nosniff`.
8. Привязать файл к комментарию или переходу можно, только если он проверен, относится к этапу события (этап комментария или целевой этап перехода) и ещё ни к чему не привязан.

Настройки ClamAV (`infra/clamav/clamd.conf`) ограничивают размер потока и глубину вложенности архивов; зашифрованный архив и превышение пределов проверки считаются угрозой. Файлы импорта проходят ту же проверку формата и антивирус, но на диске не сохраняются.

### 13.8. Импорт: предпросмотр и применение

**Задача.** Загрузить каталог из Excel так, чтобы ошибка в файле не испортила данные, повтор не создал дублей, а неоднозначное имя не привело к случайному выбору человека.

**Как устроено** (`catalogimport/CatalogImportService.java`, `catalogimport/CatalogImportWorkbookReader.java`):

1. **Проверка файла** — формат по содержимому, размер, антивирус, листы и заголовки; файл не сохраняется.
2. **Предпросмотр.** Файл читается повторно. Для каждой строки строится план: какую запись найти или создать и какие поля изменятся («было/станет»). План и версии найденных записей сохраняются в `catalog_imports` и `catalog_import_rows`; каталоги не меняются.
3. **Поиск записей**: явный UUID из дополнительных столбцов → внешний ключ → уникальное название. Если ключа в файле нет, он выводится из нормализованного названия (например, `org:<название вуза>`), и повторный импорт того же файла находит те же записи. Несколько совпадений, противоречия внутри файла, разные КАМ одного вуза — «Конфликт».
4. **Применение** (`POST /api/imports/{id}/apply` с версией предпросмотра и `Idempotency-Key`). Применяются только выбранные строки со статусами «Создать», «Обновить», «Без изменений», все в одной транзакции. Перед записью версии записей сверяются с сохранёнными в предпросмотре; если что-то изменилось, ответ `409`, ничего не записано.
5. Договор всегда принадлежит взаимодействию; если подходящего нет, создаётся новое по шаблону процесса по умолчанию тем же кодом, что и из интерфейса. Комментарий из файла сохраняется событием с автором-администратором и временем импорта, а не выдаётся за историческую запись.

### 13.9. Шифрование анкеты слушателя и ротация ключа

**Задача.** Хранить анкету из 30 полей так, чтобы значения не читались напрямую из БД и из резервной копии, но чтобы слушателя можно было найти по email, телефону, СНИЛС или ФИО без расшифровки всей таблицы, а смена ключа не требовала остановки продукта.

**Как устроено** (`enrolment/LearnerDataCipher.java`, `enrolment/LearnerRekeyJob.java`):

1. Каждое поле анкеты шифруется по отдельности AES-256-GCM; связанные данные (AAD) — версия ключа, идентификатор слушателя и код поля, поэтому значение, переставленное в другое поле или к другому слушателю, не расшифровывается.
2. Ключи заданы по версиям (`KEYS_V1`, `KEYS_V2`, …), действующая версия — `ACTIVE_KEY_VERSION`; новые записи и правки всегда шифруются действующей версией.
3. Поиск и проверка на дубль используют отдельные отпечатки HMAC (`FINGERPRINT_KEY`) по email, телефону, СНИЛС и связке фамилии с именем — по отпечатку сравниваются, значение не расшифровывается.
4. `LearnerRekeyJob` через минуту после старта сервера и затем каждый час выбирает анкеты не действующей версии ключа порциями по 100, перешифровывает и пересчитывает отпечатки каждую в своей транзакции; анкету, которая не расшифровалась (повреждение, чужой ключ), пропускает и пишет в журнал backend без значений, не прерывая порцию.

Смена версии отпечатков идёт вместе со сменой версии ключа шифрования, поэтому старый и новый отпечаток никогда не сравниваются между собой. Тест `LearnerStorageTest` проверяет, что после создания, просмотра, раскрытия и правки анкеты ни одно значение не встречается ни в одной таблице БД в открытом виде.

### 13.10. Идемпотентный приём оплаты: одна транзакция на источник, поток, слушателя и зачисление

**Задача.** Файл или ответ сайта с оплатами обрабатывается построчно; сбой на одной записи не должен оставить слушателя без зачисления или создать зачисление без записи источника, а повтор того же файла не должен задвоить слушателей.

**Как устроено** (`source/SiteRecordApplier.java`, `enrolment/PaidOrderUploadService.java`):

1. Запись `paid_order` разбирается (`PaidOrderParser`) и получает ключ «тип + внешний номер заявки» и версию — хеш разрешённых полей (раздел 6.9).
2. Поиск или создание потока обучения (курс + номер), поиск или создание слушателя по отпечаткам (раздел 13.9) или новый слушатель, создание зачисления — выполняются в той же транзакции, что и сохранение записи источника.
3. Если шаг модуля «Слушатели» отказывает, откатывается вся транзакция: запись источника получает статус «Не применено» с причиной без значений ПДн и будет разобрана заново при следующей загрузке того же или нового файла.
4. Шаг идемпотентен и выполняется повторно даже для записей, ранее сохранённых как «Пропущено» (модуль был выключен на момент первой загрузки): если зачисления по заявке ещё нет, оно создаётся; если есть, происходит только сверка контактов. Поэтому включение модуля «Слушатели» после того, как оплаты уже загружались, не требует их повторной загрузки вручную — следующая обычная загрузка достраивает недостающее.

### 13.11. Экран «Зачисление»: анкета оператора, потоки, файл для LMS

Раздел `frontend/src/features/enrolment` и API `/api/enrolment/*` (`EnrolmentApiController`, `openapi.yaml`, тег Enrolment); подробное описание процессов — `docs/enrolment.md`, раздел «Раздел «Зачисление»»:

- **Список потоков** «курс + номер» со счётчиками «Оплачено / Анкеты / Выгружено / Передано / Ожидает / Окончание / Хранить до», доступный только с флагом «Оператор зачисления»; там же — загрузка файла оплат и точный поиск слушателя по email, телефону, СНИЛС или фамилии.
- **Поток**: дата окончания с проверкой версии, таблица слушателей потока с масками и пометками (обработка ограничена, совпадающий email, нет обязательных для LMS полей), список выгрузок для LMS с кнопкой «Отметить переданными».
- **Анкета слушателя** — группы «Основное», «Документы», «Личные сведения», «Адрес», «Дательный падеж», «Образование»: кнопка «Показать» раскрывает группу с записью в журнал, «Изменить» открывает форму правки после раскрытия; конфликт версии предлагает «Обновить»; СНИЛС другого слушателя предлагает перенос зачислений со сравнением обеих анкет; вкладки «Зачисления» и «История» без значений ПДн.
- **Заполнение анкеты** оператором с проверками полей (контрольное число СНИЛС, формат паспорта РФ и кода подразделения, согласованность дат, пол и образование из фиксированного списка, телефон, email) и историей изменений; загрузка заполненного шаблона (XLSX) с антивирусной проверкой, предпросмотром, построчными ошибками по ячейкам и кнопкой «Применить» — пустая ячейка не стирает уже сохранённое значение.
- **Файл «Загрузка пользователей» для LMS** строится из анкет модуля «Слушатели» по потоку: 30 заголовков дословно по шаблону организатора, второй лист с теми же значениями, проверка данных для «Пол» и «Образование», числовой формат телефона и текстовый — для СНИЛС, паспорта и индекса; режимы «Только не переданные» и «Все слушатели потока»; предупреждение (не отказ) при неполных обязательных полях с выбором «выгрузить с пустыми ячейками» или «исключить»; «Отметить переданными» — точно по слушателям выданного файла.
- Одна строка файла — одно зачисление; совпадающий email у двух слушателей потока — предупреждение, а не отказ строки.

Проверено сборкой, typecheck и автотестами backend/frontend (`EnrolmentServicesTest` и другие, раздел 10). Живой проверки экрана в браузере, включая ширину 360 px, ещё не было — статус выполнено, не проверено вживую.

[Скриншот: форма «Новое взаимодействие»]

### 14.5. Этапы: переход, комментарий, следующий шаг

Откройте взаимодействие из списка — появится «Карточка взаимодействия».

**Карта пути.** Показывает все этапы по порядку: текущий (выделен, с числом дней на этапе), пройденные (с датой), пропущенные и будущие. Необязательные этапы помечены.

[Скриншот: карточка взаимодействия с картой пути]

**Перейти на другой этап:**

1. В блоке «Переход этапа» выберите «Новый этап». В списке — только разрешённые переходы; «(нужен комментарий)» означает, что без комментария переход не сохранится.
2. При необходимости заполните «Комментарий к переходу» и отметьте проверенные документы для этого этапа.
3. Нажмите «Перейти на этап». Этап, комментарий и документы сохраняются вместе и появляются в «Истории».

**Добавить комментарий без смены этапа:** в блоке «Комментарий» выберите «Этап комментария», введите «Текст комментария», при необходимости отметьте документы и нажмите «Добавить комментарий».

**Изменить план:** в блоке «Следующий шаг» измените следующий шаг, срок, программу или продукты и нажмите «Сохранить план». Продукт, по которому уже есть данные договора, снять нельзя.

**История** внизу карточки показывает все события: дату, действие, этапы, комментарий, новый план, документы, автора. Кнопка «Обновить историю» загружает её заново.

[Скриншот: блоки «Переход этапа» и «История»]

**Если карточку изменил кто-то другой**, при сохранении появится сообщение о конфликте. Введённый текст сохранится. Нажмите «Обновить карточку», проверьте новые данные и повторите действие.

**Изменить этапы своей карточки (КАМ).** В блоке «Изменить локальный граф этапов» выберите «Операцию» («Переименовать этап», «Добавить этап после выбранного», «Переместить этап после выбранного», «Удалить этап»), этап и новое название, затем «Применить одну операцию». Изменение касается только этой карточки. Удалить можно только будущий этап, по которому ещё нет событий и документов.

### 14.6. Файлы

1. В карточке взаимодействия найдите блок «Документы» → «Загрузить документ».
2. Выберите «Этап документа», «Вид документа» (договор, лицензионное соглашение, акт, скан подписанного документа и другие) и файл: PNG, JPEG, HEIC (фото с iPhone), PDF, ZIP, GZIP, RAR, DOC, DOCX, XLS или XLSX, до 20 МБ. HEIC хранится как есть и скачивается, просмотра в браузере у него нет.
3. Нажмите «Загрузить в карантин». Файл проверяется антивирусом, статус показывается в списке документов: «Проверен: доступен», «Отклонён: недоступен» или «Не удалось проверить: недоступен». «Обновить статус» перечитывает состояние.
4. Проверенный файл можно отметить при комментарии к его этапу или при переходе на его этап — он будет связан с событием истории.
5. «Скачать файл» доступно только для проверенных файлов. PDF, PNG и JPEG можно открыть кнопкой «Просмотреть» в новой вкладке, не скачивая.
6. «Отбор по виду документа» над списком оставляет документы одного вида; вид у загруженного файла меняется в поле «Вид документа» в его строке.
7. «Загрузить новую версию» добавляет исправленный файл к прежнему: прежняя версия остаётся в списке, у файлов видна нумерация «Версия 1», «Версия 2».
8. «Удалить» убирает ошибочно загруженный файл. Удалить может автор файла или руководитель команды; можно указать причину. Файл перестаёт открываться и скачиваться, в истории появляется запись «Удалён документ» с автором и причиной. Файл, выбранный сканом договора или подтверждением передачи, сначала замените в форме продукта.

**Договор и лицензия по продукту.** В блоке «Продукты и соглашения» у продукта нажмите «Договор и лицензия»: укажите номер договора, подписание лицензии, год окончания лицензии и скан (сначала загрузите его в «Документы» и дождитесь проверки), затем «Сохранить». Рядом показан вендор продукта и его контакт (ФИО, телефон, email, предпочитаемый канал связи) с копированием телефона и почты одним нажатием; если контакт не указан в справочнике — «Контакт вендора не указан», без права добавить его здесь (правит администратор, раздел 15.4). Изменение видно сразу в карточке, в истории («Изменены договор и передача» с прежним и новым значением) и в отчётах. Другие продукты не меняются.

**Отметки передачи.** Там же кнопка «Отметки передачи»: для материалов, лицензии и документации выберите «Передано» с датой и подтверждающим файлом или «Не передано». Статус передачи продукта пересчитывается: «Передано», «Передано частично» или «Не передано». Под каждым продуктом видно, что передано и когда.

[Скриншот: блок «Документы» со статусами файлов]

### 14.7. Отчёты

Раздел «Отчёты и статистика».

1. Выберите «Вид отчёта»: «Портфель взаимодействий» (текущее состояние карточек) или «События за период» (все действия за период).
2. Задайте даты «Период с» и «по» (включительно, по московскому времени; пустая дата снимает ограничение). Для портфеля выберите «Отбор по периоду»: «Созданные в периоде» или «С событиями в периоде».
3. Выберите фильтры: вузы, ИТ-направления, ИТ-программы, ИТ-продукты, ответственные, этапы. «Не указано» отбирает строки без значения. Если ничего не выбрано, фильтр не применяется. В блоке «Договор, лицензия и передача» можно отобрать по вендору, подписанию лицензии, году «Лицензия истекает до» и по тому, что не передано (материалы, лицензия, документация).
4. Отметьте «Колонки» отчёта. Для портфеля доступны договорные колонки: «Вендор», «Номер договора», «Подписание лицензии», «Срок лицензии», «Статус передачи», «Передача материалов» — они по умолчанию выключены.
5. Нажмите «Показать» — появится «Предпросмотр» по 50 строк с переходом по страницам и пояснениями сервера.
6. В блоке «Файл отчёта» выберите «Формат» (XLSX, XLS, PDF, JSON) и нажмите «Сформировать файл».
7. В «Заказанных файлах» статус меняется: «В очереди» → «Выбираем строки» → «Формируем файл» → «Готов». Нажмите «Скачать».

Выбор фильтров и колонок сохраняется в этой вкладке до выхода; «Сбросить выбор» очищает его. Если после заказа отчёта изменились ваши права, файл не выдаётся — сформируйте его заново.

[Скриншот: экран «Отчёты и статистика» с фильтрами и предпросмотром]

[Скриншот: список «Заказанные файлы» со статусом «Готов»]

### 14.8. Статистика и диаграммы

1. На экране «Отчёты и статистика» задайте вид отчёта, период и фильтры (как в 14.7).
2. В блоке «Статистика» выберите «Группировку»: по этапам, вузам, ИТ-направлениям, ИТ-программам, ИТ-продуктам, ответственным или месяцам.
3. Нажмите «Построить диаграмму». Появятся диаграмма и «Таблица основания диаграммы» с теми же числами.
4. «Скачать PNG» и «Скачать PDF» заказывают файл диаграммы на сервере; когда он готов, скачивание начинается автоматически.

Как читать диаграмму: шкала начинается с нуля; у каждого столбца подписано число; «Не указано» заштриховано и стоит последним — это строки без значения, а не ноль. Если столбцов больше 100, кнопки файлов неактивны: сузьте период или фильтры.

[Скриншот: блок «Статистика» с диаграммой и таблицей основания]

### 14.9. Руководитель: портфель команды и назначение КАМ

Руководитель видит в разделе «Вузы» все вузы своей команды. Вуз без ответственного помечен «Требует назначения».

**Назначить, сменить или снять ответственного:**

1. Откройте карточку вуза, блок «Назначение ответственного».
2. В поле «Новый ответственный» выберите активного КАМ своей команды и нажмите «Назначить ответственного».
3. Чтобы снять КАМ, нажмите «Снять назначение»; вуз получит отметку «Требует назначения».
4. «История назначений» показывает, кто, кому и когда передал вуз.

После смены ответственного прежний КАМ сразу теряет доступ к вузу и его файлам, а новый — получает.

[Скриншот: блок «Назначение ответственного» с историей назначений]

**Ведение карточек.** Руководитель ведёт карточки вузов команды наравне с КАМ: добавляет контакты и взаимодействия, переводит этапы, комментирует, меняет план и правит этапы карточки, загружает файлы — те же формы, что в разделах 14.3–14.6. В истории автором события указывается руководитель, а не ответственный КАМ вуза.

### 14.10. Руководитель: шаблоны этапов команды

В разделе «Вузы» сверху — блок «Шаблоны этапов».

1. Нажмите «Новый шаблон» или «Создать на основе базового» у базового шаблона — редактор откроется с его этапами и переходами.
2. Задайте «Название шаблона».
3. В разделе «Этапы» добавьте этапы («Добавить этап»), задайте названия, порядок («Выше», «Ниже»), отметьте «Необязательный».
4. В разделе «Явные переходы» задайте пары «Из этапа» → «В этап» («Добавить переход»); для пропуска этапа отметьте «Нужен комментарий».
5. Нажмите «Создать шаблон» или «Сохранить шаблон». Сервер проверит граф (раздел 13.3) и покажет ошибку, если процесс некорректен.

Шаблон команды доступен КАМ при создании взаимодействия. Изменения шаблона действуют только на новые взаимодействия. Базовый шаблон меняет администратор.

[Скриншот: редактор шаблона этапов]

### 14.11. Приём оплат и работа с анкетами (оператор зачисления)

Раздел «Зачисление» виден в шапке только сотруднику с флагом «Оператор зачисления» (назначает администратор, раздел 15.4) и только пока включён модуль «Слушатели» — иначе раздела нет.

**Загрузка оплат:**

1. Откройте раздел «Зачисление».
2. Нажмите «Загрузить оплаты» и выберите файл оплат сайта.
3. После загрузки CRM показывает протокол: сколько записей получено, пропущено (пустых), новых и найденных слушателей, зачислений, повторных заявок и переносов между потоками, а также предупреждений (например, оплата с телефоном или email, которые не удалось распознать, — поле анкеты остаётся пустым).

Повторная загрузка того же файла не создаёт дублей: уже принятые записи остаются без изменений, а недостающие зачисления достраиваются (раздел 13.10).

**Потоки и слушатели:**

4. Таблица «Потоки» показывает курс, номер, программу и счётчики «Оплачено / Анкеты / Выгружено / Передано / Ожидает / Окончание / Хранить до»; кнопка «Открыть» переходит к потоку.
5. В потоке укажите «Дата окончания потока» и нажмите «Сохранить» — от неё считается срок хранения анкет («Хранить до»).
6. В таблице «Слушатели потока» кнопка «Открыть анкету» у строки открывает анкету слушателя; в разделе «Поиск слушателя» (на экране потоков) можно найти слушателя точно по email, телефону, СНИЛС или фамилии.

**Анкета слушателя:**

7. Анкета разбита на группы «Основное», «Документы», «Личные сведения», «Адрес», «Дательный падеж», «Образование»; значения замаскированы. Кнопка «Показать» у группы раскрывает её значения (событие уходит в журнал), «Изменить» открывает форму правки после раскрытия.
8. После правки нажмите «Сохранить»; если анкету за это время изменил кто-то другой, появится сообщение с кнопкой «Обновить» — обновите анкету и повторите правку.
9. Если введённый СНИЛС уже есть у другого слушателя, CRM предложит сравнить обе анкеты и нажать «Перенести» — зачисления перейдут к найденному слушателю, пустые поля заполнятся из текущей анкеты, текущая анкета удалится.
10. Вкладки «Зачисления» и «История» под анкетой показывают потоки слушателя и события без значений персональных данных.

**Заполненный шаблон и файл для LMS:**

11. На экране потока кнопка «Загрузить заполненный шаблон» открывает диалог: выберите файл XLSX/XLS — CRM покажет предпросмотр со статусом каждой строки («Обновить», «Без изменений», «Ошибка», «Конфликт») и замечаниями по ячейкам; нажмите «Применить».
12. Кнопка «Выгрузить для LMS» открывает диалог выбора режима («Только не переданные» или «Все слушатели потока») и, если есть анкеты без обязательных полей, — «Выгрузить с пустыми ячейками» или «Исключить»; «Скачать файл» формирует XLSX по шаблону организатора.
13. После передачи файла в LMS нажмите «Отметить переданными» у соответствующей выгрузки в списке «Выгрузки для LMS».

[Скриншот: раздел «Зачисление» с формой загрузки оплат]

## 15. Руководство администратора

### 15.1. Вход и раздел «Администрирование»

Администратор входит так же, как пользователь (раздел 14.1). У роли ADMIN один раздел — «Администрирование»: «Профили CRM», «Команды», «Справочники», «Шаблоны этапов» (общие), «Импорт каталогов», «Источники данных», «Журнал администратора и безопасности», «Субъект персональных данных», «Сроки хранения». Карточки вузов и отчёты администратору не показываются: у него нет бизнес-области данных.

[Скриншот: раздел «Администрирование»]

### 15.2. Профили и права

**Учётная запись и профиль.** Логин и пароль хранит Keycloak; роль, команду и признак активности — профиль CRM. Вход без профиля CRM даёт «Профиль CRM недоступен».

**Блокировка и активация профиля:**

1. В блоке «Профили CRM» найдите сотрудника (роль, команда, статус «Активен» или «Заблокирован», ревизия доступа).
2. Нажмите «Заблокировать» и затем «Подтвердить блокировку». Доступ закрывается со следующего запроса сотрудника; вузы, где он был ответственным, снимаются с него и появляются у руководителя как «Требует назначения».
3. «Активировать» и «Подтвердить активацию» возвращают доступ; вузы автоматически не возвращаются.

Изменить собственный профиль нельзя.

[Скриншот: список «Профили CRM» с кнопкой блокировки]

**Изменение роли, команды и флага «Оператор зачисления».** В карточке профиля укажите роль (USER, LEADER, ADMIN, MANAGEMENT), команду (обязательна для активных USER и LEADER) и, если роль USER или LEADER, отметьте «Оператор зачисления» — это откроет сотруднику раздел «Зачисление» (раздел 14.11), когда включён модуль «Слушатели». Себе роль, команду и активность администратор изменить не может; систему нельзя оставить без активного администратора — последнего активного понизить или заблокировать нельзя. Каждое изменение видно в «Журнале» профиля (кнопка в его карточке).

**Профили создаются** кнопкой «Новый сотрудник» (учётная запись Keycloak и активный профиль, временный пароль показывается один раз) либо при первом входе сотрудника, заведённого в Keycloak вручную (раздел «Подключение нового сотрудника», `docs/roles.md`), со статусом «Ожидает активации»; первый администратор — только через `backend-bootstrap` при развёртывании. Интерфейс не позволяет выдать права самому себе.

**Команды.** Блок «Команды»: «Создать команду» (уникальное имя без учёта регистра), переименовать, архивировать пустую команду без активных профилей и вузов или восстановить её. У каждой команды виден состав: руководители, КАМ и число действующих вузов. «Перенести вуз» в карточке служебного списка организаций меняет команду вуза; КАМ, не входящий в новую команду, снимается с вуза автоматически.

**Пароли и учётные записи.** Временный пароль сотруднику выдаёт администратор CRM: «Профили CRM» → «⋯» → «Сбросить пароль»; там же «Завершить сеансы» и «Сменить почту» (`docs/roles.md`, «Учётные записи Keycloak из CRM»). Запасной путь, когда CRM недоступна, — команды на сервере (консоль Keycloak в публикационном варианте снаружи закрыта), например смена пароля:

```bash
docker compose --env-file .env.local exec keycloak /opt/keycloak/bin/kcadm.sh set-password -r rtk-crm --username <логин>
```

Перед этим выполняется вход `kcadm.sh config credentials` (полная последовательность — `docs/deploy.md`, «Демо-пользователи на публикуемом стенде»). Для увольняемого сотрудника достаточно заблокировать профиль CRM: CRM сама отключает его учётную запись в Keycloak и завершает сеансы. Если Keycloak был недоступен, у профиля появляется отметка «требует синхронизации» и кнопка «Отключить в Keycloak» — нажмите её, когда Keycloak заработает. Пользователь меняет свой пароль сам по ссылке «Сменить пароль» в шапке CRM.

### 15.3. Общие шаблоны процесса

Блок «Шаблоны этапов» в разделе «Администрирование». Администратор создаёт и меняет общие шаблоны, включая базовый шаблон по умолчанию. Порядок работы — как в разделе 14.10. Шаблон по умолчанию удалить нельзя. Изменение шаблона не меняет действующие карточки.

### 15.4. Импорт каталогов

Блок «Импорт каталогов».

1. Выберите «Профиль импорта»: «Каталог по ТЗ (10 полей)» или «Направления и программы».
2. При необходимости скачайте образец: «Скачать шаблон файла (10 полей ТЗ, 3 примера)». В примере замените ФИО менеджеров на ФИО реальных КАМ.
3. Выберите «Файл XLS или XLSX» и нажмите «Проверить файл». Сервер проверит формат и антивирусом, покажет листы.
4. Выберите «Лист». В «Сопоставлении столбцов» заголовки ТЗ сопоставляются автоматически; проверьте выбор. Поля со звёздочкой обязательны. В разделе «Дополнительно» можно указать столбцы ключей, реквизитов контакта и «Словарь статусов по передаче».
5. Нажмите «Создать предпросмотр». В «Протоколе предпросмотра» у каждой строки — статус, «Было», «Станет» и сообщения.
6. Для конфликтной строки можно указать явные UUID («Дополнительно: явные UUID для строк») и повторить предпросмотр.
7. Отметьте строки и нажмите «Применить», затем «Подтвердить применение». Если данные изменились после предпросмотра, применение отклоняется — создайте предпросмотр заново.

Импорт не создаёт учётные записи и роли: менеджер из файла должен уже быть активным КАМ. Правила сопоставления — `docs/import.md`.

[Скриншот: «Импорт каталогов» с протоколом предпросмотра]

### 15.4a. Справочники: направления, программы, вендоры, продукты

Блок «Справочники», вкладка на каждый вид записи.

1. «Добавить» — направление или программу (в направлении), вендора или продукт (у вендора); дубль по нормализованному названию среди действующих и архивных отклоняется («восстановите запись», если найден архивный).
2. «Переименовать» правит название с проверкой версии и того же правила дублей.
3. «Архивировать» скрывает запись из «Нового взаимодействия» и фильтров; направление или вендор с действующими программами или продуктами архивировать нельзя. «Восстановить» возвращает запись, если родитель не в архиве.
4. У вендора — вкладка «Контакты»: «Добавить контакт» (ФИО, телефон, email, канал «Почта» или «Telegram»), привязка к одному или нескольким продуктам вендора, архивирование контакта.
5. «Журнал изменений» — отдельная вкладка блока: кто, когда и что изменил в справочниках (создание, переименование, архивирование, восстановление).

Импорт справочника вендоров, продуктов и контактов файлом организатора — кнопка «Импортировать вендоров» в том же блоке; протокол работает как импорт каталогов (раздел 15.4).

[Скриншот: блок «Справочники» с вкладкой «Вендоры»]

### 15.5. Источники данных: LMS и сайт

Блок «Источники данных» в разделе «Администрирование» (`docs/integrations.md`).

1. **Moodle**: адрес, тайм-аут и токен технического пользователя задаются в конфигурации развёртывания (`.env.local`, не в интерфейсе); в блоке — список разрешённых курсов и «Сопоставить»: курс или группа Moodle → вуз, программа и даты потока.
2. **Сайт**: адрес и токен — тоже в конфигурации; на демо-стенде используется встроенный демонстрационный стенд `site-fixture` с пометкой «Предложенный контракт, DEMO».
3. «Запустить синхронизацию сейчас» — для каждого источника отдельно; ниже — расписание, время следующего планового запуска и признак «данные устарели», если синхронизация давно не выполнялась успешно. Ошибка синхронизации показывается баннером, не молчаливым нулём.
4. «Заявки, ожидающие разбора» — записи, которые не удалось сопоставить автоматически (новый вуз, оплата с курсом без сопоставления и подобное): «Сопоставить с вузом», «Создать вуз» или разбор с указанием причины.
5. «Сохранённые сопоставления» — список «курс/группа → вуз, программа, вид потока и даты» с правкой и историей запусков; удаление снимает и пересчитывает связанные снимки обучения.

Оплаченные заявки (`paid_order`) в этом же конвейере не создают вуз и не считаются заявками сайта — они уходят в модуль «Слушатели» (раздел 6.9) и в отчёт DEMAND (раздел 14.7).

[Скриншот: блок «Источники данных» с расписанием синхронизации]

### 15.6. Установка, обновление и резервное копирование

- Установка и публикация — раздел 8 и `docs/deploy.md`.
- Обновление версии: получить новый код (`git pull`) и снова запустить `./scripts/bootstrap-demo.sh`; схема БД обновляется миграциями автоматически при старте сервера. Перед обновлением сделайте резервную копию.
- Резервное копирование и восстановление — раздел 8.4. Расписание копирования (например, через cron сервера) и хранение копий вне сервера настраиваются администратором.
- Секреты стенда — в `.env.local` на сервере; файл хранится отдельно от резервных копий и не публикуется.

### 15.7. Журнал, персональные данные и сроки хранения

- «Журнал администратора и безопасности»: изменения профилей и команд, назначения КАМ, переносы вузов, запуски синхронизации, скачивания файлов и отчётов, действия с ПДн и учётными записями Keycloak. Фильтры по периоду, автору, объекту и разделу; «Выгрузить XLSX» и «Выгрузить CSV».
- «Субъект персональных данных»: по запросу человека введите ФИО, почту, телефон, СНИЛС или другие написания и нажмите «Найти». Находятся контакты вузов, профили сотрудников, упоминания в текстах и — по точному совпадению — слушатели модуля «Слушатели» (только то, что анкета есть, её состояние и потоки, без значений). Дальше — «Выгрузить сведения PDF/JSON», «Уточнить» и «Ограничить обработку» у контакта, «Ограничить обработку» и «Обезличить анкету» у слушателя (уточняет анкету оператор зачисления), отметки «Обезличить» и «Удалить файл» и кнопка «Обезличить» с подтверждением. Каждое действие попадает в журнал.
- «Сроки хранения»: действующие сроки (файлы отчётов, неактивные контакты, отключённые профили, журнал, анкеты слушателей), последний запуск, число анкет слушателей с предупреждением при приближении к 100 000, потоки без даты окончания и анкеты со старой версией ключа шифрования; кнопка «Применить сроки сейчас».

Правила — `docs/roles.md`, раздел «Безопасность и персональные данные».

### 15.8. Диагностика

- Состояние сервисов: `docker compose --env-file .env.local ps`.
- Журнал сервера: `docker compose --env-file .env.local logs backend`. Каждая строка содержит `requestId`; номер из сообщения пользователя находится поиском: `docker compose --env-file .env.local logs backend | grep <requestId>`.
- Журнал входов и административных действий — консоль Keycloak (realm `rtk-crm`, раздел событий) или Admin REST API изнутри контейнера.
- Swagger UI — `<адрес CRM>/swagger-ui/index.html`: описание всех операций и кодов ошибок.
- Если файл остаётся «Не удалось проверить», проверьте состояние контейнера `clamav` (`healthy`) и загрузите файл повторно.
- При ответе `503 REPORT_CAPACITY_EXCEEDED` все 10 построений заняты: повторите заказ позже.
