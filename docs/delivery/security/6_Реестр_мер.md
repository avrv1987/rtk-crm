# 6. Реестр требований ИБ со ссылками на проверки

Реестр отвечает на вопрос «чем подтверждено каждое требование». Для каждой меры указаны статус и проверка: автотест backend (класс и метод в `backend/src/test/java/ru/rtk/crm/`) или сценарий приёмочного тестирования на стенде. Реестр включает модуль «Слушатели» (раздел 6.9).

Статусы:

- **система** — мера выполняется продуктом, есть автотест или сценарий приёмочного тестирования;
- **регламент** — мера выполняется организационно у оператора ПДн, продукт её не заменяет;
- **не закрыто** — меры нет ни в продукте, ни в регламенте; нужна до работы с реальными ПДн;
- **не применимо** — мера не относится к CRM как к программному продукту.

Автотесты подтверждают поведение на уровне API и базы данных (H2 в режиме PostgreSQL). Живой Keycloak, nginx и Docker автотестами не проверяются — для них указан сценарий приёмочного тестирования.

Пункты со статусом «не закрыто»: шифрование томов (41а, мера оператора), автоматическое сканирование уязвимостей зависимостей и образов (45; следующий шаг — сканер в сборке с локальной базой уязвимостей). Второй фактор (7, IB-23) реализован, но выключен в демонстрационном режиме: при переходе в эксплуатацию задать `MFA_REQUIRED_FOR_PRIVILEGED=true` и запустить bootstrap (`docs/deploy.md`, раздел «Второй фактор входа»). Ключ резервных копий хранится у оператора отдельно от копий. Пункты со статусом «регламент» оператор оформляет в своих документах; утверждённые сроки хранения (30, срок анкет слушателей — раздел 1.3) задаются переменными окружения без изменения кода. Проверку публикации (IB-09) нужно повторять при каждом обновлении содержимого публичного репозитория.
